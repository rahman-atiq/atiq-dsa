Read the invoice properly

An insert's rotation restores the subtree's original height, so the repair stops dead. A delete's rotation can leave the subtree one level shorter — which is a brand new violation for the parent, and its parent, all the way up.

That is the price of |BF| ≤ 1: an invariant with zero slack notices every disturbance, and every repair it orders is a pointer rewrite.

The turn

AVL fought for a constant nobody asked for.

What "O(log n)" actually demands

height ≤ c · log₂n   for some constant c

Read that again. It says some constant. It does not say a small one. AVL spends effort on every single write to drive c down to 1.44. Big-O never asked for that. c = 2 is exactly as O(log n) as c = 1.44.

So what does c = 2 actually cost you?

Worst case at a million keys: about 40 comparisons instead of 29. Eleven extra pointer hops — in the worst case that basically never happens. On random keys both trees sit near 20. That is the entire downside, and we are about to find out what it buys.

Your design brief — write this one down

Invent a balance rule that obeys all four constraints:

aIt fits in one bit per node. Not a height. Not a counter. 01
bYou can check it by looking at a node and a couple of relatives — never by measuring a subtree.
cMost repairs move zero pointers.
dIt still caps the height at c · log n.

Five minutes, in pairs. Constraint (a) is the one that gives the game away — if you only get one bit, your rule cannot be about heights. It has to be about a label.

The mechanism

Now squeeze the two rules together and watch a bound fall out.

Ask for the extremes

Shortest possible path? Take no slack at all — every node black. Its length is exactly the black-height, bh.

Longest possible path? Take maximum slack. Reds cannot touch, so the greediest path is black, red, black, red… — one red between consecutive blacks. At most 2 · bh.

Both paths live in the same tree

longest ≤ 2 × shortest

No height is stored. No subtree is measured. No two depths are ever compared. The tree is balanced because of who may stand next to whom.

Count the nodes on each marked path
Cyan: 40→60, 2 nodes, all black. Rose: 40→20→10→5, 4 nodes, alternating. Both cross exactly three blacks (counting the NIL at the bottom). Worst ratio possible: exactly 2×.
Do the algebra yourself

Three lines. No proof machinery. Follow along on paper.

1A tree with black-height bh holds at least 2bh − 1 nodes. Delete every red node by folding it into its parent. What is left has exactly bh nodes on every path — so it is at least as full as a perfect tree of that height. n ≥ 2bh − 1
2At least half of any path is black. Reds can't be adjacent, so on a path of h nodes at most every other one is red. bh ≥ h / 2
3Substitute and rearrange. n ≥ 2bh − 1 ≥ 2h/2 − 1, so n + 1 ≥ 2h/2, so log₂(n+1) ≥ h/2.
h ≤ 2 · log₂(n + 1)

Search, insert and delete each walk one root-to-leaf path. All three are O(log n) — with c = 2, exactly as promised, and you just proved it in three lines.

Step 1, made concrete
bh = 3 → you cannot do it with fewer than 2³ − 1 = 7 nodes. Blacks are the skeleton, and rule 2 forces the skeleton to be perfectly balanced in count.

The trade, in one line. Reds are free slack that costs no structure; blacks are a rigid, perfectly-counted spine. You get to be sloppy — but only by a factor of two.

The answer, and the whole point of this lab

A colour violation can very often be repaired by flipping bits — writing zero pointers. AVL has no such move: every AVL repair is a rotation, because its invariant is about shape, and the only way to change shape is to move pointers.

recolour = 3 bit writes rotation = 6 pointer writes
Same idea, exam language

You invented two of these. Here are all five.

1Every node is either ●red or ●black. One bit.
2The root is black. Free to enforce — painting the root black adds one black to every path equally, so it can't break anything.
3Every NIL leaf is black. The leaves are the null pointers, not the keys.
4A red node's children are both black. ← this one is yours
5Every path from a node down to a NIL crosses the same number of black nodes. ← and this one

How to read them

4 and 5 are load-bearing. 1, 2 and 3 are bookkeeping that make 4 and 5 cheap to check.

Property 3 is the one everyone skips, and it shapes your C code: if NIL is a real black node, x->parent->colour is always safe to read and the fixup needs no null checks at all.

Notice what is absent: no property mentions height, depth or subtree size. Every one is checkable from a node and its immediate children — constraint (b) of your brief.

Counting convention. "Black-height 3" here counts the node itself (if black) and the NIL — what you count on paper. CLRS excludes the node, so its numbers run one lower. Say which you are using.

Why red and black? Guibas & Sedgewick, 1978 — by Sedgewick's own account, because the colour laser printer at Xerox PARC produced a particularly good red.

Two free deductions — make them yourself

This is the move AVL structurally cannot have: a rebalance that costs three bits and touches not one pointer.

Why this is the case that loops

G is now red. If G's own parent is also red, you have the identical problem again — just two levels higher. So set z = G and repeat.

Two levels per iteration, height ≤ 2log₂(n+1) → at most about log₂n iterations, and if you ever climb clean out of the top, you simply paint the root black — which property 2 says is always free.

Why recolouring is off the table here

The cheap fix needed to take a black off G and hand it to both children. U is already black — there is nothing to hand it. Blackening P while G stays put would rob every path through U. So the black has to change position, and changing position is precisely what a rotation is.

Case 3, in the order you must do it

1. Paint P black.  2. Paint G red.  3. Rotate at G, towards the light side.

P rises into G's old spot wearing G's old colour, and G drops down beside U as a red sibling. Both of them now hang under a black root, so property 4 holds and property 5 never moved. Rotation without the recolour fixes nothing — that is trap #3, later.

The bookkeeping trick, and why it exists

While you carry that debt the tree is illegal and awkward to reason about. So we pretend the node in the gap holds an extra unit of blackness — it is "doubly black".

Property 5 is then true by construction while you work, and the fixup's only job is to discharge that unit. An accounting fiction, not a new colour — no such thing exists in your struct.

4w black, outer redrotate at parent, recolour; stop

Red node leaving = free. Debt at the root = drop it. ≤ 3 rotations.

Costs

search O(log n) insert O(log n), ≤2 rot delete O(log n), ≤3 rot height ≤ 2 log₂(n+1) 1 bit per node

Black-height changes only at the root, only by recolouring, and only in whole levels.

The row that is not a difference

Both rotate at most twice per insertion. "AVL rotates more" is only reliably true for deletion, and for total restructuring across a long mixed run. Don't repeat the myth in its strong form.

If you're asked this in an interview

"Why does the kernel use red-black rather than AVL?" The answer is not "it's faster". It is: bounded rebalancing cost per single operation, and cheaper repairs under contention, paid for with a slightly deeper tree. Say it in that order.

Learn from other people's pain

The five mistakes, ranked by how often I see them.

1 · Putting the pen down after a case 1

Case 1 does not terminate — it hands you the same problem two levels up. Re-mark Z, P, G, U and ask the uncle again. Drill 4 exists to burn this in.

2 · Rotating without recolouring — or the reverse

In case 3 the rotation moves the black; the recolour kills the red-red. Do one alone and the tree is still broken, just differently. One move, not two.

3 · Inserting the new node black

It "looks safer". It turns a four-node local repair into a whole-tree problem with no local fix at all. New nodes are always red.

4 · Inventing cases that cannot exist

If P is red, G is black — the tree was legal a moment ago. Students burn minutes on "what if G is red too", which never happens. Use your free information.

5 · NULL instead of a sentinel

The delete fixup reads w->left->colour without blinking; with NULL leaves that segfaults, and you will "fix" it with null checks until the logic is unreadable. Property 3 says NIL is a black node — build one. And never forget the final root->colour = BLACK.

Two decisions before you write a line

Both of them fall straight out of the properties.

1 · Store a parent pointer

Every fixup walks upwards: node, parent, grandparent, uncle. Your AVL code walked down instead.

2 · Make NIL a real shared node

Property 3, taken literally: allocate one black node; point every empty child at it. Now x->parent->colour is always safe and the fixup needs no null checks.

typedef enum { RED, BLACK } Colour; typedef struct Node { int key; Colour colour; struct Node *left, *right, *parent; } Node; typedef struct { Node *root, *nil; } RBTree; /* the sentinel points at itself, so an accidental nil->left reads back black instead of crashing. */ t->nil->colour = BLACK; t->nil->left = t->nil->right = t->nil->parent = t->nil; t->root = t->nil;
/* x's right child y takes x's place. */ static void left_rotate(RBTree *t, Node *x) { Node *y = x->right; x->right = y->left; // 1. re-home the orphan if (y->left != t->nil) y->left->parent = x; y->parent = x->parent; // 2. link y to x's parent if (x->parent == t->nil) t->root = y; else if (x == x->parent->left) x->parent->left = y; else x->parent->right = y; y->left = x; // 3. put x below y x->parent = y; }

Count the writes: six, not four

Three child links and three parent back-links. Forget the back-links and it still looks right — until the fixup walks upward and falls off the tree.

right_rotate is not a second algorithm. Write left_rotate, then swap every left and right. If they differ otherwise, one is wrong.

Highest leverage in this lab

A broken tree still answers every search correctly.

/* returns 1 if legal; black-height via *bh */ static int check(RBTree *t, Node *n, int *bh, long lo, long hi) { if (n == t->nil) { *bh = 1; return 1; } if (n->key <= lo || n->key >= hi) // BST order return 0; if (n->colour == RED && // property 4 (n->left->colour == RED || n->right->colour == RED)) return 0; int lb, rb; if (!check(t, n->left, &lb, lo, n->key)) return 0; if (!check(t, n->right, &rb, n->key, hi)) return 0; if (lb != rb) return 0; // property 5 *bh = lb + (n->colour == BLACK); return 1; } int rb_valid(RBTree *t) { int bh; if (t->root->colour != BLACK) return 0; // property 2 if (t->nil->colour != BLACK) return 0; // property 3 return check(t, t->root, &bh, LONG_MIN, LONG_MAX); }

Why this comes before delete

A red-black tree can be structurally wrong for thousands of operations and still return correct answers to every search. Nothing observable from the outside will tell you. Only a property check catches it.

Then assert it after every operation

for (int op = 0; op < 500000; op++) { int k = rand() % N; /* insert or delete, mirrored into a plain char present[N] array */ assert(rb_valid(t)); // every single op }

Deliberately expensive, deliberately worth it: it turns "the tree broke at some point" into "it broke on this op with this key".

Build with gcc -Wall -Wextra -fsanitize=address,undefined.
