Data Structures

B-Trees
The tree every database actually uses.

You already know balanced binary trees — BST, AVL, red-black. They all assume that visiting any node costs roughly the same. That assumption is true while your data lives in RAM. The moment it doesn't, every one of those trees becomes the wrong shape for the job. This lesson explains why, and walks you through the tree that fixes it: what problem it solves, how it's built, and exactly how it inserts and deletes keys.

The problem

Your red-black tree is perfectly balanced. It's still going to feel slow.

Start with real numbers

Keys in the index109
Comparing two keys already in RAM~1 ns
Reading a random 4 KB block from an SSD~80 µs
Seeking on a spinning disk~9 ms

A billion keys don't fit in RAM. Every node your tree visits lives somewhere else on the device — so each visit costs one of the bottom two numbers, not the top one.

Do the arithmetic

Red-black tree height, 109 keys~30
A lookup visits 30 nodes — on an SSD2.4 ms
…on a spinning disk270 ms
Of that, time spent actually comparing keys30 ns

Almost none of that 2.4 ms is spent thinking. It's spent waiting for the disk to hand over pages. AVL trims height from 2log₂n to 1.44log₂n — a real win, but it only removes about ten of those thirty waits. You're still optimising the wrong number.

So what actually sets the cost of a lookup? Not how cleverly you compare keys — how many separate reads you do. And the number of reads is just the height of the tree. Which raises the real question this lesson answers: if height is the cost, what actually controls it?

The real cost unit

You asked the disk for 20 bytes. It handed you 4096.

Disks don't sell you bytes. They sell you blocks.

A disk can't hand back one byte at a time. The smallest unit it will read is a block — typically 4096 bytes. Ask for 20 bytes, you still pay for all 4096.

One red-black node — a key, two pointers, a colour bit — is about 24 bytes. The hatched part is the 4072 bytes you paid for and threw away. On every single level you visit.

So the real cost formula is simple

The thing that costs money is a page read. A lookup's price is the number of nodes on the path from root to leaf — the height — times one page read. Comparisons inside a page you've already paid for are free.

cost of a lookup ≈ height × page read

Every tree you've built so far has height O(log n) with base 2. If a page read costs 80,000× more than a comparison, base 2 is a bad trade — you want a tree that uses far fewer, far fatter pages.

The idea

Height comes from one number, and it was never the balance rule.

Where height actually comes from

A tree where every node has m children stores n keys in roughly

h ≈ logm n

Every balanced binary tree is stuck at m = 2. AVL and red-black aren't fighting over that formula — they're fighting over the constant in front of it. There's a much bigger lever nobody's touched: m itself.

Raise m and watch the height fall

What that tree needs to look like

Give a node a whole 4 KB page to itself, and it has to satisfy four things:

aHold many keys and many child pointers — enough to fill the page.
bKeep height at O(logm n) no matter what order keys arrive in.
cActually stay full. A tree of half-empty pages has fanout 2 again, and we're back where we started.
dRepair itself without moving pages around — moving a page means a disk write, and rotations move pages.

Constraint (d) is the one that changes everything: if you can't rotate, none of the rebalancing tricks from AVL or red-black trees are available to you. You need a genuinely different way to fix a broken tree.

Keys were never "the data". They're fences.

In a BST, a node's key answers one question: left or right? Here, k sorted keys answer: which of my k+1 buckets does your search key fall into? A node's job hasn't changed — you just gave it a bigger vocabulary.

Now name it

A node with sorted keys k₁ < k₂ < … < kj and j+1 children, where every key in child ci lies strictly between ki and ki+1, is an m-way search tree. Set m = 2 and this is exactly the definition of a binary search tree. The BST was the special case all along.

The operation

Scan the page you're on. Then follow one pointer.

The whole algorithm

Scan the sorted keys in the current node for your target. Find it? Done. Miss? You've landed between two keys — and that gap tells you exactly which child to follow. Repeat there.

One page read per level. The scan inside a page is essentially free — you already paid for those bytes when you read the page in.

Searching for 55 in a 3-way search tree
55 > 40 and 55 < 70, so take the middle branch. Scan that page: found. Two page reads total. A BST holding the same 8 keys would need three or four.
The catch

We just built the BST's original problem again — wider.

1The m-way search tree is only an ordering rule. Exactly like a plain BST, it says where a key must go — and says nothing about shape.
✗The tree on the right is a perfectly legal 3-way search tree. Every ordering rule holds. It's also a chain of height 5 with one key per page — a full 4 KB read to learn a single number.
✗And it's not a weird input. That's exactly what you get from inserting 10, 20, 30, 40, 50 in order — the most ordinary input there is.
2So an m-way tree gives you the potential for wide, shallow pages, with no guarantee you'll get it. It needs the same thing a BST needed: a discipline that forces good shape.

The relationship is one you already know: BST : AVL is to m-way search tree : B-tree. The first of each pair is just the ordering rule; the second adds the rule that makes the ordering actually pay off. That's what we build next.

The invention

You can't rotate. So instead of fixing a broken tree, refuse to let it break.

1Every leaf sits at exactly the same depth. Not "within one" like AVL — the same, always. There's no such thing as a long path anymore, because every path is the same length.
✗On its own that rule is worthless: the one-key-per-page chain from the last slide has exactly one leaf, so it trivially satisfies "all leaves at the same depth". Nothing yet forces pages to be full.
2Every node is at least half full: at least ⌈m/2⌉ children. Now a tree of height h is forced to hold at least 2⌈m/2⌉h−1−1 keys — so height can only grow if the key count grows exponentially with it.
3Two exceptions, both forced by reality: the root is exempt (a tree with 3 keys can't have a half-full root), and leaves have no children to count.

That's the whole invention. An m-way search tree that obeys those two rules is a B-tree. Everything left — splitting, merging, borrowing, the C code — is just how you keep those two promises while keys come and go.

One question worth sitting with

"All leaves at the same depth" is a strict promise. Add one key to a full leaf and it has to split — which would normally make that leaf deeper than its neighbours. How can insertion possibly keep every leaf level?

Hold that question. The answer, a few slides from now, is the single most elegant idea in this whole structure.

Written out formally

Same two rules, written the way you'll see them elsewhere.

1Every node holds at most m−1 keys and at most m children.
2Every node except the root holds at least ⌈m/2⌉−1 keys, and every internal one has at least ⌈m/2⌉ children.
3The root is exempt: at least 1 key, and at least 2 children if it isn't itself a leaf.
4All leaves are on the same level. This is the rule doing the real work.
5Keys inside a node are sorted, and child ci holds exactly the keys between ki and ki+1.

One naming note: this deck defines order m as the maximum number of children. Some textbooks (CLRS included) instead define a minimum degree t, where m = 2t. Same tree, different label — always check which convention a source is using before comparing numbers.

Why the rules work

Rule 2 is what puts m in the height formula.

1Write t = ⌈m/2⌉. The root sits alone at level 1. Level 2 has at least 2 nodes (rule 3), and every level below drags in at least t children per node — so level i has at least 2ti−2 nodes.
2Give every node its minimum key count and sum across levels: n ≥ 2th−1 − 1.
3Rearrange for h. Every step used a minimum, so this bounds height from above — a B-tree can never be taller than this.
h ≤ 1 + log⌈m/2⌉ ( (n+1) / 2 )

Notice the base of that log isn't 2 — it's ⌈m/2⌉. Rule 2 is exactly what put m into the denominator. Drop rule 2 and the base collapses back to 2, and you've reinvented a red-black tree with extra steps.

In practice it's even better

The root is read on every lookup, so it stays cached in RAM — often level 2 as well. A billion-key index typically costs one or two real disk reads, while the red-black tree's 30 touches were all misses.

Being precise

A B-tree doesn't compare fewer keys. It reads far fewer pages.

Multiply it out

Binary-searching the keys inside one page costs log₂m comparisons. You visit logmn pages. Multiply the two:

log₂m × logmn = log₂n

The m cancels out. Total comparisons are identical to a perfectly balanced binary tree — because a B-tree effectively is one, with its comparisons grouped into pages you'd already paid to read.

So what actually changed?

Not the comparisons — the number of separate reads. That's the whole win: fewer, fatter reads instead of many tiny ones.

Say it this way, not the other way

Comparisons per lookupunchanged
Pointer dereferences (reads)30 → 4
Bytes usefully read per page24 → 4096
Cache / page misses~30 → ~1

"B-trees are faster than AVL trees" is the wrong sentence. The right one: a B-tree does the same search with far fewer boundary crossings — and boundary crossings are what the hardware actually bills you for. If your data already fits in cache, an AVL tree can still win.

Insertion

New keys always land in a leaf. What if that leaf is already full?

The fix: overfill on paper, then cut

Let the page briefly hold m keys — illegal, but only in your head, for one step. Sort all m keys, then cut the page into left | median | right. The median key moves up into the parent, becoming the new fence between the two halves it just created.

The minimum is ⌈m/2⌉−1 = 2. Only the median leaves both halves at or above that — it's the only choice that works, not a stylistic one.

Why rule 4 can never actually break

Splits push keys upward. An ordinary leaf split leaves every leaf exactly where it was. The only event that changes a leaf's depth is the root itself splitting — and that adds one level to every path at once.

So "every leaf at the same depth" isn't something you enforce. It's something the structure makes impossible to break.

Growth runs backwards from what you're used to

Every other tree you've built grows downward at the leaves and gets rebalanced from above. A B-tree grows upward from the root. That single inversion buys perfect level balance for free — zero rotations, ever.

It's also the only way the tree ever gets taller, which is why height changes very rarely: at order 256, a tree crosses from 3 levels to 4 at around 5 million keys, and from 4 to 5 at around a billion. Most real indexes change height two or three times in their whole life.

Deletion

Splitting solved "too many keys". Deletion has to solve the opposite.

1The key is in a leaf with keys to spare (above the minimum). Just remove it. Nothing else to do — and this covers most deletions.
2The key is in an internal node. You can't just erase it — it's a fence other keys depend on. Instead, overwrite it with its in-order predecessor (the largest key in the subtree to its left) or successor — both always live in a leaf — then delete that key from the leaf instead.
3The leaf that lost a key is now below the minimum. This is called underflow. Fix it in this order: first try to borrow a key from a neighbouring sibling that has one spare; if none does, merge with a sibling instead.

Why the predecessor swap works

The predecessor is a perfect stand-in: it's larger than everything in the left subtree and smaller than everything in the right one — which is exactly what the fence you removed needs to be true. Ordering never wobbles, even for an instant.

And this trick converts every deletion into a leaf deletion. You only ever need to know how to repair a starved leaf — the same idea you used for BST deletion, just with wider nodes.

Only case 3 repeats, and it climbs at most one level per merge. Always try borrowing first — it's cheaper and stops immediately.

A merge can never overflow

Starved page (⌈m/2⌉−2 keys) + sibling (⌈m/2⌉−1 keys) + separator:

2⌈m/2⌉ − 2  ≤  m − 1

At order 5: 1 + 1 + 2 = 4, exactly the maximum. Merging is always safe by construction — you never need to check.

The mirror image of insertion

If merges cascade all the way to the root and empty it, the root is discarded and its one remaining child becomes the new root.

grows at the root  ·  shrinks at the root

That's the only place height ever changes, in either direction — which is exactly why every leaf stays level forever.

Why it rotates instead of sliding sideways

If 40 moved directly into the left leaf, you'd get 1040 sitting left of the fence 30 — but 40 is bigger than 30, which breaks the ordering rule. The only key that legally belongs there is the separator, 30, itself.

So 30 comes down, which leaves the fence slot empty — and the sibling's smallest key, 40, is the only key that can legally fill it. The rotation isn't a stylistic choice; it's forced.

Borrowing from the left is the mirror image

Same three moves, every direction reversed: the separator comes down to become the starved page's first key, and the left sibling's largest key goes up.

At an internal node, the key that moves drags a child pointer along with it. Forgetting that pointer is the single most common deletion bug.

The separator moving down is the catch

A merge always takes a key from the parent — two pages become one, so the parent needs one fewer fence. That means the parent is now a key lighter, and it might have been at its own minimum already.

So you re-check the same question one level up: does the parent underflow now? Borrow, merge, or stop — the same problem, one level higher. It's the exact mirror of a split cascading upward during insertion.

Always try to borrow first

Borrowing stops immediately and only touches 3 pages. Merging destroys a page, lowers the tree's fill, and can cascade all the way to the root — they're not equally cheap.

Check both adjacent siblings before giving up. A node's cousins don't count, though — only siblings that share your parent can lend, because only they have a separator key between you and them.

Insert

1Walk the fences down to a leaf. New keys always land in a leaf.
2Room? Slot it in, sorted, and stop. A full page (m−1 keys) is legal.
3Overflowed to m keys? Sort all m, take the median: left half stays, median goes up, right half is a new page.
4Parent overflowed too? Repeat. Root overflowed? Build a new root with 1 key — height +1.

The median is of all m keys including the new one — never of the original m−1.

Delete

1Key in an internal node? Overwrite it with its predecessor (or successor), then delete that from its leaf.
2Remove from the leaf. Still ≥ minimum? Stop.
3Underflow → try to borrow: check both adjacent siblings. Separator down, sibling's nearest key up. Stops immediately.
4Both siblings at minimum → merge: separator down, pages fused. Parent lost a key — repeat. Root emptied? Discard it — height −1.

Borrowing or merging at an internal page moves a child pointer along with the key.

What actually ships

Every database you've used indexes with a variant, not the plain original.

One small change

In a B-tree, a key carries its full record wherever it sits — a key in the root is data. In a B+ tree, internal nodes hold separator keys only, and every record lives in a leaf. A separator is a copy, so a key can appear twice: once as a fence, once as data. The leaves are then linked left to right in a list.

Why that tiny change wins

Internal pages carry no payload → more fences per pagehigher fanout
Higher fanout → fewer levelsshorter tree
Range scan — "rows between X and Y"walk the leaf list
Every lookup costs exactly h readspredictable latency

The range scan is the real payoff: WHERE age BETWEEN 30 AND 40 re-descends the whole tree for every match in a plain B-tree, but in a B+ tree it's one descent then a sequential walk — the access pattern disks are fastest at.

Learn from other people's bugs

The mistakes that show up again and again.

1Splitting a page that's merely full. A page holding m−1 keys is fine — you only split once it would hold m. Splitting early wastes work and lowers fill, undoing the whole point of rule 2.
2Taking the median of the wrong set. Insert the new key first, write out all m keys, then pick the middle one. Taking the median of the original m−1 gets it right about half the time by luck — which means you never notice when it's wrong.
3Erasing a key straight out of an internal node. That key is a fence, not just data. Overwrite it with its predecessor or successor, then delete that key from the leaf it actually came from.
4Losing a child pointer. When you borrow or merge at an internal node, the key that moves drags a subtree with it. Checking children = keys + 1 at every node catches this in seconds.
5Reaching for a merge too early. When a page starves, check both adjacent siblings for a lender before merging. Borrowing terminates immediately; merging can cascade all the way to the root.

A fast self-check, every time you finish a B-tree by hand. Read the leaves left to right — sorted? Count the keys in every node — within range, root exempt? Count the children — always keys + 1? Hold a ruler under the leaves — all on one line? Those four checks catch nearly every mistake above.

Implementation · 1 of 2

One decision before writing a line: give every page one spare slot.

#define M 5 /* order: max children */ #define MAXK (M - 1) /* max keys, m-1 = 4 */ #define MINK (((M + 1) / 2) - 1) /* min keys, = 2 */ typedef struct BTNode { int n; /* keys in use */ int key[MAXK + 1]; /* +1: the overfill slot */ struct BTNode *kid[MAXK + 2]; int leaf; } BTNode; typedef struct { BTNode *root; } BTree; /* the whole search, and it really is this short */ BTNode *bt_search(BTNode *x, int k, int *pos) { while (x) { int i = 0; while (i < x->n && k > x->key[i]) i++; if (i < x->n && k == x->key[i]) { *pos = i; return x; } if (x->leaf) return NULL; x = x->kid[i]; /* one page read */ } return NULL; }

Decision 1 — the overfill slot

key[MAXK+1] and kid[MAXK+2] are one slot larger than the rules allow. That spare slot lets the code overfill a page on purpose, exactly like the scratch-paper step, and only then cut it. Size the arrays tightly instead and you need a special case for "the key that didn't fit" — which is where most hand-written B-trees go wrong.

Decision 2 — no parent pointers

A split hands its median upward, and the recursion is already standing on the parent when the call returns. Unlike red-black fixup, nothing here ever walks back up: no parent field, no stack, no sentinel.

Read bt_search again

The inner while scans inside a page — free, since those bytes are already loaded. The outer one is the descent, and each trip is one page read. Those are the same two cost units from earlier in this lesson, in the same function.

Implementation · 2 of 2

Split, promote, and let the recursion do the climbing.

/* x holds MAXK+1 keys. The median leaves via *up; the new right page is returned. */ static BTNode *split(BTNode *x, int *up) { int mid = (MAXK + 1) / 2; /* = 2 */ BTNode *z = calloc(1, sizeof *z); z->leaf = x->leaf; z->n = MAXK - mid; /* = 2 */ for (int j = 0; j < z->n; j++) z->key[j] = x->key[mid + 1 + j]; for (int j = 0; j <= z->n; j++) z->kid[j] = x->kid[mid + 1 + j]; *up = x->key[mid]; /* moves up */ x->n = mid; return z; } static BTNode *ins(BTNode *, int, int *); /* → */ void bt_insert(BTree *t, int k) /* height changes here */ { int up; BTNode *r2 = ins(t->root, k, &up); if (!r2) return; /* no new root */ BTNode *r = calloc(1, sizeof *r); r->leaf = 0; r->n = 1; r->key[0] = up; r->kid[0] = t->root; r->kid[1] = r2; t->root = r; /* grew at the top */ }
/* NULL = absorbed, nothing for you to do. Non-NULL = I split; *up is the median and this is the page that goes to its right. */ static BTNode *ins(BTNode *x, int k, int *up) { int i = 0, promoted; BTNode *right = NULL; while (i < x->n && k > x->key[i]) i++; if (i < x->n && k == x->key[i]) return NULL; /* duplicate */ if (x->leaf) promoted = k; /* lands here */ else if (!(right = ins(x->kid[i], k, &promoted))) return NULL; /* child coped */ /* make room at slot i, then drop them in */ for (int j = x->n; j > i; j--) { x->key[j] = x->key[j - 1]; x->kid[j + 1] = x->kid[j]; } x->key[i] = promoted; x->kid[i + 1] = right; x->n++; return x->n <= MAXK ? NULL : split(x, up); }

Three return paths

Duplicate → NULL.
My child absorbed it → NULL.
I overflowed → the new right page.

A caller only ever needs to ask one question: "did my child hand me a key?" — the same paper method, as one question.

The last line is the whole algorithm

x->n <= MAXK ? NULL : split(...) — under the limit, stop; over it, cut and pass the median up. That one ternary is the cascade.

Prove it, don't just trust it

After every insert, assert: keys in range, children = keys+1, all leaves at one depth, in-order walk sorted. Write this check first — don't start on deletion until it passes.

That's the lesson

Fill the page.
Grow at the root. The rest follows.

The big idea isn't really a new tree — it's that the cost model chooses the data structure. When the unit of cost changed from comparisons to page reads, a structure that had been optimal for decades became the wrong answer. The fix wasn't a cleverer balance rule; it was a wider node.

The one sentence to keep

A B-tree is an m-way search tree that keeps every leaf on one level and every page at least half full — and it manages both without measuring anything, because it only ever changes height at the root.
