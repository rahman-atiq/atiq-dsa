Recursion

A function that calls itself is not a trick. It is you borrowing the one stack the machine already maintains, and letting the compiler write the pushes and pops.

The highlighted path is the call stack at one instant. Everything else in that tree has either already returned or has not been born yet — which is why the tree is your running time and the path is your memory. Arrow keys, or the buttons below, to move through the deck.

01 — the problem

Write me a loop nest whose depth is an input

The eight queens puzzle, with the eight replaced by a number read from stdin.

Place eight queens on a chessboard so that none attacks another. Eight is small, so brute force is honest work: try every square for queen one, every square for queen two, and so on.

In a language with loops and nothing else, that reads:

for (int a = 0; a < 64; a++)
 for (int b = a+1; b < 64; b++)
  for (int c = b+1; c < 64; c++)
   for (int d = c+1; d < 64; d++)
    for (int e = d+1; e < 64; e++)
     for (int f = e+1; f < 64; f++)
      for (int g = f+1; g < 64; g++)
       for (int h = g+1; h < 64; h++)
        if (legal(a,b,c,d,e,f,g,h)) report();

Eight nested loops, one per queen. It compiles. It even works. Now change the first line of main to scanf("%d", &n) and place n queens.

What just broke

You cannot write n nested loops. The loop nest is fixed when you compile; n arrives when you run. There is no for that generates more fors.

This is not a stylistic complaint. It is a structural one: the depth of the search is data, and the only tool you have is a construct whose depth is source code.

And the brute force above is not merely rigid, it is unaffordable. Choosing 8 squares from 64 is 4,426,165,368 placements. Testing them all at a nanosecond apiece is four and a half seconds for n = 8, and the universe's age for n = 20.

02 — what does not fix it

Four repairs, all attacking the wrong thing

Before reaching for recursion, people reach for these. Each is worth understanding, because each fails in an instructive direction.

A while loop and a goto

You can flatten any nest into one loop with a program counter and a jump. What you have then written is a state machine, by hand, whose states are "which queen am I placing". It works, and nobody — including you next month — can read it.

An array of loop counters

int idx[n], advance idx[r], carry into idx[r-1] when it overflows. This is closer than it looks, and it is a real technique. But notice what you are now maintaining: a stack of positions, a depth pointer, and an unwinding rule. You have not avoided the stack. You have rebuilt it, in application code, without a type checker.

Generate the source

Write a program that emits n nested loops and compile it. Genuinely done in production for fixed small n in hot numeric kernels. Useless when n is a runtime value, which was the entire problem.

A faster inner loop

SIMD the legality test. Cache the diagonals. Rewrite it in assembly. You will make 4.4 billion placements into 400 million placements and the n = 20 case is still not finishing.

Three of these attack the constant factor. The fourth attacks readability. The problem is neither: the shape of the computation is not known until it runs, and the tool has to be able to grow to fit it.

03 — the reframe

You are already carrying a stack. Use that one.

Every function call your program has ever made pushed a record onto it and popped it on return. It is there whether you use it or not.

The "array of loop counters" idea failed for a revealing reason: it reinvented a stack. So stop reinventing it and ask the better question.

What if the bookkeeping were the algorithm? If a function can call itself, then "place queen r, then solve the rest" becomes one line, the depth of the nest becomes the depth of the call chain, and the unwinding — the part everybody gets wrong by hand — becomes return.

That is all recursion is. Not elegance, not mathematics: a stack whose push and pop instructions are written by the compiler, from a description of one level.

You describe a single step and where the next step begins. The machine supplies the ladder.

What you get, and what you are billed

The bargain has exactly two sides, and knowing both is the difference between using recursion and being surprised by it:

  • You get automatic state save and restore at every level, correct by construction.
  • You pay one activation record per level alive, out of a fixed-size region you did not allocate and cannot grow.

The whole puzzle, recursively

void solve(int r) {
  if (r == n) { report(); return; }
  for (int c = 0; c < n; c++)
    if (safe(r, c)) {
      col[r] = c;     /* choose  */
      solve(r + 1);   /* explore */
      col[r] = -1;    /* un-choose */
    }
}

Eight lines, and n is now a variable. The loop nest of the previous slide is in there — it is the chain of solve frames, built at runtime, one per row.

The three-line body is the easy half. The reason this deck has twenty more slides is that the second bullet on the left — a fixed-size region you cannot grow — is where recursion actually kills programs.

04 — the mechanism

A call is a push, a return is a pop

Step through fact(4) and watch the only data structure involved.

▸ live frame▸ suspended, waiting on a callee▸ returned

What is in one activation record

  • the return address — where to resume in the caller
  • the caller's saved frame pointer, so the chain can be walked back
  • any callee-saved registers this function clobbers
  • the parameters that did not fit in registers
  • the local variables whose address is taken or which outlive a register
  • padding, because the ABI wants the stack pointer 16-byte aligned

On x86-64 a frame for a function this small is typically 32 or 48 bytes. Take the address of a 4 KB local array and it is 4 KB plus that.

Notice what the stepper shows and the source does not: at the moment fact(1) runs, four frames are alive. Three of them are doing nothing but holding a number and an address, waiting to be resumed. That waiting is the memory cost of recursion.

The frame is not yours. You did not malloc it, you cannot free it early, and when you run out there is no NULL to check — the process dies on a guard page. Recursion is the one place in C where you allocate memory by accident.

05 — the rules and the bill

Two rules make it correct. Two numbers make it affordable.

The rules

  1. A base case that returns without calling. At least one input for which the function does no recursive work at all.
  2. Every recursive call moves strictly toward it. Not "usually", not "on the inputs I tested" — there must be a quantity that decreases on every call and cannot decrease forever.

That decreasing quantity is the whole proof. For fact(n) it is n. For a tree walk it is the height of the subtree. For solve(r) it is n − r. If you cannot name it, you have not written a recursion, you have written a loop with no exit and extra steps.

The classic violation is subtle: gcd(a, b) written as gcd(b, a % b) recurses on a shrinking value and terminates. Written as gcd(b, a - b) it also shrinks — until a == b, when it stops shrinking and runs until the stack is gone.

The bill

Draw the tree of calls. It answers both cost questions at once, and it is the single most useful habit in this subject:

quantityread off the recursion tree
running timenumber of nodes × work per node
stack memorydepth × bytes per frame

These are wildly independent, and that is the point most courses skip.

  • fact(n) — a path. n nodes, depth n. Cheap in time, linear in stack.
  • hanoi(n) — a full binary tree. 2n+1−1 nodes, depth n+1. Ruinous in time, trivial in stack.
  • binary search — a path of length log n. Cheap in both.

"Recursion is slow" and "recursion uses a lot of memory" are different claims about different dimensions of the same picture, and a given recursion is usually guilty of at most one of them.

07 — recursion vs iteration

They are not rivals. They are the same machine, differently addressed.

Anything you can write recursively you can write iteratively and vice versa — the proof is that the compiler does the translation in one direction and an explicit stack does it in the other. So the choice is never about power. It is about which of these you would rather maintain.

recursioniteration
state between stepskept in frames, saved and restored for freekept in variables you declare and reset yourself
where the memory comes fromthe stack — fixed size, no failure returnthe frame you are already in, or the heap, which reports failure
cost per stepa call, a return, and a frame set-upa compare and a jump
shape of problem it fitsbranching, tree-shaped, depth not known until runtimelinear, one thing after another
what a bug looks likea crash with no line number, at a depth you never testedan off-by-one you can print
reading the codeone level, stated onceevery level, interleaved with the bookkeeping

Pick recursion when the data is tree-shaped — parsers, directory walks, expression evaluation, divide and conquer, anything backtracking. The structure of the code then matches the structure of the data, and that is worth a great deal.

Pick iteration when the recursion is linear and the depth is data. Walking a linked list recursively is elegant, correct, and one long list away from a segfault. The depth is the length of the list, and the length of the list is whatever your input says it is.

08 — tail recursion

Tail position is a precise thing, and almost nothing is in it

A call is in tail position if its result is the caller's result — with nothing left to do afterwards.

"Nothing left to do" is not a mood. It means no arithmetic, no assignment, no destructor, no cleanup — the return value of the callee travels straight out. When that holds, the caller's frame is dead the instant the call is made, so a compiler may reuse it instead of pushing a new one. The recursion runs in constant stack.

Not tail recursive

long fact(int n) {
  if (n <= 1) return 1;
  return n * fact(n - 1);
}

After fact(n-1) returns there is still a multiply to do, and the thing it multiplies by — n — lives in this frame. The frame must survive. Depth n.

Tail recursive

long fact_go(int n, long acc) {
  if (n <= 1) return acc;
  return fact_go(n - 1, acc * n);   /* nothing after */
}
long fact(int n) { return fact_go(n, 1); }

The multiply moved into the argument, so it happens before the call, not after. Now the frame has no future.

The transformation, as a recipe

  1. Find the work that happens after the recursive call.
  2. Add a parameter — the accumulator — that carries that work forward instead.
  3. The base case returns the accumulator rather than a constant.
  4. Wrap it, so callers keep the original signature.

And then it is a loop, mechanically

long fact(int n) {
  long acc = 1;
  while (n > 1) { acc *= n; n--; }
  return acc;
}

Reassign the parameters, jump to the top. That substitution is exactly what tail-call elimination performs, and seeing it written out is the point: a tail-recursive function is a loop that has not been spelled that way yet.

Watch for the impostor: return (void) helper(x), 0; and return f(x) + 0; are not tail calls. Neither is a call in a function with a local whose address escaped — the frame has to stay alive to keep that pointer valid.

09 — the limit is real

C does not promise to eliminate your tail call

Scheme guarantees it in the language standard. C says nothing at all.

Write the tail-recursive version, compile it at -O2, and gcc and clang will very likely turn it into a loop. Compile the same file at -O0 for a debugger session and they will not. Your function now consumes a frame per level in the build you are debugging and not in the build you shipped, which is a memorable way to find out that your test inputs were small.

So: never rely on tail-call elimination for correctness in C. If a recursion's depth is bounded by input size and the input is attacker-supplied, convert it to a loop yourself. Do not file the optimiser as a safety property.

Check what you actually got — the tail call becomes a jmp, the real call stays a call:

gcc -O2 -S -o - fact.c | grep -E 'call|jmp'

Both buttons recurse until the engine refuses, then binary-search for the exact depth that survived. The engine picks the frame layout, so read the ratio rather than the absolute levels — that is the part which transfers to C.

The ratio between those two numbers is the lesson. Same algorithm, same depth of logic, a few dozen locals declared inside the function — and the depth you can survive collapses. Locals in a recursive function are multiplied by the depth.

In C, the failure has no manners

There is no ENOMEM, no return value to test. The stack pointer walks into a guard page and the kernel sends SIGSEGV. In a build without frame pointers the backtrace is often 10,000 identical lines or nothing at all.

Catch it in testing instead: gcc -fsanitize=address reports stack-overflow with the recursing function named, which is the difference between a five-minute fix and an afternoon.

10 — measurement

Predict first, then press

Real implementations, counted exactly. The call counts are not estimates — every routine increments a counter on entry.

Nothing measured yet. Write your predictions down first — the fibonacci row is the one that surprises people, and it is more fun if you have committed.

Questions worth asking before you press

  • Recursive and iterative factorial: which does fewer multiplications? (Count them. The answer is neither.)
  • Naive fib(30) — order of magnitude of the call count?
  • Memoised fib(30) makes how many calls? Is it closer to 30, 300, or 3,000?
  • hanoi(20): how deep does the stack get? Most people guess far too high.

How to read it honestly

  • Calls and ops are exact and will reproduce on any machine. Compare those.
  • Milliseconds are not. They include JIT warm-up and garbage collection, and the same code in C has a different constant. Use them for orders of magnitude, never for "23% faster".
  • Max depth is the memory number. It is what would decide whether the C version survives.
  • The memoised row does more work per call than the naive row — a map lookup versus an addition. If you want the fair comparison, look at the call count and then ask what each call costs.

11 — tower of hanoi

The problem that is easier to solve than to state

Three pegs. n disks of distinct sizes stacked on peg A, largest at the bottom. Move the stack to peg C. One disk at a time, taken from the top of a peg, and never a larger disk onto a smaller one.

Attack it head-on and you get nowhere: which disk moves first? For n = 5 the answer is not obvious and the sequence is 31 moves long. So do not attack it head-on. Ask instead what has to be true just before the last big move.

The biggest disk has to get from A to C. For that, peg C must be empty and the other n−1 disks must be out of the way — which means all of them are stacked on B. So the hard part of the problem is a smaller copy of the problem.

That single observation is the whole solution, and it writes itself:

void hanoi(int n, char from, char to, char via) {
  if (n == 0) return;
  hanoi(n - 1, from, via, to);        /* clear the way   */
  printf("disk %d: %c -> %c\n", n, from, to);
  hanoi(n - 1, via, to, from);        /* rebuild on top  */
}

Note what the two recursive calls differ in: only which peg plays which role. The pegs are not named A, B and C in the body — they are source, destination and spare, and the spare of one call is the destination of the next. Getting that permutation right is the only thing to get right.

Why 2n − 1, and why you cannot do better

Let M(n) be the moves needed. The recursion gives M(n) = 2M(n−1) + 1 with M(0) = 0, so M(n) = 2n − 1.

And it is optimal, by the same argument run as a lower bound: at some point the largest disk must move, and at that moment every other disk is on the one spare peg. Getting them there costs at least M(n−1), and clearing them off afterwards costs at least M(n−1) again. No strategy escapes it.

So the algorithm is exponential and that is not a flaw in the algorithm. The output itself has 2n − 1 lines. The 64-disk temple version takes 264−1 moves — about 585 billion years at one move a second.

13 — backtracking

Choose, explore, un-choose

Hanoi's recursion always succeeds. Backtracking is what you do when a choice can turn out to be wrong.

A backtracking search walks a tree of partial solutions. At each node you extend the partial solution one step in every way that is still legal, recurse, and then undo the extension before trying the next one. The undo is what makes the sibling branches independent.

void search(State *s, int depth) {
  if (complete(s)) { report(s); return; }
  for (each candidate c at this depth) {
    if (!legal(s, c)) continue;     /* prune */
    apply(s, c);                    /* choose */
    search(s, depth + 1);           /* explore */
    undo(s, c);                     /* un-choose */
  }
}

Every backtracking program you will ever write is this. Sudoku, maze solving, graph colouring, the knapsack, regular expression matching, type inference, a SAT solver's core loop — all of them are apply, search, undo with different definitions of legal.

The two places it goes wrong

A missing undo. The most common bug in the whole family. It does not crash — it quietly leaks state from one branch into its sibling, and you get some right answers and some wrong ones. Write apply and undo as a pair, adjacent in the file, and make undo exactly invert apply.

Pruning too late. Testing legality only at the leaves turns the search back into brute force. Test the moment a choice is made — the earlier a branch dies, the more of the tree dies with it, and the saving is multiplicative.

The trap that hides: if apply allocates or mutates something undo does not exactly reverse — a counter incremented twice, a flag set but not cleared on the early-return path — the search still terminates and still prints answers. It just prints the wrong ones. Nothing catches this except a property test on the results.

Why an explicit stack is so much worse here

To do this with your own stack you must push not just "where am I" but "what do I have to undo when I come back", and pop it in the right order on every exit path. That bookkeeping is the recursion, badly. Here, undo(s, c) sits on the line after the call and runs on the way out. This is recursion earning its keep.

14 — eight queens

Three observations, and the search space collapses by six orders of magnitude

None of them is clever. Each one just refuses to generate something that could never work.

what you generatecomplete placements tested
every set of 8 squares out of 644,426,165,368
one queen per row, any column
two queens in a row always attack		16,777,216  = 88
one per row, no repeated column
so the placement is a permutation		40,320  = 8!

The third row is already a factor of 110,000 better than the first, and we have not written a search yet — only stopped generating placements that are illegal by inspection. That is the first half of backtracking: encode the constraints into the shape of the search, not into a test at the end.

The remaining constraint — the diagonals — cannot be folded into the representation the way rows and columns were. Two queens share a diagonal when |r1 − r2| = |c1 − c2|. That is the test that has to run during the search, and where it runs decides everything.

Test it only on finished permutations and you check 40,320 of them. Test it the moment you place each queen, and a conflict at row 2 kills every arrangement of rows 3 through 8 beneath it — thousands of placements never generated, from one comparison.

The representation is the first design decision

int col[N];   /* col[r] = column of the queen in row r */

One array of n ints. It cannot represent two queens in a row, so that whole class of illegal states is unreachable — not rejected, unrepresentable.

Contrast with int board[N][N], which can represent every illegal position there is and makes you test for all of them. Picking the type that cannot hold a wrong answer is most of the work.

The safety test, in full

int safe(int r, int c) {
  for (int i = 0; i < r; i++) {
    if (col[i] == c) return 0;              /* same column   */
    if (abs(col[i] - c) == r - i) return 0; /* same diagonal */
  }
  return 1;
}

Only rows above r are checked, because rows below have nothing in them yet. r - i is positive, so no abs is needed on that side.

This is O(r) per test. The next slide measures what it buys; slide 20 shows how to make it O(1) with three occupancy arrays, which is the version you would actually ship.

What each step is

  • place — a legal square was found for this row; recurse into the next row.
  • reject — the square is attacked from above. The branch is never entered. This is the prune, and it is where all the savings are.
  • undo — every option in the row below has been exhausted. Lift the queen and try the next column here.
  • solution — the last row was filled.

Keep an eye on the rejects per place ratio in the status line. Most of what this algorithm does is refuse to explore. The queens it places are the small minority of its work, and the ones it keeps are smaller still.

Things to try

  • Run n = 4 to completion. There are exactly 2 solutions and they are mirror images.
  • Set n = 6 and press next solution four times, then once more. It reports 4 and stops — n = 6 is a local minimum in a sequence that is otherwise climbing.
  • Watch row 0. The search will never find a solution with the first queen at the far edge for n = 6, and it spends a good fraction of its total effort proving that.

16 — pruning, measured

The recursion is not the algorithm. The pruning is.

Same recursive structure, same answers, one difference: where the legality test runs.

unpruned is only executed up to n = 8; above that it is the exact closed form

Predict the ratio at n = 8 before you press. Most people are three orders of magnitude low.

Where the closed form comes from

The unpruned search generates every one of the n columns at every one of the n rows, so the tree is a complete n-ary tree of depth n, and it visits

1 + n + n² + … + nn = (nn+1 − 1)/(n − 1)

nodes. At n = 10 that is 11,111,111,111 — a number you should never generate to confirm, which is why the deck checks the formula against the executed count for n ≤ 8 and then trusts the arithmetic.

Read the ratio column, not the times. The times are a JavaScript engine on your laptop and mean little. The node counts are exact, reproducible, and identical to what the C on slide 21 will do — they are a property of the algorithm, not of the machine.

Both columns are exponential. Pruning buys an enormous constant and a much smaller base, and it does not buy polynomial time — n-queens solution counting has no known polynomial algorithm. At n = 30 the pruned search is still hopeless. Backtracking makes intractable problems reachable at useful sizes; it does not make them tractable.

17 — design decisions

Three choices to make before you type a recursive function

1 · Where does the state live

Three options, in increasing order of how much you will like yourself later:

  • File-scope globals. Zero per-frame cost, no threading, no reentrancy, and untestable in isolation. Fine for a one-file exercise, wrong for anything else.
  • Pass everything as parameters. Pure and testable, and every parameter is copied into every frame at every level.
  • One pointer to a state struct. Eight bytes per frame, reentrant, testable. This is the answer almost always.

The rule underneath: anything that does not change across levels should be pointed at, not copied.

2 · How big is the frame

You multiply it by the maximum depth. A char buf[256] declared for convenience inside a function that recurses 5,000 deep is 1.2 MB of stack that no profiler will attribute to you.

  • Hoist big locals out, or make them static if there is genuinely one at a time.
  • Keep the parameter list short — every argument beyond the register-passed few is stack.
  • Beware struct parameters passed by value. A 64-byte struct as a parameter is 64 bytes per level.

3 · What bounds the depth

Answer this in writing before you ship. Every recursion falls into one of three cases:

  • Bounded by a constant — a fixed-arity expression tree, hanoi(n) for n ≤ 64. Safe.
  • Bounded by log of the input — balanced trees, binary search, merge sort's split. Safe at any realistic size.
  • Bounded by the input itself — list walks, unbalanced trees, JSON nesting depth from the network. Not safe. Either convert to iteration or enforce an explicit depth limit and return an error.

A parser that recurses once per [ and reads from a socket is a denial-of-service bug with a syntax highlighter.

Write the depth bound in a comment above the function. If you cannot state it, you do not yet know whether the code is correct — the base case tells you it terminates, but only the bound tells you it terminates before the stack does.

18 — the small ones in C

Three recursions, and the loops they turn into

#include <stdio.h>
#include <stdlib.h>

/* ---- not tail recursive: work remains after the call ----
   depth: n frames. For n = 20 this is fine; the type
   overflows long before the stack does. */
long fact(int n) {
  if (n <= 1) return 1;          /* base case   */
  return n * fact(n - 1);        /* multiply AFTER the call */
}

/* ---- tail recursive: the accumulator carries the work ----
   at -O2 gcc turns this into a loop and the depth is 1.
   At -O0 it is still n frames. Do not depend on it. */
static long fact_go(int n, long acc) {
  if (n <= 1) return acc;
  return fact_go(n - 1, acc * n);   /* nothing after */
}
long fact_tail(int n) { return fact_go(n, 1); }

/* ---- and the loop it provably is ---- */
long fact_loop(int n) {
  long acc = 1;
  while (n > 1) { acc *= n; n--; }
  return acc;
}

All three return identical values for every n in range — which is a test you should write, not a claim you should believe. The differences are entirely in the stack column.

/* ---- naive fibonacci: the tree that eats itself ----
   calls(n) = 2*fib(n+1) - 1. For n = 30 that is
   2,692,537 calls to compute 31 distinct values. */
long fib(int n) {
  if (n < 2) return n;
  return fib(n - 1) + fib(n - 2);
}

/* ---- memoised: same recursion, one line of memory ----
   the table turns the tree back into a path.
   memo[] must be sized n+1 and cleared to -1. */
long fib_memo(int n, long *memo) {
  if (n < 2) return n;
  if (memo[n] >= 0) return memo[n];
  return memo[n] = fib_memo(n-1, memo) + fib_memo(n-2, memo);
}

/* ---- iterative: two variables, no stack at all ---- */
long fib_loop(int n) {
  if (n < 2) return n;
  long a = 0, b = 1;
  for (int i = 2; i <= n; i++) { long c = a + b; a = b; b = c; }
  return b;
}

The memoised version is still recursive and still uses n frames of stack. Memoisation fixes the time axis of the recursion tree and does nothing whatever to the depth axis. If you needed the depth fixed, you needed the loop.

Note memo[n] = ... as the return expression: assignment in C yields the value assigned, so the store and the return are one statement. Idiomatic here, and the reason the function reads as one rule rather than three.

19 — hanoi in C

Four lines, and the forty lines you did not have to write

The recursion

/* depth bound: n frames, and n is the disk count,
   which is bounded by the width of a long. Safe. */
static long hanoi_moves;

void hanoi(int n, char from, char to, char via, FILE *out) {
  if (n == 0) return;
  hanoi(n - 1, from, via, to, out);
  hanoi_moves++;
  if (out) fprintf(out, "%d %c %c\n", n, from, to);
  hanoi(n - 1, via, to, from, out);
}

Read the argument order of the two calls against each other. In the first, the destination is the spare; in the second, the source is the spare. That swap is the entire algorithm, and it is the only line worth checking twice.

The base case is n == 0, not n == 1. Both work, but n == 0 means the function is total — it is correct for every non-negative input with no special case at the bottom. Prefer the base case that removes work rather than adds it.

The same thing, with the stack in your hands

typedef struct { int n; char a, c, b; int stage; } Frame;

void hanoi_iter(int n, FILE *out) {
  Frame st[65];  int top = 0;              /* n <= 64 */
  st[top++] = (Frame){ n, 'A', 'C', 'B', 0 };
  while (top > 0) {
    Frame *f = &st[top - 1];
    if (f->n == 0) { top--; continue; }
    if (f->stage == 0) {                   /* before first call */
      f->stage = 1;
      st[top++] = (Frame){ f->n-1, f->a, f->b, f->c, 0 };
    } else if (f->stage == 1) {            /* between the calls */
      if (out) fprintf(out, "%d %c %c\n", f->n, f->a, f->c);
      f->stage = 2;
      st[top++] = (Frame){ f->n-1, f->b, f->c, f->a, 0 };
    } else top--;                          /* after second call */
  }
}

Look at stage. It exists because the function has three resumption points and an explicit stack has to record which one you are returning to. That field is the return address, hand-rolled. This is precisely the work the compiler does for you, and it is why "just use a loop and a stack" is advice with a price on it.

Both versions emit byte-identical output for n = 1 to 12 — verified, not assumed. If you write the iterative one yourself, diff it against the recursive one; that is the only test that catches a swapped peg.

20 — n-queens in C

The safety test, in O(1), with the un-choose as its mirror

#define MAXN 16

typedef struct {
  int  n, col[MAXN];
  char colUsed[MAXN];     /* is column c taken?          */
  char d1[2 * MAXN];      /* diagonal r + c     (↘ to ↗) */
  char d2[2 * MAXN];      /* diagonal r - c + n (↗ to ↘) */
  long solutions, nodes;
} QState;

static void q_search(QState *q, int r) {
  q->nodes++;
  if (r == q->n) { q->solutions++; return; }

  for (int c = 0; c < q->n; c++) {
    int a = r + c, b = r - c + q->n;
    if (q->colUsed[c] || q->d1[a] || q->d2[b]) continue;

    q->col[r] = c;                                  /* choose    */
    q->colUsed[c] = q->d1[a] = q->d2[b] = 1;

    q_search(q, r + 1);                             /* explore   */

    q->colUsed[c] = q->d1[a] = q->d2[b] = 0;        /* un-choose */
    q->col[r] = -1;
  }
}

long queens(int n, long *nodes) {
  QState q; memset(&q, 0, sizeof q); q.n = n;
  for (int i = 0; i < n; i++) q.col[i] = -1;
  q_search(&q, 0);
  if (nodes) *nodes = q.nodes;
  return q.solutions;
}

Why two diagonal arrays, and why the + n

Squares on the same ↗ diagonal share r + c, which runs 0 … 2n−2. Squares on the same ↘ diagonal share r − c, which runs −(n−1) … n−1 — and negative indices are undefined behaviour. Adding n shifts it into 1 … 2n−1, which is why the arrays are 2 * MAXN and not MAXN.

This is the single most common bug in the fast version, and ASan catches it instantly. Run the sanitised build once and you never debug it.

The choose line and the un-choose line are literal mirrors, three assignments each, in the same order. Write them together, and never let an early return, break or goto appear between them — that is how the undo gets skipped and the search starts leaking state into its siblings.

What this buys over the O(r) scan

The obvious safe() from slide 15 walks every row above r. That is O(n) per candidate and O(n²) per node. The occupancy arrays make it three array reads.

It does not change which nodes are visited — both versions visit exactly 2,057 nodes at n = 8. That equality is worth asserting in a test, because a fast prune that accidentally prunes more is a wrong answer wearing a performance win.

MAXN 16 is not decoration. n = 16 already takes minutes; n = 20 is days. A fixed bound you can state beats a malloc you cannot afford to use.

21 — testing it

Test the property, not the printout

Hanoi has one correct move sequence; n-queens has 92 correct answers at n = 8 and no natural order. Neither is testable by comparing to a golden file you typed by hand.

Replay the moves on real pegs

/* Does not care WHICH moves were produced. Checks only
   that every one of them was legal and the tower arrived. */
int hanoi_check(const char *path, int n) {
  int peg[3][32], h[3] = {0, 0, 0};
  for (int d = n; d >= 1; d--) peg[0][h[0]++] = d;

  FILE *f = fopen(path, "r"); if (!f) return 0;
  int disk; char s, t; int steps = 0;
  while (fscanf(f, " %d %c %c", &disk, &s, &t) == 3) {
    int si = s - 'A', ti = t - 'A';
    if (si < 0 || si > 2 || ti < 0 || ti > 2) return 0;
    if (h[si] == 0) return 0;                  /* empty source  */
    if (peg[si][h[si]-1] != disk) return 0;    /* buried disk   */
    if (h[ti] > 0 && peg[ti][h[ti]-1] < disk)
        return 0;                              /* large on small */
    peg[ti][h[ti]++] = peg[si][--h[si]];
    steps++;
  }
  fclose(f);
  if (h[2] != n) return 0;                     /* all arrived   */
  for (int i = 1; i < n; i++)
    if (peg[2][i-1] < peg[2][i]) return 0;     /* in order      */
  return steps == (1 << n) - 1;                /* and optimal   */
}

Five independent properties, each one a rule of the puzzle stated directly in code. A solver that produces a different but equally valid sequence still passes — which is exactly what you want from a test, and exactly what a golden-output diff cannot give you.

The whole harness

int main(void) {
  int ok = 1;

  /* three factorials, three fibonaccis, must agree */
  for (int n = 0; n <= 20; n++)
    if (fact(n) != fact_tail(n) || fact(n) != fact_loop(n)) ok = 0;

  /* hanoi: legal, optimal, and the explicit-stack version
     must emit byte-identical output to the recursive one */
  for (int n = 1; n <= 12; n++) {
    write_recursive(n, "/tmp/_h1.txt");
    write_iterative(n, "/tmp/_h2.txt");
    if (!hanoi_check("/tmp/_h1.txt", n)) ok = 0;
    if (!hanoi_check("/tmp/_h2.txt", n)) ok = 0;
    if (!files_equal("/tmp/_h1.txt", "/tmp/_h2.txt")) ok = 0;
  }

  /* queens against the known sequence, OEIS A000170 */
  const long known[] = {0,1,0,0,2,10,4,40,92,352,724,2680,14200};
  for (int n = 1; n <= 12; n++)
    if (queens(n, NULL) != known[n]) ok = 0;

  /* and the fast prune must visit the SAME nodes as the slow one */
  for (int n = 4; n <= 10; n++) {
    long fn = 0, sn = 0;
    long fs = queens(n, &fn), ss = queens_slow(n, &sn);
    if (fs != ss || fn != sn) ok = 0;
  }

  puts(ok ? "ALL PROPERTY TESTS PASSED" : "FAILURES");
  return !ok;
}

Build it this way every time, and especially the first time:

gcc -std=c11 -Wall -Wextra -O2 \
    -fsanitize=address,undefined recursion.c -o recursion

ASan is the only tool that gives a recursion a civilised death. Without it a stack overflow is a bare SIGSEGV; with it you get stack-overflow and the name of the offending function. The diagonal-index bug from the previous slide is caught by the same flag.

22 — where it wins, where it loses

Use it for trees. Be suspicious of it for lists.

Where recursion is the right answer

  • Parsers. Recursive descent is the default way to parse a programming language, because grammars are trees and the code ends up shaped like the grammar.
  • Filesystem and tree walks. Depth is bounded by path depth.
  • Divide and conquer. Merge sort, quicksort, FFT, Karatsuba. Depth is log n.
  • Backtracking search. Sudoku, SAT solvers, constraint solvers, regex engines, type inference.
  • Anything on an algebraic data type — expression evaluation, tree rewriting, interpreters.

Where it loses

  • Linear recursion over user-sized data. A recursive linked-list length is a crash with extra steps. Use a loop.
  • Unbalanced trees from untrusted input. A BST built from sorted keys is a list; a recursive walk on it dies. Deeply nested JSON has been a real CVE in more than one parser.
  • Tight numeric kernels. Call overhead per element is real when the body is three instructions.
  • Embedded and kernel code. 4 KB stacks; many style guides ban recursion outright, and they are right to.
  • Overlapping subproblems. Not recursion's fault, but plain recursion will happily recompute fib(3) five times and never mention it.

Reach for instead

  • A loop — for linear recursion, always.
  • An explicit stack — when the depth is data-driven and unbounded. It fails with a testable NULL, not a signal.
  • A depth cap and an error return — the minimum defence for any parser reading from a network.
  • Memoisation or a DP table — when the recursion tree repeats itself.
  • An accumulator, then a loop — when you want tail recursion's shape without depending on the optimiser.

Exercises — predict first, then instrument

  1. Before running anything: how many calls does fib(20) make? Now instrument it and check. The exact rule is calls(n) = 2·fib(n+1) − 1 — derive it from the recursion tree rather than fitting it to data.
  2. Write sum_to(n) recursively and call it with n = 1,000,000. Predict what happens, then find the smallest n that crashes on your machine. Now add char pad[1024] as an unused local and find the smallest crashing n again. Explain the ratio between the two numbers.
  3. Compile fact_tail at -O0 and -O2 and diff gcc -S output. Find the call that became a jmp. Then add printf("%d", n) after the recursive call and confirm the jmp goes away — you moved the call out of tail position.
  4. Delete the un-choose line from q_search and run the harness. Predict first: does it report too many solutions, too few, or crash? Then explain the number it actually gives.
  5. Make the diagonal bug real: change d2[r - c + n] to d2[r - c] and run under ASan. Find the smallest n that trips it, and say why n = 1 does not.
  6. Instrument hanoi to record the maximum depth reached. Predict it for n = 20 before you run it, then explain to someone else why it is not 1,048,575.
  7. Write hanoi_iter from scratch without looking at slide 19, then diff its output against the recursive version for n = 1 … 12. Count how many attempts it takes. That count is the honest price of "just use a loop".
