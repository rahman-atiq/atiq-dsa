Heap sort

Selection sort spends O(n) finding the maximum and then throws away everything it learned. A heap remembers.

The result is the only comparison sort that is simultaneously O(n log n) in the worst case, in place, and free of recursion. Arrow keys, or the buttons below, to move through the deck.

02 — the problem

Selection sort rediscovers the same array n times

The algorithm is not wrong. It is amnesiac.

Selection sort has exactly one idea: find the largest remaining element, put it where it belongs, repeat. The idea is correct. The cost is in the word find.

Each pass scans the whole unsorted region to locate the maximum. That scan learns a great deal — it sees every pairwise comparison along the way — and at the end of the pass it discards all of it and starts again from nothing.

Press the button. The comparison count is n(n−1)/2 for every input, sorted or not. Selection sort has no best case.

03 — the problem

Things that do not fix this

  • Scan from both ends. Cocktail-style, grab the max and the min in one pass. Halves the number of passes. Still n²/2 comparisons.
  • Remember the second largest. After removing the max, the runner-up is the new max — but only if you tracked it, and tracking it correctly for the next pass means tracking the whole ordering. You have reinvented sorting.
  • Faster comparisons. Comparisons were never the bottleneck. There are simply too many of them.
  • Sort the array first, then read off the maxima. Circular.

Every one of these attacks the cost of a pass. The problem is not the cost of a pass — it is that there are n of them, each starting from zero.

The quantity to attack is the information thrown away between passes. If the array could carry a little structure forward — not full sorted order, just enough to make the next maximum obvious — each pass would cost a fraction of a scan.

That is the whole of heap sort, stated before we know what a heap is.

04 — the problem

Merge sort and quicksort each give up something you may need

Two O(n log n) sorts already exist. Neither closes the gap.

Quicksort (Lomuto)O(n²)O(1)O(n) depth worst caseno
Heap sortO(n log n)O(1)none neededno

Merge sort's guarantee is real, and it is paid for with a second array the size of the first. On an embedded device, or inside a kernel, that buffer may simply not exist.

Quicksort is usually faster than either, and its worst case is not a curiosity — the Lomuto partition you already know degrades to O(n²) on already-sorted input, which is the most common shape real data arrives in.

The gap: a sort that is guaranteed O(n log n), uses no extra memory, and needs no stack. Nothing above is all three.

05 — the reframe

We never needed the array sorted. We needed the maximum, repeatedly.

Sorted order is an answer to a much harder question than the one selection sort is asking.

Selection sort asks the array a single question, n times: who is the largest of you? It does not need to know the ordering of the rest. It never uses that information.

Full sorted order answers that question — and also answers a million questions nobody asked. Maintaining it is expensive precisely because it is so informative.

So the question becomes: what is the weakest ordering that still makes "who is the largest" free?

What the answer has to satisfy

  1. The maximum is findable in O(1) — no scan.
  2. After the maximum is removed, the structure repairs itself in O(log n), not O(n).
  3. It lives inside the original array. No second buffer, no malloc, no pointers.
  4. It can be established from an unordered array cheaply — ideally in O(n), or the setup cost eats the saving.

A structure satisfying all four gives a sort immediately: build it once, then extract n times.

06 — the heap

A heap is a partial order, and that is the point

You have just built BSTs. A heap relaxes almost every rule a BST enforces, and gets something in return.

A binary search tree orders every node against every other: everything left of a node is smaller, everything right is larger. Read it in order and the array falls out sorted.

A max-heap enforces one rule and nothing else:

Every node is ≥ both of its children. Siblings have no relationship. Cousins have no relationship. A node on the left may be larger than a node three levels up on the right.

That looseness is not a defect to be apologised for. It is the reason repair costs one root-to-leaf path instead of a rebalance, and it is the reason a heap survives being stored in a bare array.

Say it out loud once: a heap is not sorted. It only knows who is biggest.

BST — every node ordered against every other
Max-heap — same keys, only parent ≥ child

07 — the heap

The array is the tree. There are no pointers anywhere.

This is the slide to slow down on. Everything afterwards is index arithmetic.

the small number beside each node is its array index
  1. The tree is complete: every level full except possibly the last, which fills left to right. This is what makes the array packed with no gaps.
  2. Node i has children 2i+1 and 2i+2.
  3. Node i has parent (i−1)/2, integer division.
  4. Indices n/2 … n−1 are the leaves. They have no children, so they are already valid one-node heaps.

The tree is a way of reading the array. It is never built. No node struct, no left and right fields, no allocation — the parent-child relationship is arithmetic on an index.

This is also why a heap has no rotations, no rebalancing and no deletion cases. The shape is fixed by n alone; only the values move.

Property 4 is the one students skip, and it is the one that makes the build step cheap.

08 — the heap

Completeness caps the height at ⌊log₂ n⌋, for free

No invariant to maintain, no rotations to perform. The shape cannot degenerate.

An AVL or red-black tree pays, on every write, to keep its height near log n. A heap gets the same bound without paying anything, because completeness is a property of the shape and the shape is determined entirely by how many elements there are.

A complete tree with n nodes fills level d with 2d nodes. After h full levels it holds 2h+1−1 nodes, so h = ⌊log₂ n⌋. Feed a heap sorted input, reverse input, or all-equal input: the height is identical, because the height never depended on the values.

Every sift travels one root-to-leaf path. The height bound is therefore also the bound on the work of a single repair — and unlike an average, it is a guarantee.

09 — mechanics

siftDown is the entire algorithm

One procedure. Build uses it, sort uses it, priority queues use it. Learn it and you are done.

The situation siftDown handles is always the same: one node may be too small for its position, and everything below it is already a valid heap. That precondition is what makes it cheap.

The rule: compare the node with its children. If a child is larger, swap with the larger of the two and continue from the new position. Stop when the node is ≥ both children, or when it reaches a leaf.

Swap with the larger child, always. Swap with the smaller one and the promoted child ends up below its own sibling — the invariant breaks one level down, silently, and the array still looks plausible. This is the classic heap bug.

Cost: one comparison pair per level, at most ⌊log₂ n⌋ levels.

3 is too small — children are 9 and 7
swap with 9, the larger — 9 ≥ 7 holds
swap with 7 instead — 7 < 9, broken

10 — mechanics

Build from the bottom, and the whole build costs O(n)

The surprising one. Most of the tree is leaves, and leaves do no work.

Half the nodes are leaves and are already heaps, so start at the last internal node, index n/2 − 1, and siftDown backwards to index 0. Every call meets its precondition, because everything below it has already been fixed.

The cost argument is a counting argument. A node at height h sifts at most h levels, and a complete tree has about n/2h+1 nodes at height h. Most nodes sit near the bottom where h is 0 or 1. Summing h·n/2h+1 over all heights converges to a constant multiple of n — the log never appears.

The rival approach — start with an empty heap and insert n times, sifting each new element up — is O(n log n) in the worst case. Press the button rather than take that on trust; the gap only shows on some inputs, which is the interesting part.

11 — mechanics

The sort loop: one array, two regions, no extra memory

This is why a max-heap produces ascending order, which trips up everyone the first time.

heap region — still being repairedfinal position — never moves again

Once the heap is built, a[0] is the largest element in the array. The largest element belongs at the end. So swap it there, declare that slot finished, and shrink the heap by one.

The swap has put some arbitrary leaf at the root, which is the one situation siftDown was written for — and every subtree below the root is still a valid heap. One siftDown, and the shrunken heap is correct again.

Repeat n−1 times. The sorted region grows backwards from the end, which is precisely why a max-heap yields ascending order.

The two regions share one array and never overlap. That is the entire memory cost of heap sort: a loop variable and one temporary for the swap.

Want descending order? Build a min-heap instead. Do not sort ascending and reverse the array — that is an extra O(n) pass for nothing, and a min-heap is the same code with one comparison flipped.

Note the asymmetry with the build phase: build fixes n/2 nodes each sifting a little; the sort loop fixes one node n times, each sifting a lot. Build is O(n), the loop is O(n log n), and the loop dominates.

13 — mechanics

Five boundaries, and what each one does when you get it wrong

None of these produce a crash. All of them produce an array that is nearly sorted, which is worse.

15 — measurement

What the harness says, including the part that is awkward

Run slide 14 before reading this. The numbers below are the ones the page computes; they are named as patterns, not as figures.

Heap sort barely notices the input. Random, ascending and descending land within roughly ten percent of each other. There is no adversarial input to find, because the work is determined by the tree's shape and the shape is determined by n.

The maximum single sift never exceeds ⌊log₂ n⌋. That is the row that matters for anything real-time — not the total, but the worst one operation.

All-equal input is heap sort's best case. Nothing ever sinks, so the whole sort collapses to about 3n comparisons.

On random input, heap sort loses to quicksort on comparisons. Both are O(n log n) and quicksort still does noticeably fewer. Heap sort is not the fastest sort; it is the most predictable one. A deck that hid this would be selling something.

Randomising the pivot does not save Lomuto on duplicate keys. The all-equal column goes quadratic for both pivot rules, because the partition puts every equal element on one side regardless of which one you pick. The fix is three-way partitioning, not randomisation — and heap sort needed neither.

16 — implementation

Four decisions to make before you type a line

A reader who understands the choices can adapt the code. One who only has the code cannot.

0-based indexing. Children are 2i+1 and 2i+2. Many textbooks use 1-based, where children are 2i and 2i+1 and the arithmetic is prettier — at the cost of wasting slot 0 and of every array in C being 0-based anyway. Pick one and never mention the other; mixing them is the most common source of off-by-one heap bugs.

Iterative siftDown, not recursive. The recursion is a tail call and compilers usually eliminate it, but "usually" is not a guarantee. Written as a loop, heap sort's stack usage is a fixed handful of bytes — which is the whole reason to choose it over quicksort on constrained hardware.

Size passed explicitly, not stored. sift_down(a, i, n) takes the heap size as a parameter because during the sort loop the heap shrinks while the array does not. A struct holding its own size would have to be mutated on every extraction, and forgetting to is the bug on slide 13's last row.

Max-heap for ascending output. Swapping the root to the end grows the sorted region backwards. A min-heap here would produce descending order — correct code, different answer.

All four decisions are visible in one signature: static void sift_down(int *a, int i, int n).

17 — implementation

siftDown and build, in full

static void swap(int *a, int i, int j) { int t = a[i]; a[i] = a[j]; a[j] = t; }

/* Precondition: the subtrees rooted at 2i+1 and 2i+2 are already max-heaps.
   Postcondition: the subtree rooted at i is a max-heap.
   n is the size of the HEAP, not of the array. */
static void sift_down(int *a, int i, int n)
{
    for (;;) {
        int l = 2 * i + 1;
        int r = l + 1;
        int big = i;

        if (l < n && a[l] > a[big]) big = l;   /* left child exists and is bigger  */
        if (r < n && a[r] > a[big]) big = r;   /* right child may not exist at all */
        if (big == i) return;                  /* already >= both children: done   */

        swap(a, i, big);
        i = big;                               /* follow the element down          */
    }
}

static void build_heap(int *a, int n)
{
    for (int i = n / 2 - 1; i >= 0; i--)       /* last internal node, backwards    */
        sift_down(a, i, n);
}

The for (;;) loop with an internal return is deliberate: the exit condition is discovered in the middle of the body, after both children have been examined, and forcing it into a while header means computing big twice.

if (r < n && a[r] > a[big]) compares against a[big], not a[i]. That single detail is what makes it the larger child rather than just a larger child.

C's && short-circuits, and that is load-bearing. Reverse the operands to a[l] > a[big] && l < n and you read past the heap boundary before checking whether you may. Address sanitizer will not always catch it, because the memory is still inside the array — it is the sorted region.

n / 2 - 1 on an empty or single-element array gives −1 and 0 respectively; the loop body simply does not execute or does nothing. No special case needed.

18 — implementation

The sort is six lines, and two of them are the trap

void heap_sort(int *a, int n)
{
    build_heap(a, n);
    for (int end = n - 1; end > 0; end--) {
        swap(a, 0, end);          /* largest of the heap to its final slot */
        sift_down(a, 0, end);     /* heap shrinks: end, not n              */
    }
}

Everything heap sort needs beyond the input array: end, i, and one int inside swap. That is the O(1) space claim, stated concretely.

sift_down(a, 0, end), not (a, 0, n). After the swap, a[end] holds a finished element. Passing n leaves it inside the heap, it is the largest thing there, and it sifts straight back to the root. The array then never sorts and the loop still terminates — you get a wrong answer with no crash and no warning.

end > 0, not end >= 0. When one element remains it is trivially in place. Running to zero swaps a[0] with itself, which is harmless but tells a reader you had not thought about the boundary.

Trace it by hand on {4, 10, 3, 5, 1} before running it. Build gives {10, 5, 3, 4, 1}; the first extraction should leave {5, 4, 3, 1 | 10}. If your trace disagrees with the code, one of the two is wrong and it is worth finding out which before you compile.

19 — implementation

Write the validator first

A broken heap answers most queries correctly for a long time. Only a property check finds the operation that broke it.

int is_max_heap(const int *a, int n)
{
    for (int i = 0; i < n; i++) {
        int l = 2 * i + 1, r = l + 1;
        if (l < n && a[l] > a[i]) return 0;
        if (r < n && a[r] > a[i]) return 0;
    }
    return 1;
}

int is_sorted(const int *a, int n)
{
    for (int i = 1; i < n; i++)
        if (a[i - 1] > a[i]) return 0;
    return 1;
}

static int cmp_int(const void *x, const void *y)
{
    int a = *(const int *)x, b = *(const int *)y;
    return (a > b) - (a < b);
}

static void harness(void)
{
    unsigned s = 2463534242u;
    int a[64], b[64];

    for (int trial = 0; trial < 20000; trial++) {
        s ^= s << 13; s ^= s >> 17; s ^= s << 5;
        int n = (int)(s % 64);
        for (int i = 0; i < n; i++) {
            s ^= s << 13; s ^= s >> 17; s ^= s << 5;
            b[i] = a[i] = (int)(s % 50);   /* small range: forces duplicates */
        }

        build_heap(a, n);
        assert(is_max_heap(a, n));         /* check the invariant on its own  */
        for (int end = n - 1; end > 0; end--) {
            swap(a, 0, end);
            sift_down(a, 0, end);
            assert(is_max_heap(a, end));   /* ... after every single sift     */
        }

        qsort(b, (size_t)n, sizeof *b, cmp_int);
        assert(is_sorted(a, n));
        assert(memcmp(a, b, (size_t)n * sizeof *a) == 0);
    }
    printf("harness: 20000 trials, n = 0..63, duplicates included -- OK\n");
}

The assertion inside the extraction loop is the one that earns its keep: it checks the invariant after every sift, so a failure names the operation that broke it rather than the operation that noticed.

Check the property, not the printed output. is_max_heap does not care which of several valid heaps you produced — many arrangements of the same keys are legal heaps, and a test that demanded one specific arrangement would fail on a correct implementation.

Small n, small value range. n = 0..63 exercises the empty array, the single element, the one-child node and both parities of n. s % 50 forces heavy duplication, which is where the comparison operators matter: use >= instead of > in sift_down and you get pointless swaps between equal elements that this harness will not catch — but a swap counter will.

20 — implementation

The same machine, doing the job it is actually used for

Heap sort is a nice sort. The priority queue is why heaps are everywhere.

typedef struct { int *a; int n, cap; } PQ;

static void sift_up(int *a, int i)
{
    while (i > 0) {
        int p = (i - 1) / 2;
        if (a[i] <= a[p]) break;
        swap(a, i, p);
        i = p;
    }
}

int pq_push(PQ *q, int v)
{
    if (q->n == q->cap) return 0;
    q->a[q->n] = v;
    sift_up(q->a, q->n);
    q->n++;
    return 1;
}

int pq_pop_max(PQ *q, int *out)
{
    if (q->n == 0) return 0;
    *out = q->a[0];
    q->a[0] = q->a[--q->n];
    sift_down(q->a, 0, q->n);
    return 1;
}

A sort needs the heap built once and drained once. A priority queue needs elements to arrive over time, so it needs the operation heap sort never uses: siftUp, for an element inserted at the end that may be too large for its position.

siftUp compares against one parent, siftDown against two children. That asymmetry is why building by repeated insertion costs more than building bottom-up, and it is the same asymmetry measured on slide 10.

pq_pop_max moves the last element to the root rather than promoting a child. Promoting a child would leave a hole in the middle of the array and destroy completeness, and completeness is the only reason the index arithmetic works.

This is the structure underneath Dijkstra's algorithm, task schedulers, event simulation, and the k-largest problem you will meet in interviews. Slides 21 and 22 assume you have seen it.

21 — where it wins and where it loses

Heap sort is chosen for its worst case, and for nothing else

Where it is genuinely used

  • As quicksort's parachute. C++'s std::sort is introsort: quicksort until the recursion gets suspiciously deep, then switch to heap sort. Quicksort supplies the speed, heap sort supplies the guarantee.
  • Kernel and embedded code. The Linux kernel's generic sort() is heap sort. No allocation, no recursion, no worst case — the three things kernel code cannot tolerate.
  • Hard real-time systems, where the number that matters is the slowest possible run, not the average.
  • Anywhere an adversary chooses the input. Quicksort's worst case is reachable on purpose; heap sort has no input to construct.
  • The heap itself, far more often than the sort — priority queues, Dijkstra, schedulers, top-k.

Where it loses, and to what

  • Average-case speed: use quicksort. Slide 14 shows it doing fewer comparisons, and the wall-clock gap is wider than the comparison gap, because heap sort jumps from index i to 2i+1 and defeats the cache on every level. Quicksort walks memory sequentially. This is heap sort's real weakness and it is invisible in Big-O.
  • Stability: use merge sort. Heap sort is not stable, and cannot easily be made so. Equal keys are reordered by the swaps.
  • Nearly-sorted data: use insertion sort or Timsort. Heap sort has no best case worth the name — it does the same Θ(n log n) work on an already-sorted array.
  • Small n: use insertion sort. Below roughly a few dozen elements the build phase is not worth it.

If you take one sentence away: heap sort trades average speed for the absence of a bad case. Choose it when you have to answer the question "what is the slowest this can possibly be?"

  1. Trace it. On paper, build a heap from {4, 10, 3, 5, 1}, writing the whole array after each sift_down call. How many swaps? Now instrument the C and check.
