one instance, one class, one chain — and one rule that searches them in a fixed order

Python OOP

Classes, properties, mixins, descriptors and metaclasses are not five features. They are five consequences of one lookup rule, and the rule fits on a slide.

This deck goes from class Dog: to writing your own metaclass, but it refuses to teach them as a list. 01 — the failure

A program of dicts and functions has nowhere to put a rule

Here is a bank account, written the way you would write it on day one. It works, and it is wrong in two ways that will not show up for months.

def make_account(owner, balance=0):
    return {"owner": owner, "balance": balance}

def deposit(acct, amount):
    acct["balance"] += amount

def withdraw(acct, amount):
    acct["balance"] -= amount

# ... 40 files and 3 months later
acct["balnce"] = 500          # a typo is a new key, silently
acct["balance"] = -2_000_000  # the rule was never written down

The rule "a balance may never go below zero" exists in somebody's head. There is no place in this program to put it where every write has to go past it, because every write is a write to a dict from anywhere.

Count the places that could break the invariant: every line in the codebase that can reach the dict. Count the places that check it: the ones you remembered. The second number never catches up with the first.

And the second failure

Dispatch. The same shape of code, asked to handle more than one kind of thing:

def area(s):
    if s["type"] == "circle":
        return pi * s["r"] ** 2
    if s["type"] == "rect":
        return s["w"] * s["h"]
    raise ValueError(s["type"])

Now add a triangle. You edit area, perimeter, draw, scale and to_json — five functions, in five files, and nothing tells you when you miss one. The fifth one fails in production, on the one input nobody tested.

changefiles touched
New shape kind5 functions, 1 per branch
New operation1 function
Missed a branchruntime, in production

Note which way round that is. Adding a kind is expensive, adding an operation is cheap. Remember it — at the end of the deck it is the reason a function sometimes beats a class.

02 — and what does not fix it

Four patches that leave the hole exactly where it was

Before reaching for classes, it is worth watching the obvious repairs fail. Each of these is something people really ship.

A naming convention

"Only functions in account.py may touch the balance key." Nothing enforces it. The rule survives exactly as long as the one person who remembers it.

A checking helper

def check(acct): assert acct["balance"] >= 0 — real, and useless, because it has to be called. The bug is the write that forgot to call it.

A "type" field

Moves dispatch from five if-chains to five if-chains that agree on a spelling. The branching, and the missed branch, are untouched.

Defensive checks at every call site

This one does work — and that is what makes it instructive. It works by putting the invariant in N places, so it holds until someone adds the N+1th. The cost of correctness grows with the size of the program, which is the definition of a design that does not scale.

The common thread: in every patch, the data and the rules about the data are in different places, and only convention connects them. Any fix that leaves them apart is a fix that has to be reapplied forever.

So the interesting question is not "how do I check the balance?" It is "how do I make it impossible to reach the balance without going past the check?"

03 — the reframe

Stop asking what the data looks like. Ask who is allowed to touch it.

Both failures have the same shape once the question is turned around:

  • The invariant. Not "where do I check the balance", but "how do I make the balance reachable only through code that checks it?"
  • The dispatch. Not "how do I branch on the kind", but "how does the value itself decide what a call means, so no caller has to?"

Those two questions have one answer: attach the functions to the data, and let the lookup of a name on a value decide which function runs. That is all an object is.

An object is a namespace with a search path. Everything in the rest of this deck — self, @property, inheritance, super(), mixins, dunder methods, descriptors, metaclasses — is a consequence of what that search path is and what it finds.

The same account, with the hole closed

class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance   # goes through the setter

    @property
    def balance(self):
        return self._balance

    @balance.setter
    def balance(self, v):
        if v < 0:
            raise ValueError("balance may not go negative")
        self._balance = v

Every assignment to acct.balance anywhere in the program now runs those three lines. Not by convention — by the lookup rule, which finds the property before it finds anything else.

The call sites did not change. acct.balance = 500 still reads like a plain attribute, because it still is one: what changed is what the name resolves to. That is the slide the next eight build toward.

04 — what a class statement is

A class body is a block of code that runs, once, immediately

Most languages treat a class as a declaration the compiler reads. Python treats it as a statement it executes: the body runs top to bottom in a fresh namespace, and whatever is left in that namespace becomes the class.

class Noisy:
    print("   class body executing")
    x = 1
    print("   after x = 1:", [k for k in dir() if k == 'x'])
$ python3 noisy.pyCPython 3.14.6
   class body executing, namespace so far: []
   after x = 1: ['x']

No instance exists. Nothing was called. The print ran at definition time, because a class body is just code.

And when the body finishes, Python hands its three results — the name, the bases, the namespace — to a callable that builds the class object:

The class statement, desugared

class Dog(Animal):
    sound = "woof"
    def speak(self): ...

# is, near enough:
ns = {}

Dog = type("Dog", (Animal,), ns)  # build the class
>>> type('D', (object,), {'greet': lambda self: 'hi'})

D().greet()   -> 'hi'
type(D) is type          -> True
type(type)               -> <class 'type'>

type is a class whose instances are classes. Sit with that for a second: it is the whole of metaclasses, twenty-five slides early, and you have already seen it work.

Two facts to keep: a class body runs, and the thing that turns its namespace into a class is an ordinary callable you can replace.

05 — instances

Two dictionaries, and a rule about which one wins

An instance is a dict plus a pointer to its class. The class is a dict plus a pointer to its bases. Almost everything else is bookkeeping.

class Dog:
    species = "canis"         # lands in Dog.__dict__

    def __init__(self, name):
        self.name = name      # lands in the instance __dict__

06 — the classic

The mutable class attribute, which every Python programmer ships once

Predict before you read on. Two dogs. Only the first is ever touched. What does the second one print?

class Dog:
    tricks = []

    def add(self, t):
        self.tricks.append(t)

a, b = Dog(), Dog()
a.add("sit")
print(b.tricks)
$ python3 dogs.pyCPython 3.14.6
b.tricks after only a added: ['sit']
a.tricks is Dog.tricks: True

There is only ever one list. It was created once, when the class body ran, and it lives in Dog.__dict__ — so every instance that looks up tricks and finds nothing of its own gets that list.

Why the previous slide explains it

self.tricks.append(t) contains no assignment. It reads self.tricks — which misses in the instance and hits in the class — and then mutates the object it found. Nothing ever writes to the instance dict, so nothing ever shadows.

Change it to self.tricks = self.tricks + [t] and the bug vanishes, because assignment writes to the instance. The same expression, one character of difference in intent, opposite behaviour.

The rule: a class attribute is shared by every instance. That is fine for species = "canis", which is immutable, and a bug for [] or {}, which are not. Per-instance mutable state is created in __init__:

class Dog:
    def __init__(self):
        self.tricks = []      # a new list per instance

Twenty-four slides from here, @dataclass will refuse to let you write the broken version at all — it raises at class-creation time rather than letting you find out in production. That refusal is the same rule, enforced earlier.

07 — methods

self is not magic. It is the argument you can see.

A method is a plain function, stored in the class namespace like any other value. The only unusual thing happens when you look it up through an instance.

class Dog:
    def speak(self, loud=False):
        return "WOOF" if loud else "woof"

rex = Dog()

rex.speak()        # 'woof'
Dog.speak(rex)     # 'woof'  — the same call
Dog.__dict__['speak']
# <function Dog.speak at 0x...>
rex.speak
# <bound method Dog.speak of <Dog object>>

Looking the function up on the class gives you a function. Looking it up on an instance gives you a bound method: a small object holding the function and the instance, which calls the function with that instance as the first argument.

Who does the binding?

Not the interpreter, specially. Functions implement __get__, and the lookup rule calls __get__ on anything it finds in a class that defines it. The bound method is the return value of that call.

f = Dog.__dict__['speak']
f.__get__(rex, Dog)
# <bound method Dog.speak of <Dog object>>
f.__get__(rex, Dog)()   # 'woof'

That mechanism is the descriptor protocol, and it has its own slide later. For now, note only this: self is not a keyword, not a compiler trick, and not special-cased. It is the first parameter of a function that something handed the instance to.

Which is why self is spelled out in every signature: Python would rather show you the argument than hide it. Rename it to this and every method still works — it is a convention, and the only reason to keep it is that everyone else has.

Now we have seen the lookup rule do three different things — find a class attribute, be shadowed by an instance one, and call __get__ on what it found. The next slide states the rule exactly, once, and then we can stop guessing.

08 — the one rule

What obj.name actually does

  1. Walk type(obj).__mro__ in order. Stop at the first class whose __dict__ holds the name; call what you found M.
  2. If M is a data descriptor — it defines __set__ or __delete__ — return M.__get__(obj). Stop. The instance never gets a say.
  3. If the name is in obj.__dict__, return that.
  4. If M exists, return M.__get__(obj) if it is a descriptor, otherwise M itself.
  5. If nothing was found and the class defines __getattr__, call it.
  6. Otherwise raise AttributeError.

Six steps. Every remaining slide in this deck is one of them, used deliberately. @property is step 2. A method is step 4. __slots__ is step 2. A mixin changes step 1. A metaclass changes what is in the dicts that step 1 walks.

Note the order of 2 and 3. Nearly everyone assumes the instance always wins — it does not, and the exception is precisely the mechanism that lets @property enforce an invariant no assignment can dodge.

Look a name up on rex, an instance of Dog(Animal). The walk below is produced by a real implementation of the six steps, not a recording.

    09 — the step everybody gets wrong

    A data descriptor outranks the instance dictionary

    This is the experiment. Put a value directly into the instance's __dict__, bypassing every setter, then read the attribute back. If the instance dict always won, the answer would be obvious.

    class Loud:                       # data: defines __set__
    def __get__(self, obj, owner): return "from descriptor"
    def __set__(self, obj, v): raise AttributeError("read-only")

class Holder:
    x = Loud()

h = Holder()
h.__dict__['x'] = "from instance dict"   # smuggled in
print(vars(h), h.x)
    $ python3 descr.pyCPython 3.14.6
    vars(h) = {'x': 'from instance dict'}   h.x = from descriptor
vars(h2) = {'y': 'from instance dict'}  h2.y = from instance dict

    The value is right there in the instance, and the read does not return it. Holder.x defines __set__, so step 2 fires and step 3 never runs.

    The second line of that output

    h2's class holds a descriptor with only __get__ — a non-data descriptor. Same smuggled instance value, opposite answer: the instance dict wins, because a non-data descriptor is step 4 and the instance is step 3.

    what the class holdswho wins
    __get__ + __set__
    property, slot, validator    		the class, always
    __get__ only
    function, classmethod, staticmethod    		the instance, if it has one
    a plain value
    strings, ints, lists    		the instance, if it has one

    Why the language is built this way. Methods are non-data descriptors, so obj.method = something_else is allowed to shadow a method on one instance — occasionally useful, and harmless.

    Properties are data descriptors, so obj.balance = -1 cannot dodge the setter, no matter what the caller does. The invariant from slide four holds because of this row of the table.

    This is also why __slots__ works at all, and why a class with __slots__ refuses attributes it did not declare. Both are on their own slide later.

    10 — the hooks

    Three ways to intercept the rule, and one that will bite you

    __getattr__

    Called only when the normal lookup failed. Step 5. Cheap: an attribute that exists costs nothing extra, because this never runs for it.

    def __getattr__(self, n):
    if n.startswith("get_"):
        return lambda: self.data[n[4:]]
    raise AttributeError(n)

    Always raise AttributeError for names you do not handle. Returning None instead breaks hasattr, copy, pickle and every library that probes for optional hooks.

    __getattribute__

    Called for every attribute access, before anything else. It is the six-step rule; overriding it replaces the rule wholesale.

    def __getattribute__(self, n):
    log(n)
    return object.__getattribute__(self, n)

    The trap: writing self.anything inside it calls it again. Infinite recursion, and the traceback is a thousand identical frames. Always delegate to object.__getattribute__.

    __setattr__

    Called for every assignment, including the ones in __init__. The symmetric trap, and the more common one:

    def __setattr__(self, n, v):
    self.__dict__[n] = v       # correct
    # self.n = v               # recursion

    Useful for freezing an object after construction, or for validating any name rather than one named field.

    Reach for these last. In order of preference: a plain attribute, then @property for one named field, then a descriptor for the same rule on many fields, then __getattr__ for a genuinely open-ended namespace — a proxy, an RPC stub, a config object over a dict. __getattribute__ is for people writing tracing tools, and it makes every attribute in the class slower.

    11 — privacy

    There is no private, and the thing that looks like it is not it

    Python has no access control. It has one convention and one name transformation, and confusing them for security is how people end up disappointed.

    _balanceNothing at all. A note to a human: not part of the contract, may change. Every tool and every caller can still touch it.

    What mangling is for

    Not secrecy — collision avoidance. A base class that stores self.__cache is guaranteed that no subclass, written by someone who never read it, can clobber that name by accident. The two __cache attributes are different keys.

    Use it in a base class meant to be subclassed by strangers. Everywhere else, one underscore says what you mean and costs nothing.

    If your threat model includes the caller, Python is the wrong tool. A determined caller reads vars(obj). What _ and __ buy you is a clear line between the part of the class you promise to keep working and the part you reserve the right to rewrite on Tuesday.

    The real encapsulation tool in Python is the one on the next slide: not hiding the attribute, but controlling what happens when it is touched — while it still reads like an attribute at every call site.

    12 — properties

    Why Python does not need a getter on every field

    In a language without properties, exposing a field is a one-way door: change your mind later and every call site changes with it. So people write getters for everything, defensively, forever.

    class Circle:          # version 1, day one
    def __init__(self, r):
        self.r = r

    Ship it. Two months later you need to reject negative radii and to cache the area. In Python the class changes and nothing else does:

    class Circle:          # version 2
    def __init__(self, r):
        self.r = r              # still goes through the setter

    @property
    def r(self):
        return self._r

    @r.setter
    def r(self, v):
        if v <= 0:
            raise ValueError(f"radius must be positive, got {v}")
        self._r = v

    @property
    def area(self):             # computed, read-only
        return pi * self._r ** 2

    c.r = 5 and c.area are untouched at every call site in the codebase. This is why "always write getters" is cargo cult here: the refactor it defends against is free.

    What @property is underneath

    No syntax was added to the language for this. property is a class whose instances define __get__, __set__ and __delete__ — a data descriptor, step 2 of the rule.

    r = property(get_r, set_r)   # the decorator form
                             # is the same thing

    Which is the whole reason an assignment cannot dodge it. There is no check to forget, because there is no check: there is a lookup, and the lookup finds the property first.

    When not to. A property that is only return self._x with no validation, no computation and no logging is a getter with extra steps. Delete it and expose the attribute.

    And keep them cheap. c.area looks like an attribute, so callers will write it inside a loop; if it costs a database query, name it fetch_area() so the cost is visible at the call site.

    Cheap is relative, and measurable: a property read is about 3× the cost of a plain attribute read. The measurement slide has the numbers, and the answer is still "use them" for all but the hottest loops.

    13 — the invariant, closed

    The account from slide two, with the hole welded shut

    class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance        # validated, even here

    @property
    def balance(self):
        return self._balance

    @balance.setter
    def balance(self, v):
        if not isinstance(v, (int, float)):
            raise TypeError("balance must be a number")
        if v < 0:
            raise ValueError("balance may not go negative")
        self._balance = v

    def withdraw(self, amount):
        self.balance = self.balance - amount   # raises if under
        return amount

    Now count the ways to reach an invalid balance. a.balance = -1 raises. a.withdraw(10**9) raises. Constructing with a bad value raises, because __init__ assigns through the same setter rather than writing self._balance directly.

    The one remaining door is a._balance = -1 or a.__dict__['_balance'] = -1 — a caller deliberately reaching past the underscore. That is not a leak, it is the line from slide eleven: below the underscore you are on your own, and you did it on purpose.

    The two disciplines that make it hold

    • Assign through the public name in __init__. Writing self._balance = balance there is the single most common way this pattern is broken: the object is born invalid and every later write is guarded.
    • Never read self._balance outside the property. The moment a method reads the private name, the property stops being the only path and starts being one of two.

    What this bought, precisely

    Not "encapsulation" as an abstract virtue. A concrete change in what is possible:

    dict versionclass version
    Places that can break itevery line1, on purpose
    Places that checkthe ones you recallall of them
    Cost of a typoa new key, silentlyAttributeError

    Line three is the quiet win. acct["balnce"] = 500 succeeds; acct.balnce = 500 on a __slots__ class raises immediately, and even without slots it fails the next time something reads balance.

    14 — what inheritance is for

    Inherit to be substitutable, not to save typing

    The test is not "does a square have the same fields as a rectangle". It is: can code written against the base keep its promises when handed the subclass? Here is a contract that a square breaks.

    class Rect:
    def __init__(self, w, h): self.w, self.h = w, h
    def set_w(self, w): self.w = w
    def area(self): return self.w * self.h

class Square(Rect):              # "a square IS-A rectangle"
    def __init__(self, n): super().__init__(n, n)
    def set_w(self, w): self.w = self.h = w   # keeps it square

def contract(r):                       # written against Rect
    r.set_w(5)                         # only the width changes
    return r.area()                    # so: 5 * original height
    $ python3 lsp.pyCPython 3.14.6
    contract(Rect(2, 3))  = 15   (expected 15)
contract(Square(2))   = 25   (expected 15)

    Nothing is wrong with either class in isolation. The error is the class Square(Rect) line: it promised substitutability that the override cannot honour.

    The three questions, in order

    1. Is every one of these really one of those? Not in the dictionary — in the code. Does every method of the base still mean what it said?
    2. Am I inheriting to reuse code? Then you want an attribute, not a base class. A Car is not an Engine; it has one.
    3. Am I inheriting to be polymorphic? In Python you usually do not need to: duck typing dispatches on the method, not the class. Two slides on.

    The smell: a subclass that overrides a method to narrow what it accepts, to raise NotImplementedError, or to ignore an argument the base honours. Each one says "this is not really one of those" out loud.

    The honest fix for the square is that neither is a subclass of the other: both are Shapes with an area(), and a Square has one side. The inheritance was never carrying weight — only the word "is-a" was.

    Slide 33 has the rest of this argument, including the cases where inheritance genuinely is the right answer. First, the machinery: what actually happens when a subclass calls up.

    15 — super()

    super() does not mean "my parent"

    It means: the next class after me in the MRO of type(self). With single inheritance those are the same thing, which is why the misunderstanding survives so long. With two bases they are not, and here is the proof.

    class L1:
    def who(self): return "L1"

class L2(L1):                       # L2's only base is L1
    def who(self): return "L2 -> " + super().who()

class L3(L1):
    def who(self): return "L3 -> " + super().who()

class L4(L2, L3):
    def who(self): return "L4 -> " + super().who()
    $ python3 super.pyCPython 3.14.6
    L4().who() = L4 -> L2 -> L3 -> L1
L2.__bases__ = ['L1']

    Read those two lines together. Inside L2.who, super() resolved to L3 — a class that is not a base of L2, that L2's author may never have heard of, and that did not exist when L2 was written.

    super() is not a reference to a class. It is a position in a list — and which list it is depends on the type of the object the method was called on, not on the class the method was written in.

    Consequences worth knowing

    • A method that calls super() may end up calling a sibling class rather than an ancestor. That is not a bug; it is the mechanism that makes mixins compose.
    • Hard-coding L1.who(self) instead of super().who() works until someone inherits from you twice over — then it silently skips L3 and any state L3 was maintaining.
    • The zero-argument super() only works inside a class body: the compiler passes the class and the instance to it invisibly. Outside one, spell it super(L2, self).

    So everything now depends on what that list is. The next slide computes it — with the actual algorithm, which is stricter and more interesting than "left to right, depth first".

    16 — C3 linearization

    How __mro__ is computed, one merge step at a time

    The MRO is built by merging the MROs of the bases, plus the list of bases itself. At each step, take the first head that appears in no other list's tail — because being in a tail means something still has to come before it.

    Pick a hierarchy and step through. The lists, the choice and the rejections below are computed by a C3 implementation in this page, checked against CPython on 4,000 random hierarchies.

    17 — cooperative inheritance

    A chain of super() calls is only as strong as its weakest link

    Multiple inheritance works when every class in the MRO passes the call along. Here each mixin does its bit and calls up:

    class Base:
    def __init__(self, **kw): print("Base", kw)

class Loud(Base):
    def __init__(self, **kw):
        print("Loud"); super().__init__(**kw)

class Timed(Base):
    def __init__(self, **kw):
        print("Timed"); super().__init__(**kw)

class Job(Loud, Timed):
    def __init__(self, **kw):
        print("Job"); super().__init__(**kw)
    $ python3 coop.pyCPython 3.14.6
    MRO: ['Job', 'Loud', 'Timed', 'Base', 'object']
   Job.__init__
   Loud.__init__
   Timed.__init__
   Base.__init__ {'n': 1}

    Note again: Loud calls super() and reaches Timed, which is not its base. Neither mixin knows the other exists.

    Now one link forgets the call — a single missing line, in a class that looks perfectly reasonable on its own:

    class Rude(Base):
    def __init__(self, **kw):
        print("Rude (no super call)")   # chain ends here

class Job2(Loud, Rude): pass
    $ python3 coop.pyCPython 3.14.6
    MRO: ['Job2', 'Loud', 'Rude', 'Base', 'object']
   Loud.__init__
   Rude.__init__ (no super call)

    Base.__init__ never ran. No exception, no warning — the object is simply half-initialised, and it fails later somewhere that has nothing to do with Rude. This is the characteristic multiple-inheritance bug, and why the pattern needs discipline rather than cleverness.

    The rules that keep a chain working

    • Every class in the chain calls super().__init__(**kw), including the ones that "obviously do not need to".
    • Accept and forward **kwargs, so a class further along can take arguments you have never heard of.
    • There is one class at the bottom that does not call up — and it should be object, or a base you own.
    • If you cannot make every link cooperate — because one is third-party — do not use multiple inheritance here. Use composition.

    18 — mixins

    The one multiple-inheritance pattern that reliably pays

    A mixin is a class that is never instantiated on its own, holds no state of its own if it can help it, and adds one orthogonal capability to whatever it is mixed into.

    class ReprMixin:
    """__repr__ from whatever the instance holds."""
    def __repr__(self):
        fields = ", ".join(f"{k}={v!r}"
                           for k, v in vars(self).items())
        return f"{type(self).__name__}({fields})"

class ComparableMixin:
    """Ordering from one method the class must define."""
    def _key(self): raise NotImplementedError
    def __eq__(self, o): return self._key() == o._key()
    def __lt__(self, o): return self._key() <  o._key()

class Version(ReprMixin, ComparableMixin):
    def __init__(self, major, minor):
        self.major, self.minor = major, minor
    def _key(self):
        return (self.major, self.minor)

    Each mixin is testable alone, has one reason to change, and composes with any class that meets its one requirement. Version reads as a list of the capabilities it wants.

    What makes a mixin good

    • One capability. A "UtilsMixin" is a bag, not a mixin.
    • Named for the capability, not for the thing it is mixed into: ReprMixin, JSONSerialisableMixin, LoginRequiredMixin.
    • A stated requirement. Above, "you must define _key" — and it raises NotImplementedError so a class that forgets fails loudly.
    • No __init__ where possible. If it must have one, it cooperates by the previous slide's rules.

    Where it goes wrong: mixins that talk to each other, mixins that expect a particular order, and stacks deep enough that answering "where does this method come from?" needs Class.__mro__ printed out. Once you are reading the MRO to understand your own code, the mixins have stopped paying for themselves.

    The Python standard library uses this well — socketserver.ThreadingMixIn is one capability, added to any server. Django's class-based views are the cautionary tale in the other direction.

    Six slides from here, the same Version class appears written with composition and with @dataclass(order=True) instead. Both are shorter. Knowing when the mixin is still the right answer is the point.

    19 — duck typing

    The interface is the set of methods, and nothing declares it

    In a nominal type system, len(x) works because x's class was declared to implement an interface. In Python it works because the class defines __len__. There is no declaration, no registration and no inheritance involved.

    class Bag:
    def __init__(self, items): self.items = items
    def __len__(self):   return len(self.items)
    def __iter__(self):  return iter(self.items)
    def __contains__(self, x): return x in self.items

b = Bag([1, 2, 3])
len(b)            # 3
list(b)           # [1, 2, 3]
2 in b            # True
if b: ...         # True — falls back to __len__ != 0

    Bag inherits from nothing. It is usable everywhere a sized, iterable container is expected, because the functions that need those things ask the object, not its ancestry.

    This is the same lookup rule again, one level up: len(x) is type(x).__len__(x). The builtin is a thin wrapper over an attribute lookup on the type — which is why assigning b.__len__ = ... on an instance does nothing.

    What this buys, and what it costs

    consequence
    BuysYour class works with code written before it existed. No base class to import, no interface to implement, no adapter.
    BuysTesting with a stand-in is trivial: anything with the right methods is the right type.
    CostsThe requirement is invisible. "This function needs something with .read()" lives in a docstring, or nowhere.
    CostsFailures are late and can be partial: half the protocol works, then the call that needs __exit__ raises.

    Two slides on, abc and typing.Protocol each buy back one of those costs — in opposite ways, and they are not interchangeable.

    First, though: the set of dunder methods is the language's extension surface. Nearly every piece of syntax is a method call on the type, and implementing the method makes the syntax work on your class.

    20 — the data model

    Every piece of syntax is a method you can define

    A Vector that starts with nothing but two fields. Switch a dunder on and the expressions below start working — each result is dispatched through the same method table Python uses, and each failure is the message CPython actually prints.

    __repr__ first, always. It is what the debugger, the REPL, a list of your objects and every log line will show. __str__ is for the human-facing form, and falls back to __repr__ when absent — so defining only __str__ is the wrong way round.

      Two to try deliberately:

      • Turn on only __len__ and look at bool(v). Truthiness falls back to length, so a vector of length zero becomes falsy — the single most surprising consequence of defining __len__ on something that is not really a container.
      • Turn on __eq__ and watch hash(v) break. That is not this page being clever; it is the language, and it is the next slide.

      21 — the contract

      __eq__ and __hash__ are one decision, not two

      Define __eq__ alone and Python removes the inherited __hash__. Your objects stop being usable as dict keys or set members — deliberately, and at the first attempt rather than later:

      class P:
    def __init__(self, x): self.x = x
    def __eq__(self, o): return isinstance(o, P) and self.x==o.x
      $ python3 eq.pyCPython 3.14.6
      P.__hash__ is None
hash(P(1)) -> TypeError: unhashable type: 'P'

      The rule it is protecting: objects that compare equal must hash equal. Default hashing is by identity, so two equal-but-distinct objects would land in different buckets and a dict would hold both.

      So write them together, from the same fields:

          def __hash__(self):
        return hash((self.x,))   # same fields as __eq__

      And now the harder half. A correct __hash__ is still a bug if the fields it reads can change:

      k = Key(1)
d = {k: "found"}
k.v = 2            # mutate the key, after insertion
print(d.get(k))
print(len(d), list(d.values()))
      $ python3 mutablekey.pyCPython 3.14.6
      d.get(k)        -> None
len(d) = 1      still inside: ['found']
d.get(Key(2))   -> None

      The entry is still in the dict. The key object is still the same object. And neither the original key nor an equal fresh one can find it, because it was filed under the old hash. No exception is raised — the value is simply unreachable. This is the quietest data-loss bug in the language.

      The discipline

      • Hash only immutable fields — ideally a frozen object.
      • @dataclass(frozen=True) generates both methods and blocks the mutation, in one line.
      • If the object must be mutable, leave it unhashable. Unusable as a key beats silently lost.

      22 — naming the interface

      ABCs and Protocols solve the same problem from opposite ends

      abc.ABC — nominal, enforced at runtime

      from abc import ABC, abstractmethod

    @abstractmethod
    def get(self, k): ...
    @abstractmethod
    def put(self, k, v): ...
      $ python3 abc_demo.pyCPython 3.14.6
      Store() -> TypeError: Can't instantiate abstract class

      A subclass that forgets a method fails the first time anyone constructs it, with the method named. You inherit from it, so the relationship is declared — and a class you do not own cannot join without Store.register(...).

      typing.Protocol — structural, checked by the type checker

      from typing import Protocol, runtime_checkable

@runtime_checkable

    def __len__(self) -> int: ...

class Bag:                     # inherits from nothing
    def __len__(self): return 3
      $ python3 proto_demo.pyCPython 3.14.6
      isinstance(Bag(), Sized) = True

      Duck typing with a name on it. The requirement becomes writable in a signature — def total(x: Sized) -> int — and mypy checks it, without anyone inheriting anything. runtime_checkable only checks that the methods exist, not their signatures.

      Choose ABC when you own the hierarchy and want implementations to fail loudly at construction: a plugin base class, a framework extension point, something with shared concrete helpers alongside the abstract methods.

      Choose Protocol when you are describing what a parameter needs — especially for types you do not own. "Anything with .read()" is a Protocol; making every caller inherit from your Readable base is not an option you have.

      23 — composition

      Has-a survives changes that is-a does not

      The inheritance version reads well right up to the day the requirements move:

      class Job(LoggingMixin, RetryMixin, TimingMixin, Base):
    def run(self): ...
      • Where does run's logging happen? Somewhere in the MRO.
      • Can one job retry but not log? Only by making a new class.
      • Can retry behaviour be swapped at runtime? No — the MRO is fixed when the class is created.
      • Can you test the retry logic alone? Only through a class that mixes it in.

      The composed version answers all four, and the answer is the same sentence each time: they are objects, so they are values you can pass, swap and test.

      class Job:
    def __init__(self, task, retry=None, logger=None):
        self.task   = task
        self.retry  = retry or NoRetry()
        self.logger = logger or NullLogger()

    def run(self):
        self.logger.info("starting %s", self.task)
        return self.retry.call(self.task)

      The trade honestly stated

      inheritancecomposition
      Wiringnone — implicitexplicit, and more typing
      Swappable at runtimenoyes
      Testable aloneawkwardtrivially
      Where does X happen?read the MROread __init__
      Two of the same kindimpossibletwo attributes

      "More typing" is a real cost, not a rhetorical one. For three capabilities, the mixin version is shorter and perfectly clear. The composed version pays off at the point where behaviour has to vary per instance rather than per class.

      Where inheritance still wins: a framework contract you do not control (Exception, Enum, a Django Model); a genuine specialisation where every base method still means what it said; and sharing a small, stable set of concrete helpers with an ABC. "Favour composition" is advice, not a prohibition.

      And if the delegation is only ever forwarding — def info(self, *a): return self.logger.info(*a) for nine methods — that is composition being used where a plain attribute would do. Let callers reach the collaborator.

      24 — dataclasses

      The boilerplate has a generator, and it is stricter than you are

      Most classes are a handful of fields with an __init__ that assigns them, a __repr__ for debugging, and an __eq__ that compares them. All three are derivable from the field list, so Python derives them:

      from dataclasses import dataclass, field

@dataclass(frozen=True, slots=True, order=True)

    minor: int = 0
    tags: list[str] = field(default_factory=list)

      The generated __eq__ compares the tuple of fields, so value semantics arrive for free — and with frozen=True a matching __hash__ arrives with them, which is the contract from slide 22 satisfied by construction.

      The four arguments worth knowing

      argumentwhat it does
      frozen=TrueAssignment raises. Generates __hash__. Makes the object usable as a dict key and safe to share.
      slots=TrueAdds __slots__ from the fields. Smaller instances, no stray attributes, no __dict__.
      order=TrueGenerates the four comparisons from the field tuple — the ComparableMixin of slide 19, in one word.
      kw_only=TrueCallers must name the fields. Kills the "which of these five ints is which" class of bug.

      And the mutable default is refused outright. Writing tags: list[str] = [] raises ValueError: mutable default <class 'list'> for field tags is not allowed: use default_factory — at class-creation time, before a single instance exists. Slide 7's bug, promoted from "found in production" to "cannot be written". field(default_factory=list) is the spelling that means "a new one per instance".

      Reach for a plain class when there is real behaviour and few fields; a dataclass when it is mostly fields; NamedTuple when it must be a tuple; and a plain dict when the keys are genuinely dynamic and there is no invariant to keep.

      25 — descriptors

      The protocol that everything else on this deck was already using

      A descriptor is any object that defines __get__, and optionally __set__ or __delete__. Put one in a class, and the lookup rule calls it instead of returning it. You have seen this four times already without the name:

      $ python3 descriptors.pyCPython 3.14.6
       meth: function     __get__=True  __set__=False
 prop: property     __get__=True  __set__=True
   cm: classmethod  __get__=True  __set__=False
   sm: staticmethod __get__=True  __set__=False

      Methods, properties, classmethod and staticmethod are not four language features. They are four descriptors in the standard library, and you can write a fifth.

      Here is the one worth writing: a validated field, defined once and used on as many attributes as you like — which is the thing @property cannot do without repeating itself per field.

      class Positive:
    def __set_name__(self, owner, name):
        self.name = "_" + name          # told its own name

    def __get__(self, obj, owner=None):
        if obj is None: return self     # accessed on the class
        return getattr(obj, self.name)

    def __set__(self, obj, value):      # __set__ => data descriptor
        if value <= 0:
            raise ValueError(f"{self.name[1:]} must be positive")
        setattr(obj, self.name, value)

class Rectangle:
    width  = Positive()
    height = Positive()

    def __init__(self, width, height):
        self.width, self.height = width, height

      Two properties became two lines. Ten would still be ten lines, and the validation exists exactly once. __set_name__ is what makes it reusable: the class tells the descriptor which attribute it was assigned to, so the descriptor does not have to be told its own name twice.

      The one trap: state belongs on the instance, not the descriptor. A descriptor is created once, at class-creation time, and shared by every instance — self.value = value inside __set__ would make every rectangle the same width. Store under a per-instance key, as above.

      26 — __slots__

      Trading the instance dictionary for descriptors

      Declaring __slots__ tells Python not to give instances a __dict__. The attributes become data descriptors on the class, each one pointing at a fixed offset in the object — step 2 of the lookup rule, one more time.

      class Point:
    __slots__ = ('x', 'y')
    def __init__(self, x, y):
        self.x, self.y = x, y
      $ python3 slots.pyCPython 3.14.6
      p.z = 1
AttributeError: 'S' object has no attribute 'y'
and no __dict__ for setting new attributes

      The first message is the real reason to use slots in a class that is not performance-critical: a typo becomes an error instead of a new attribute nobody reads. The last line is the usual disappointment — one subclass without __slots__ hands the dict back, and every saving with it.

      What it saves, measured rather than quoted

      $ python3 slotsize.pyCPython 3.14.6, arm64
      sys.getsizeof:
  plain object 48 B + __dict__ 296 B = 344 B
  slotted object 48 B, no dict      =  48 B

      Those two blocks disagree, and the second one is right. sys.getsizeof on the dict reports a full standalone dict; instances of the same class actually share their key table (PEP 412), so the real per-instance cost is a fraction of what the naive measurement implies. The widely repeated "slots save you 80%" is an artefact of measuring it the easy way.

      Use slots for classes you create in millions, and for value objects where a stray attribute is a bug. @dataclass(slots=True) is the least painful spelling. Skip them otherwise: they break multiple inheritance from two slotted classes, weak references unless you add __weakref__, and every library that assumes vars(obj) works.

      27 — construction

      __new__ makes the object. __init__ only fills it in.

      Calling C(...) runs two methods. __new__ is a static method that returns the new object; __init__ is handed that object and returns nothing.

      obj = C.__new__(C, *args)        # allocate
if isinstance(obj, C):
    obj.__init__(*args)          # initialise
return obj

      For ninety-nine classes in a hundred, __init__ is all you need. __new__ earns its place when the object must be fully formed before anyone sees it — which is exactly the case for immutable types:

      class Odd(int):
    def __new__(cls, v):
        return super().__new__(cls, v * 2)
      $ python3 new.pyCPython 3.14.6
      Odd(5)        -> 10
type(Odd(5))  -> Odd

      An int's value is fixed at allocation. There is no self.value = ... to write in __init__, so subclassing int, str, tuple or frozenset means __new__ or nothing.

      The three legitimate uses

      • Subclassing an immutable builtin, as above.
      • Returning an existing instance — caching, interning, a singleton. Note the consequence: if __new__ returns an object of the right type, __init__ runs again on the cached instance. Guard it, or do the work in __new__.
      • Returning a different class entirely — a factory hiding behind a constructor. Use sparingly: Shape(...) quietly handing back a Circle is a surprise in a traceback.

      Not a legitimate use: validating arguments. That is __init__'s job, or a property's, and doing it in __new__ means doing it before the object exists — with worse error messages and no self to put anything on.

      A classmethod is usually the better factory anyway. Date.from_iso("2026-09-20") says what it does at the call site; a __new__ that branches on argument types does not.

      28 — the two modern hooks

      __init_subclass__ and __set_name__

      Most of what metaclasses were used for was one of two things: reacting when someone subclasses you, and telling a class attribute what it was named. Both now have a plain hook, and neither needs a metaclass.

      class Tracked:
    def __set_name__(self, owner, name):
        print(f"__set_name__(owner={owner.__name__}, name={name!r})")

class Parent:
    def __init_subclass__(cls, **kw):
        super().__init_subclass__(**kw)
        print(f"__init_subclass__(cls={cls.__name__})")

class Child(Parent):
    field = Tracked()
    other = Tracked()
      $ python3 hooks.pyCPython 3.14.6
      __set_name__(owner=Child, name='field')
__set_name__(owner=Child, name='other')
__init_subclass__(cls=Child)

      Note the order, and that no instance was created: the descriptors are named first, in definition order, then the parent is told a subclass exists — all while class Child is still executing.

      What they are for

      • Plugin registration. A base class that keeps a registry of every subclass ever defined — four lines, no metaclass: 
        class Plugin:
    registry = {}
    def __init_subclass__(cls, key, **kw):
        super().__init_subclass__(**kw)
        cls.registry[key] = cls

class Csv(Plugin, key="csv"): ...
      • Enforcing a contract at definition time. Check in __init_subclass__ that the subclass defined what it must, and raise there — the error arrives when the file is imported, not when something is finally constructed in production.
      • Self-naming descriptors, as on slide 25.

      Reach for these before a metaclass, every time. They are ordinary methods, they compose through super(), they do not change the type of your class, and nobody inheriting from you has to care that they exist.

      A class is an instance of something, and you can change what

        30 — measurement

        What the lookup rule actually costs

        The structural cost first, and this page can compute it: how many namespaces does a lookup probe before it answers? Every bar is produced by running the six-step rule in this page against a generated hierarchy.

        A hit on the class you started from is one probe whatever the depth. A name that lives on the instance is the expensive case, because it is found after the whole MRO has been walked and missed — the rule looks at the type first, always.

        Now the wall clock, from CPython rather than from this page — a browser cannot time an interpreter it is not running.

        $ python3 -m timeit …CPython 3.14.6, arm64, 2M reps
        instance __dict__     8.0 ns
__slots__             7.6 ns
@property            25.6 ns
__getattr__ miss     47.2 ns

        A property is about three times a plain read, and still eight nanoseconds of actual work. Use them; just do not put one in the innermost loop of a numeric kernel.

        And the measurement that contradicts the obvious prediction. If a deep MRO means more probes, deep hierarchies should be slower to read from:

        $ python3 -m timeit …CPython 3.14.6, arm64
        depth  0 (MRO len  2):   7.8 ns
depth  5 (MRO len  7):   7.8 ns
depth 20 (MRO len 22):   7.8 ns
depth 50 (MRO len 52):   7.8 ns

        Flat. CPython keeps a type attribute cache: the result of walking an MRO for a name is memoised per type, and invalidated when any class in that MRO is modified. The walk on the left is what happens on a cold lookup and after an invalidation; the steady state is a cache hit regardless of depth.

        So "flatten your hierarchy for speed" is folklore — at 50 levels deep it costs nothing measurable. Flatten it because you cannot find the method, which is a real cost and does not show up in a benchmark.

        Sixty lines that use every rule in this deck

        32 — the validator

        Write these three tests before the class is finished, not after

        An object model fails the way a tree does: it answers most questions correctly for a long time, and the one broken rule is invisible until something far away misbehaves. Three property checks catch nearly all of it.

        def check_eq_hash(make, n=2000):
    """Equal objects must hash equal. Collisions between
       unequal ones are legal and must not fail."""
    for _ in range(n):
        a, b = make(), make()
        if a == b:
            assert hash(a) == hash(b), (a, b)

        And the honest summary of the last thirty slides: reach for a class when there is an invariant to protect, or a behaviour that varies by kind. If there is neither, you are typing for nothing.

        Exercises — predict first, then run

        1. One character apart. class A: x = []. Predict A.x, b.x and whether 'x' in vars(a), after a.x += [1]. Then after a.x = a.x + [1] on a fresh class. One of them changes the class attribute and creates an instance one. Which, and why?
        2. The MRO. Write down the MRO of class D(B, C) where B(A) and C(A), before running anything. Now do the same for class M(K1, K2, K3) from slide 17. Check both with __mro__.
        3. Break it deliberately. Find the shortest program that puts a value into a dict and then makes it unreachable, without deleting it and without an exception. Fewer than ten lines is achievable.
        4. The boundary. Add __slots__ = ('x',) to a class that already has x = 1 in its body. Predict what happens and when — at import, at construction, or at first access?
        5. The chain. Take slide 18's four-class cooperative chain and delete one super().__init__(). Predict which __init__ bodies still run before you run it. Then move the deletion one class up and predict again.
        6. Both descriptors. Write one descriptor with __get__ only and one with __get__ and __set__. Put each on a class, smuggle a value into the instance's __dict__, and predict which read returns which value. Slide 10 has the answer; do not look first.

        Where to go from here: read dataclasses.py in the standard library — it is a class decorator that builds methods from a field list, and after this deck you can follow all of it. Then enum.py, which is the metaclass case done properly.
