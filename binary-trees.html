Binary trees: the words and the arithmetic

Same fifteen keys. Same fifteen nodes. Same struct definition, byte for byte. Everything else about these two differs — and every difference has a name.

Memory, recursion depth, cache misses, whether the array trick is even legal: all of it is a function of shape, and the vocabulary is how we name shapes. This deck derives every number rather than listing it. Arrow keys, or the buttons below, to move through the deck.

How this actually bites

You are sizing the backing array for a binary heap of n = 1000 elements. A heap is a complete binary tree, and its height is 9.

  • "a tree of height h holds up to 2h nodes" → malloc(512 * sizeof(int))
  • "a tree of height h holds up to 2h+1 − 1 nodes" → malloc(1023 * sizeof(int))

One of these is half the room you need. Both sentences are printed, verbatim, in books currently in use. The only thing separating them is which convention the author was counting in, and neither author said.

This is not pedantry about vocabulary. It is a heap corruption bug whose root cause is a footnote.

04 — the patches that do not hold

Things that do not fix this

"Pick a convention and stick to it."

Fine for the code you write. Useless for the code you read, the paper you are implementing from, and the Stack Overflow answer you are about to paste. The convention is a property of the sentence, not of you.

"Just always use a balanced tree."

A binary heap is not balanced in the AVL sense — it is complete, which is a different and stronger shape constraint, and it is exactly what makes the array representation legal. Erase the distinction and you lose the reason heaps work.

"Memorise the formula table."

There are about fifteen formulas in circulation and they all look the same at three in the morning. 2h, 2h+1−1, 2h−1, (n+1)/2, (n−1)/2, ⌊log₂ n⌋, ⌈log₂(n+1)⌉−1. Misremember one sign and the bug is silent.

"Just measure it at runtime."

You cannot allocate before you count, and you cannot count before you allocate. The bound is a design-time quantity. That is what the arithmetic is for.

Every one of those attacks the symptom. The problem is that the vocabulary is being treated as a list to memorise instead of as a set of consequences of two very small facts.

05 — stop memorising

Three facts. Everything else is arithmetic.

If you can rebuild the formulas in ten seconds you never have to trust your memory of where the −1 went.

  1. Branching. Level 0 holds one node, the root. Every node has at most two children, so level ℓ+1 holds at most twice what level ℓ holds. By induction, level ℓ holds at most 2ℓ nodes.
  2. The geometric sum. 1 + 2 + 4 + … + 2h = 2h+1 − 1. One-line proof: call the sum S; then 2S − S = 2h+1 − 1.
  3. The handshake. Every node except the root is exactly one node's child, so n nodes span n − 1 edges. Every node offers two child slots, so there are 2n slots, of which n−1 are filled and n + 1 are null.

06 — the handshake, drawn

Count the edges once and two theorems fall out

□ = a null child slot, an external node

Theorem 1 — null links

2n child slots exist. n−1 of them point at a real node. So nulls = 2n − (n−1) = n + 1, for every binary tree of every shape, with no exceptions. Press the buttons; the count never moves off n+1.

Theorem 2 — leaves and forks

Split the nodes by how many children they have: n₀ leaves, n₁ with one child, n₂ with two. Then n = n₀+n₁+n₂, and counting edges from above gives n−1 = n₁ + 2n₂. Subtract:

n₀ = n₂ + 1

A binary tree always has exactly one more leaf than it has two-child nodes. Any shape, any size. This single line is where "a full tree has an odd number of nodes" and "Huffman on k symbols builds 2k−1 nodes" both come from.

Those n+1 nulls are not an accounting curiosity. In a three-word node they are roughly a third of the entire structure sitting there holding zero, which is the whole reason threaded binary trees exist. Slide 17 puts a number on it.

07 — every noun on one diagram

The nouns that have no highlight

  • edge — a parent-to-child link. Also called a branch. n nodes, n−1 edges.
  • path — a sequence of nodes each the child of the last. Its length is measured in edges, so a path of four nodes has length 3.
  • size — node count, of the tree or of any subtree.
  • degree of a node — its number of children, 0, 1 or 2. Degree of the tree — the largest of those, which is why this is a binary tree.
  • forest — a set of disjoint trees. Delete the root of a tree and you are holding a forest of two.
  • ordered — see the note below.

A binary tree is ordered: left and right are different places. A node with one left child is not the same tree as a node with one right child. That sounds obvious and it is load-bearing — it is why slide 18 counts twice as many shapes as you would otherwise expect, and why preorder + postorder cannot always rebuild a tree.

08 — depth, height, level

Depth counts downward. Height counts upward. They are not the same number.

The conventions this deck uses

  • depth(x) = number of edges from the root down to x. depth(root) = 0.
  • height(x) = number of edges on the longest path from x down to a leaf. height(leaf) = 0.
  • height(empty) = −1.
  • height of the tree = height of its root = the largest depth in it.
  • level = depth. (Some books make the root level 1. If a formula surprises you, check this first.)

Why −1 for the empty tree is the right answer and not a quirk: it makes

height(x) = 1 + max(height(x.left), height(x.right))

correct with no special case for leaves and no special case for one-child nodes. Every other convention needs at least one if. Pick the definition that deletes code.

The identity nobody states

For every node x in a tree of height H: depth(x) + height(x) ≤ H, with equality exactly when x sits on a longest root-to-leaf path. Press depth + height and read it off — the nodes showing H are the critical path, and they are the ones a rotation has to touch.

09 — where the nodes actually live

The bottom level outweighs the entire tree above it

Facts 1 and 2, read as a table. The consequence is the single most useful intuition about tree costs.

The deepest level of a perfect tree holds one more node than every other level put together. Half the tree is leaves. Three quarters of it is in the bottom two levels.

What that buys you

  • Average depth is not half the height. Sum the depths of a perfect tree of height h and you get (h−1)·2h+1 + 2, which over 2h+1−1 nodes is about h − 1. A random node is essentially at the bottom.
  • Heap construction is O(n), not O(n log n). Sift-down costs are proportional to height-above-the-bottom, and almost every node has none. The expensive nodes are the rare ones.
  • Recursion on a tree spends most of its time in leaf frames. If you are optimising a tree walk, optimise the leaf case first — that is where half your calls are.
  • Caching the top of the tree is cheap and effective. Ten levels of a perfect tree is 1 023 nodes: 24 KB, comfortably resident, and it covers the first ten steps of every single search.

Every row above is fact 1 (2ℓ per level) divided by fact 2 (2ℓ+1−1 cumulative). Nothing new was introduced.

10 — full, proper, strict

Full: every node has zero children or two. Never one.

Also printed as proper, strict and strictly binary. Some older books use "full" to mean what this deck calls perfect — check before you trust a formula.

Both of those are full. They have the same node count and the same leaf count, and their heights differ. Full says nothing whatsoever about height — that is the most common wrong inference about this word.

A full binary tree can still be a disaster. Attach a leaf to every node of a chain and you have a perfectly legitimate full tree of height (n−1)/2. Fullness is a statement about forks, not about balance.

Derived, not memorised

Start from theorem 2 on slide 6: n₀ = n₂ + 1 for any binary tree. A full tree is exactly the case n₁ = 0. Substitute:

nodesn = 2n₂ + 1 — always odd
leavesn₀ = (n + 1) / 2
internaln₂ = (n − 1) / 2
from L leavesn = 2L − 1
height range⌈log₂(n+1)⌉−1 … (n−1)/2

There is no full binary tree with 2, 4, 6, 8 or any other even number of nodes. If your Huffman builder ever produces one, it has a bug and you now have a one-line assertion that catches it.

Where fullness is the point

Huffman trees, expression trees for binary operators, segment trees, and every "combine two things into one" structure. A one-child node in any of those means an operator with a missing operand. n = 2k − 1 is how you size the node array for k symbols before you build anything.

11 — complete

Complete: every level full except the last, and the last packed to the left

The clause people drop is the second one, and it is the entire reason the word exists.

each node is labelled with its array index, not its key

A binary tree is complete exactly when its array indices are 0, 1, 2, …, n−1 with no gaps. That is not a consequence of the definition — it is the definition, restated. Everything else about completeness follows from it.

The indexing, 0-based

left child of i2i + 1
right child of i2i + 2
parent of i⌊(i − 1) / 2⌋

1-based is nicer: left = 2i, right = 2i+1, parent = i >> 1. Slide 21 shows the trick that only works in 1-based.

Everything a complete tree tells you

height⌊log₂ n⌋ — the minimum possible
internal nodes⌊n / 2⌋, indices 0 … ⌊n/2⌋−1
leaves⌈n / 2⌉
nodes on the last leveln − (2h − 1)

Derivation of the leaf count, since it looks arbitrary: node i is internal iff its left child exists, iff 2i+1 ≤ n−1, iff i < n/2. Count them. That is all.

Corollary worth keeping: a complete tree with an odd number of nodes is also full, because the only node that could have one child is the last internal one, and it only does when n is even.

12 — perfect

Perfect: every level is completely full, leaves all at the same depth

Substituting fact 2 into fact 1: a tree that holds the maximum at every level holds 1 + 2 + 4 + … + 2h nodes, which is 2h+1 − 1. Every other formula on this slide is that one rearranged.

A tree of height h is perfect if and only if it has 2h+1 − 1 nodes. It cannot be anything else, because that is the maximum and the maximum is only reachable by filling every level. This makes is_perfect a two-line function with no traversal of its own.

The perfect-tree identities

nodesn = 2h+1 − 1
heighth = log₂(n + 1) − 1
leavesL = 2h = (n + 1) / 2
internalI = 2h − 1 = (n − 1) / 2
nodes above the leavesL − 1
null linksn + 1 = 2h+1
sum of all depths(h − 1)·2h+1 + 2
legal sizes1, 3, 7, 15, 31, 63, 127, …

Why you almost never have one

Perfect trees exist only at n = 2k − 1. For every other n — which is all but a vanishing sliver of them — the shape is unreachable. That is why real structures aim at complete (achievable at every n) or at height-balanced (maintainable under updates), and treat perfection as a bound to measure against rather than a goal.

Where it does appear: segment trees and Merkle trees pad n up to the next power of two precisely to buy perfection, and eat the wasted leaves as the price.

Perfect is not a conjunction of the other two. It is its own single check, and the cheapest one in the taxonomy:

perfect ⇔ n == (1 << (h+1)) − 1

Count the nodes, measure the height, compare. No second traversal, no recursion on shape.

15 — the rest of the shape words

Degenerate, skewed, and the four different things "balanced" means

Degenerate / pathological

Every node has at most one child. Equivalently n₂ = 0, equivalently exactly one leaf, equivalently a linked list wearing a tree's struct. Height = n−1, the worst possible.

Left-skewed / right-skewed are the degenerate trees where every child is on the same side. They are not equally bad: in 0-based array indexing a right chain of n nodes needs 2n−1 slots and a left chain needs 2n−1. Twice the waste, same tree flipped.

They are genuinely different sets, and the implications run one way only:

  • complete ⇒ minimum height, and height-balanced
  • minimum height ⇏ height-balanced — hang a perfect 7-node subtree off a root whose other side is a single leaf: height 3 = ⌊log₂ 9⌋, and the root is off by two
  • height-balanced ⇏ minimum height — a Fibonacci tree is AVL-legal at height 1.44 log n

When someone says a tree is balanced, the useful question is not "how balanced" but "balanced in which sense, and what does that buy me".

16 — the height bounds

⌊log₂ n⌋ ≤ h ≤ n − 1, and both ends are reachable

Lower bound. A tree of height h holds at most 2h+1−1 nodes (facts 1 and 2). So n ≤ 2h+1−1, which rearranges to h ≥ log₂(n+1) − 1. Since h is an integer, h ≥ ⌈log₂(n+1)⌉ − 1, and that expression equals ⌊log₂ n⌋ for every n ≥ 1. Achieved by any complete tree.

Upper bound. A tree of height h holds at least h+1 nodes, one per level. So n ≥ h+1, giving h ≤ n − 1. Achieved by any degenerate chain.

The other direction. Fixing h instead, the node count ranges over h+1 … 2h+1−1. A height-20 binary tree holds anywhere from 21 nodes to just over two million.

The middle case, measured rather than quoted

Insert n keys in random order into a plain BST and the height is not log₂ n. The known result is asymptotic:

E[h] = 4.311 ln n − 1.953 ln ln n + O(1)

whose leading term alone is 2.99 · log₂ n — the source of "a random BST is about three times as deep as it needs to be". Here is what this page measures when it actually builds them:

17 — the memory bill

A third of your tree is holding nothing

Theorem 1 said n+1 nulls. Here is that theorem denominated in bytes.

layoutbytes / nodetotaldead weight

Assumes LP64: int 4 bytes, pointer 8, struct padded to an 8-byte boundary. struct Node { int key; Node *left, *right; } is 24 bytes, not 20 — the padding after key is free real estate you can spend on a colour bit, a height byte or a subtree size.

Of the 2n pointer slots, n+1 are null. On a 24-byte node that is 8 bytes × (n+1) of pure nothing — about a third of the entire allocation, sitting in cache lines you paid to fetch.

Three ways to stop paying it

  • Threaded binary tree. Point each null left link at the in-order predecessor and each null right link at the in-order successor, and spend two bits tagging which links are real. In-order traversal then runs with no stack, no recursion and O(1) extra space. The n+1 nulls are exactly the n+1 threads you need — the fit is not a coincidence.
  • Array embedding. A complete tree needs no child pointers at all: 4 bytes a node instead of 24. Six times smaller, and the children are computed with a shift. Legal only for complete trees — see slide 21 for what happens otherwise.
  • Widen the node. If you are going to eat a cache miss per level, carry more than one key per miss. That is the entire B-tree argument, and it is why a database index is not a binary tree.

The miss that dominates

A 64-byte cache line fits 2.67 of these nodes, but malloc scatters them, so assume one useful node per line. A root-to-leaf walk in a balanced million-node tree is then about 20 cache misses. At roughly 80 ns each that is 1.6 µs — and the comparisons inside it are free by comparison. Shape determines how many misses. Nothing else you do to a binary tree matters as much.

18 — how many shapes are there

Catalan numbers, and the two bits per node they imply

How many distinct binary trees have exactly n nodes? Pick the root. If i nodes go left, the other n−1−i go right, and the two sides are independent. Sum over i:

C₀ = 1,   Cn = Σi=0..n−1 Ci · Cn−1−i

That recurrence has the closed form Cn = (1 / (n+1)) · C(2n, n), the Catalan numbers, and it grows like 4n / (n3/2√π).

nCn — distinct shapeslog₂ Cnbits / node

Computed live from the recurrence above, in exact big-integer arithmetic.

log₂ Cn → 2n. A binary tree's shape carries about two bits of information per node, no matter how big it gets. That is a hard floor on any encoding of tree structure — and succinct representations (balanced parentheses, LOUDS) actually reach it, storing a million-node shape in 2 million bits where the pointer version wanted 128 million.

Where those two bits come from

Walk the tree in preorder and write ( on the way into a node and ) on the way out. Every binary tree maps to exactly one balanced parenthesis string of length 2n, and every such string maps back. Two symbols, 2n positions, one bit each. The bijection is the encoding.

Two corollaries worth having

  • The number of distinct BSTs on n distinct keys is also Cn. Once the shape is fixed, the key assignment is forced — in-order must come out sorted. Shape and BST are the same counting problem.
  • A uniformly random shape is not a random BST. Draw a shape uniformly from the Cn possibilities and the expected height is Θ(√n) — about 2√(πn), which at n = 106 is around 3 500. Insert a random permutation and it is around 60. Same object, two completely different distributions, and papers are sloppy about which one they mean.

19 — path length

Internal and external path length, and why a failed search costs the same

□ = external node  ·  badge = depth

The definitions

  • IPL — sum of the depths of all n real nodes. Average node depth is IPL/n, and a successful search costs IPL/n + 1 comparisons on average.
  • EPL — sum of the depths of all n+1 external (null) positions. An unsuccessful search costs EPL/(n+1) comparisons on average.

EPL = IPL + 2n, for every binary tree.

Induction on insertion. Adding a node at depth d turns one external node at depth d into an internal one and creates two externals at depth d+1. So IPL rises by d, and EPL rises by 2(d+1) − d = d + 2. The gap grows by exactly 2 per node, from 0 at n = 0.

What it tells you

Average unsuccessful cost = (IPL + 2n)/(n+1), average successful cost = IPL/n + 1. Those differ by less than one comparison for any interesting n. Looking for something that is not there costs the same as finding something that is. A "fast negative lookup" path in a plain BST is not a thing — that is what Bloom filters are for.

The minimum possible IPL over all n-node trees is Σk=1..n ⌊log₂ k⌋, achieved by the complete tree. A random BST has the exact expected IPL 2(n+1)Hn − 4n, which runs about 37–38% above that minimum and stays there as n grows.

Careful with the usual shorthand: that expression's leading term is 2n ln n, and at n = 1000 the leading term alone overstates the truth by 26%. It is also quicksort's expected comparison count — not a coincidence, because building a BST from a permutation performs exactly the comparisons quicksort performs on it. The BST is quicksort's recursion tree, made out of pointers.

21 — the array embedding

Drop the pointers — but only if the tree is complete

Completeness is not an aesthetic preference. It is the precise condition under which the index set is {0, 1, …, n−1} and the array has no holes. Break it anywhere and the slot count stops tracking n and starts tracking 2h.

The 1-based trick

With the root at index 1, left = 2i, right = 2i+1, parent = i >> 1. Then:

  • the level of node i is ⌊log₂ i⌋, which is its bit length minus one
  • the binary digits of i, after the leading 1, spell the path from the root: 0 means go left, 1 means go right. Node 13 is 1101, so root → right → left → right.

That is why heaps, segment trees and Fenwick trees are written 1-based. The index is not a location; it is a route.

Where it wins and where it burns

  • Wins: binary heaps, segment trees, iterative heapsort, Fenwick trees, implicit static search structures. No allocation, no pointer chasing, four bytes a node.
  • Burns: anything that stores a BST this way. A BST's shape is dictated by insertion order, which you do not control, so the slot count is 2h+1−1 and h can be n−1. Press right chain 6 and scale that in your head to n = 40.
  • The hidden cost even when it works: level-order layout means a root-to-leaf path touches h addresses that double in distance each step. Every one is a different page. The van Emde Boas layout fixes exactly this, and it is the reason B-trees exist.

22 — traversal vocabulary

Four orders, one walk, and what any two of them pin down

They are one traversal, not four

The recursive walk passes each node three times: on the way down, between its two children, and on the way back up. That is the Euler tour. Preorder, inorder and postorder are just which of the three visits you choose to record. Level-order is the odd one out — it is the same algorithm with a queue instead of a stack.

What each one is for

preordercopy, serialise, prefix/Polish notation
inordersorted output — only meaningful for a BST
postorderfree the tree, evaluate an expression, compute sizes and heights
level-orderanything organised by depth: completeness checks, pretty-printing, BFS

Postorder is the one to reach for when a node's answer depends on its children's answers — which is every "measure the tree" function on the next slide.

Reconstruction. With distinct keys: inorder + preorder determines the tree. So does inorder + postorder, and inorder + level-order. Preorder + postorder does not — unless the tree is full.

The counterexample fits on one line. A root A with a single left child B, and a root A with a single right child B, both give preorder A B and postorder B A. Inorder is what distinguishes them: B A against A B. One-child nodes are exactly the ambiguity, which is why fullness removes it.

Preorder alone is enough if you also emit a marker for every null child — that is n+1 markers, theorem 1 again, and it is how every "serialise a binary tree" answer works.

Every row is the same handshake. n nodes span n−1 edges; each node offers m slots; subtract. The binary results are not special cases you learned separately — they are the right-hand column.

m is the base of the logarithm, and the base is the whole game. Three levels of a binary tree reach 15 keys. Three levels of a 100-ary tree reach 1 010 101. Same number of pointer dereferences, five orders of magnitude more data.

Why binary is still enough

Any ordered tree of any arity converts to a binary tree with no loss, by the left-child right-sibling transform: a node's left becomes its first child and its right becomes its next sibling. n nodes in, n nodes out, structure preserved and reversible.

So the binary vocabulary is not a restriction. It is the normal form, which is why every general-tree problem eventually shows up as a binary tree problem.

Where the arity actually gets chosen

Not by the algorithm — by the hardware. Pick m so a node fills one unit of transfer: a cache line, a disk block, a database page. Everything in the B-tree deck is this table plus that one sentence.

24 — C: the decisions before the code

Four choices, and what each one costs

#include <stdio.h>
#include <stdlib.h>
#include <assert.h>

typedef struct Node {
    int          key;
    struct Node *left, *right;
} Node;          /* 24 bytes on LP64:
                    4 key + 4 padding + 8 + 8 */

static Node *node_new(int key)
{
    Node *n = malloc(sizeof *n);
    if (!n) { perror("malloc"); exit(1); }
    n->key  = key;
    n->left = n->right = NULL;
    return n;
}

/* postorder: you cannot free a node and
   then read its children out of it */
static void tree_free(Node *t)
{
    if (!t) return;
    tree_free(t->left);
    tree_free(t->right);
    free(t);
}

1. NULL or a shared sentinel

NULL is free in space and costs a branch at every access. A single shared sentinel node lets you read x->left->colour without checking, which is what makes red-black fixups short. For measuring and classifying, NULL — the sentinel only pays off where a hot loop would otherwise branch.

2. Parent pointer or not

Adds 8 bytes to every node, a third more memory, and one more field to get wrong in every rotation. It buys iterative traversal and O(1) successor-from-a-node. Nothing in this deck needs it; recursion carries the parent on the stack for free.

3. That 4-byte hole after key

The padding is already allocated. A colour bit, a height byte, a balance factor and a 32-bit subtree size all fit in it at zero marginal cost. If you are going to annotate nodes, annotate them there.

4. Recursion depth is the height, not the size. tree_height on a degenerate million-node tree wants a million stack frames — tens of megabytes against a default 8 MB stack. The function that crashes is not your insert; it is the innocent-looking measurement you wrote to check on it. If shape is not under your control, write the iterative version with an explicit stack.

25 — C: measuring a tree

Every quantity in the deck, in twelve lines each

int tree_size(const Node *t)
{
    return t ? 1 + tree_size(t->left)
                 + tree_size(t->right) : 0;
}

/* empty = -1, leaf = 0.  The -1 is what
   removes the special cases -- try 0 and
   watch two of them grow back. */
int tree_height(const Node *t)
{
    if (!t) return -1;
    int l = tree_height(t->left);
    int r = tree_height(t->right);
    return 1 + (l > r ? l : r);
}

int count_leaves(const Node *t)
{
    if (!t) return 0;
    if (!t->left && !t->right) return 1;
    return count_leaves(t->left)
         + count_leaves(t->right);
}

/* d = 0, 1 or 2 children */
int count_degree(const Node *t, int d)
{
    if (!t) return 0;
    int c = (t->left != NULL)
          + (t->right != NULL);
    return (c == d)
         + count_degree(t->left,  d)
         + count_degree(t->right, d);
}
/* returns n + 1.  Always.  For every tree
   of every shape -- that is theorem 1, and
   this is the whole proof, executable. */
int count_nulls(const Node *t)
{
    if (!t) return 1;
    return count_nulls(t->left)
         + count_nulls(t->right);
}

/* internal path length: sum of node depths.
   Call it as ipl(root, 0). */
long ipl(const Node *t, int d)
{
    return t ? d + ipl(t->left,  d + 1)
                 + ipl(t->right, d + 1) : 0;
}

/* external path length: sum of the depths
   of the n+1 empty slots.  Note where the
   d goes -- that one swap is the whole
   difference between the two functions. */
long epl(const Node *t, int d)
{
    return t ? epl(t->left,  d + 1)
             + epl(t->right, d + 1) : d;
}

/* BST only: follow the comparisons down */
int depth_of(const Node *t, int key)
{
    int d = 0;
    while (t) {
        if (key == t->key) return d;
        t = key < t->key ? t->left : t->right;
        d++;
    }
    return -1;
}

All of these are postorder in disguise: the parent's answer is a function of the children's answers. When you meet a new "measure the tree" problem, the first question is what a node needs from below — the recursion writes itself after that.

26 — C: the classifiers

Full, perfect, complete, balanced — and the one that is a one-liner

int is_full(const Node *t)
{
    if (!t) return 1;
    /* exactly one child is the only
       thing a full tree forbids */
    if ((t->left == NULL) != (t->right == NULL))
        return 0;
    return is_full(t->left) && is_full(t->right);
}

/* perfect <=> n == 2^(h+1) - 1.
   No shape recursion at all: the maximum
   node count is only reachable by filling
   every level.  Use long so h = 31 does
   not shift a signed int off the end. */
int is_perfect(const Node *t)
{
    int h = tree_height(t);
    return (long)tree_size(t)
         == ((long)1 << (h + 1)) - 1;
}

/* -2 means "unbalanced somewhere below".
   Returning the height as we go is what
   keeps this O(n) instead of O(n^2). */
static int bal(const Node *t)
{
    if (!t) return -1;
    int l = bal(t->left);
    if (l == -2) return -2;
    int r = bal(t->right);
    if (r == -2) return -2;
    if (l - r > 1 || r - l > 1) return -2;
    return 1 + (l > r ? l : r);
}
int is_height_balanced(const Node *t)
{
    return bal(t) != -2;
}
/* Completeness restated: every node's array
   index is below n.  That is the definition,
   not a clever trick -- and it needs no
   queue, no level tracking, no flag. */
static int cidx(const Node *t, long i, long n)
{
    if (!t)     return 1;
    if (i >= n) return 0;
    return cidx(t->left,  2*i + 1, n)
        && cidx(t->right, 2*i + 2, n);
}
int is_complete(const Node *t)
{
    return cidx(t, 0, tree_size(t));
}

/* The textbook BFS version, for contrast.
   q must hold 2n+1 pointers.  Once a gap
   has been seen, nothing may follow it. */
int is_complete_bfs(const Node *t, Node **q)
{
    int head = 0, tail = 0, gap = 0;
    if (!t) return 1;
    q[tail++] = (Node *)t;
    while (head < tail) {
        Node *n = q[head++];
        if (!n) { gap = 1; continue; }
        if (gap) return 0;
        q[tail++] = n->left;
        q[tail++] = n->right;
    }
    return 1;
}

int is_degenerate(const Node *t)
{
    if (!t) return 1;
    if (t->left && t->right) return 0;
    return is_degenerate(t->left)
        && is_degenerate(t->right);
}

The classic wrong is_complete checks only "every level is full except the last" and forgets the left-packing. It accepts a two-node tree whose only child hangs on the right: level 0 is full, the last level is allowed to be partial, and nothing ever looks at the packing. Two nodes is the smallest input that catches it — exercise 5.

27 — C: the validator

Write this first. It tests the theorems, not the printout.

One traversal collects every fact; the assertions are the first half of this deck, executable. Nothing here checks a value you typed in by hand.

typedef struct {
    int n, h, leaves, d1, d2, nulls;
} Facts;

static void survey(const Node *t, int d, Facts *f)
{
    if (!t) { f->nulls++; return; }
    int c = (t->left != NULL) + (t->right != NULL);
    f->n++;
    if (d > f->h) f->h = d;
    if      (c == 0) f->leaves++;
    else if (c == 1) f->d1++;
    else             f->d2++;
    survey(t->left,  d + 1, f);
    survey(t->right, d + 1, f);
}

static int floor_log2(int n)
{
    int k = -1;
    while (n) { k++; n >>= 1; }
    return k;
}

static void check(const Node *t)
{
    Facts f = { 0, -1, 0, 0, 0, 0 };
    survey(t, 0, &f);
    int n = f.n;

    assert(n == tree_size(t));
    assert(f.h == tree_height(t));
    assert(f.leaves + f.d1 + f.d2 == n);
    assert(f.nulls == n + 1);              /* thm 1 */
    assert(n == 0 || f.leaves == f.d2 + 1);/* thm 2 */
    assert(epl(t, 0) == ipl(t, 0) + 2L * n);

    if (n) {
        assert(f.h >= floor_log2(n));
        assert(f.h <= n - 1);
    }
    assert(is_perfect(t) ==
           (n == ((1L << (f.h + 1)) - 1)));
    if (is_perfect(t)) {
        assert(is_full(t));
        assert(is_complete(t));
    }
    if (is_full(t) && n) {
        assert(n % 2 == 1);
        assert(f.leaves == (n + 1) / 2);
        assert(f.d1 == 0);
    }
    if (is_complete(t) && n) {
        assert(f.h == floor_log2(n));
        assert(f.leaves == (n + 1) / 2);
        assert(f.d1 == (n % 2 == 0));
        assert(is_height_balanced(t));
        if (n % 2) assert(is_full(t));
    }
    if (is_degenerate(t) && n) {
        assert(f.d2 == 0);
        assert(f.leaves == 1);
        assert(f.h == n - 1);
    }
}

/* xorshift: the low bit of an LCG alternates,
   so rnd() & 1 would not be a coin flip and
   whole branches would never be reached. */
static unsigned long rs = 88172645463325252UL;
static unsigned long xr(void)
{
    rs ^= rs << 13;
    rs ^= rs >> 7;
    rs ^= rs << 17;
    return rs;
}

/* drop a node into a uniformly chosen slot */
static Node *grow(Node *t, int key)
{
    if (!t) return node_new(key);
    if (xr() & 1) t->left  = grow(t->left,  key);
    else          t->right = grow(t->right, key);
    return t;
}
static Node *build_complete(int n)
{
    if (!n) return NULL;
    Node **a = malloc(n * sizeof *a);
    for (int i = 0; i < n; i++) a[i] = node_new(i);
    for (int i = 0; i < n; i++) {
        if (2*i + 1 < n) a[i]->left  = a[2*i + 1];
        if (2*i + 2 < n) a[i]->right = a[2*i + 2];
    }
    Node *r = a[0];
    free(a);
    return r;
}
int main(void)
{
    for (int n = 0; n <= 300; n++) {
        Node *r = build_complete(n);
        check(r);
        assert(is_complete(r));
        tree_free(r);
    }
    for (int t = 0; t < 50000; t++) {
        Node *r = NULL;
        int n = (int)(xr() % 60);
        for (int i = 0; i < n; i++) r = grow(r, i);
        check(r);
        tree_free(r);
    }
    puts("every identity holds");
    return 0;
}

28 — where the words earn their keep

What this vocabulary is actually for

In production

  • Binary heaps are complete, and that is precisely what makes the pointer-free array legal. Every priority queue, every heapsort.
  • Huffman trees are full, so k symbols build exactly 2k−1 nodes — you size the arena before you start.
  • Segment and Fenwick trees pad n up to a power of two to buy perfection, and eat the dead leaves.
  • Merkle trees duplicate the last leaf for the same reason; Bitcoin's does exactly this.
  • Succinct trees (LOUDS, balanced parentheses) store shape in 2n bits — the Catalan bound, reached.
  • Expression and parse trees are full because a binary operator with one operand is a syntax error.

Where the words mislead

  • "Balanced" is not "fast". A perfectly balanced million-node BST still costs about 20 cache misses per lookup. A B-tree of order 100 costs three. Once you are off-chip, shape within the binary world is a second-order effect.
  • Completeness is not a goal for search trees. Maintaining it costs O(n) per insert. Heaps can afford it only because they never need ordered traversal.
  • Degenerate is not always wrong. If you only append and scan, the linked list wins on every axis.
  • Below about 30 elements, a sorted array with binary search beats every tree on this slide, and you can read it.
  • Random-order analysis is an assumption, not a property. Real input arrives sorted far more often than chance allows.

The three facts, one last time

  • Level ℓ holds at most 2ℓ nodes.
  • 1 + 2 + … + 2h = 2h+1 − 1.
  • n nodes, n−1 edges, 2n slots, n+1 null.

Everything on the previous twenty-seven slides came out of those. If you remember nothing else, remember that you do not have to remember anything else.
