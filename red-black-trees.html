Red-black trees

A binary search tree that stays balanced using one bit per node instead of a stored height — and why that one bit changes what the tree costs to write to.

Sorted input is the worst case for a plain BST. The tree above never exceeds four levels while taking it. Use the arrow keys, or the buttons at the bottom, to move through the deck.

01 — the failure we are fixing

A plain BST has no defence against its input

Insert 1, 2, 3, 4, 5, 6, 7 into an unbalanced BST and every key lands on the right spine. You have written a linked list with extra pointers and worse cache behaviour.

  • Search, insert, delete all degrade from O(log n) to O(n).
  • This is not an exotic input. Sorted or nearly-sorted data is the normal case: timestamps, auto-increment IDs, imported files, a rebuilt index.
  • The average case is fine. The average case is not what breaks at 3am.

Balance is not an optimisation. It is the thing that makes the asymptotic promise of a BST true regardless of who supplies the keys.

02 — the first answer

AVL: measure every subtree, never let it drift

AVL enforces the strictest reasonable invariant:

For every node, |height(left) − height(right)| ≤ 1.

To check it, each node stores its height (or a two-bit balance factor). After every insert and delete you walk back up the path, recompute heights, and rotate wherever the balance factor leaves {-1, 0, +1}.

It works, and it works well: the height of an AVL tree with n keys never exceeds about 1.44 log₂ n — within 44% of a perfectly balanced tree. Lookups are as fast as a BST realistically gets.

What AVL gets right

  • Hard height guarantee, tighter than any competitor in common use.
  • Simple, symmetric case analysis: LL, LR, RR, RL.
  • Shallowest tree ⇒ fewest key comparisons per lookup.

So why does anything else exist?

Because a guarantee about shape is paid for in writes, and AVL's invoice arrives on every single modification — including the ones that change nothing.

03 — the bill

Three costs of being strict

1. Deletion can cascade to the root

An AVL insertion needs at most one rotation (single or double), because that rotation restores the subtree's original height and the fix stops there. Deletion has no such luck: a rotation can leave the subtree one level shorter than before, which unbalances the parent, which unbalances its parent. One deletion can cost O(log n) rotations.

2. Metadata on every path, always

Even when no rotation is needed, every node on the search path has its height recomputed and rewritten. That is a write to O(log n) cache lines per operation, whether or not the shape changed.

3. A strict invariant reacts to small disturbances

|bf| ≤ 1 leaves no slack. A single insertion that nudges one subtree by one level is already a violation, so structural repair — pointer rewriting — is triggered often. Under a lock, or in a shared kernel data structure, every rotation is contention. Under a memory hierarchy, every pointer rewrite is a potential cache miss.

None of this makes AVL wrong. It makes AVL a read-optimised structure. The open question is what you use when writes are frequent, or when the worst-case cost of a single deletion has to be bounded by a constant.

04 — asking a better question

We never needed the tightest tree. We needed a bounded one.

Look at what the asymptotics actually demand. For O(log n) operations, height must be c · log n for some constant c. Any constant. AVL pays a real price on every write to drive c down to 1.44 — but 2 would have been just as good asymptotically, and roughly 1 extra comparison per lookup in practice.

So the design question changes from

“how do I keep this tree as short as possible?”

to

“what is the cheapest invariant to maintain that still caps the height at some constant times log n?”

What “cheap” has to mean

  • Detectable by looking at a node and a couple of its relatives — not by comparing subtree heights.
  • Repairable, in most cases, without touching a single pointer.
  • Bounded number of pointer rewrites per operation, on insert and delete.
  • Stored in as little space as possible.

The last constraint is the giveaway. If the invariant only needs one bit per node, it cannot be about heights. It has to be about something local — a label.

05 — the idea

Colour is a budget, not a decoration

Give every node one bit: red or black. Then impose two constraints that between them do all the work:

  • Every root-to-leaf path contains the same number of black nodes. Call that number the black-height.
  • A red node cannot have a red child.

Now reason about the extremes. The shortest possible path is all black — length equal to the black-height, bh. The longest possible path must alternate, because reds cannot touch: black, red, black, red… — length at most 2 · bh.

The longest path is at most twice the shortest. That is the entire mechanism. No heights are stored, no subtrees are measured, no comparisons of depth are made anywhere.

Black nodes are the structural skeleton and must be perfectly balanced in count. Red nodes are the slack — free insertions that cost nothing structurally, as long as you never stack two of them.

counted toward black-height free slack

Both marked paths pass through exactly the same number of black nodes. One is short because it takes no slack; the other is long because it takes the maximum. Neither can be worse than the other by more than a factor of two.

06 — the invariant, stated properly

Five properties

  1. Every node is either red or black. One bit.
  2. The root is black. Free to enforce — recolouring the root black never breaks anything else.
  3. Every leaf (NIL) is black. The leaves are the null pointers, not the keys. Treating them as real black nodes removes every special case from the code.
  4. If a node is red, both its children are black. Equivalently: no two reds in a row on any path.
  5. For any node, every path from it down to a descendant NIL contains the same number of black nodes.

Reading them correctly

Properties 4 and 5 are the load-bearing pair. Properties 1–3 are bookkeeping that make 4 and 5 cheap to check.

Property 3 is the one students skip. It matters because it makes node->colour readable without a null check — which is why the C implementation uses a shared sentinel rather than NULL.

Note what is absent: no property mentions height, depth, subtree size, or the number of nodes. Every property is checkable by looking at a node and its immediate children.

07 — why the rules are enough

From five local rules to a global height bound

Three steps, no proof machinery.

Step 1 — a subtree with black-height bh holds at least 2bh − 1 nodes

Strip out the red nodes by merging each into its parent. What is left is a tree whose every path has exactly bh nodes, so it is at least as full as a perfect tree of that height.

Step 2 — at least half of any path is black

Property 4 forbids consecutive reds, so on a path of height h at most half the nodes are red: bh ≥ h / 2.

Step 3 — combine

n ≥ 2bh − 1 ≥ 2h/2 − 1, and rearranging gives

h ≤ 2 log₂(n + 1)

Search, insert and delete all follow one root-to-leaf path, so all three are O(log n) — and the constant is 2 instead of AVL's 1.44.

These are worst-case bounds, not typical heights. A red-black tree built from random keys sits close to log₂ n in practice — the gap only opens up under adversarial input.

Trade a handful of extra comparisons on lookup for a constant bound on rotations per write. Whether that is a good trade depends entirely on your read/write ratio — which is the honest answer to “AVL or red-black?”.

09 — evidence, not assertion

Predict first, then run it

Both trees below are real implementations running in this page. Write your prediction down before you press anything.

Questions worth asking before you press

  • Which tree performs more total rotations inserting a sorted run?
  • What is the largest number of rotations either tree needs for a single deletion?
  • How much taller does the red-black tree actually end up?

Reading the result honestly

The per-operation worst case is the guarantee you can rely on. Total counts vary with input order and tell you about typical cost. If the numbers contradict what you expected, the numbers are right — go and work out why.

10 — insertion

New nodes are always red. That choice is the whole design.

You insert exactly as in a plain BST — walk down, attach at the null position — then colour the new node and repair. The colour you choose determines how hard the repair is.

If you inserted it black

Property 5 breaks immediately. Every path through the new node now has one extra black node, and every path not through it does not. That is a global violation: to fix it you would have to reason about the whole tree.

If you insert it red

Property 5 is untouched — red nodes are not counted. The only property that can break is 4, and only if the parent happens to be red. That is a local violation involving four nodes: the new node, its parent, its grandparent, and its uncle.

Every repair either terminates immediately, or pushes an identical local problem two levels up and repeats. At most log n / 2 iterations, at most 2 rotations in total.

The repair loop, in one sentence

While the parent is red, look at the uncle: if it is red, recolour; if it is black, rotate.

That single question — what colour is the uncle? — splits the whole algorithm in two, and it is worth making a student say it out loud before showing them any code.

Three cases

  • Case 1 — uncle red: recolour, move up. No rotation.
  • Case 2 — uncle black, node is an inner child (triangle): rotate at the parent to convert into Case 3.
  • Case 3 — uncle black, node is an outer child (line): recolour and rotate at the grandparent. Loop ends.

Each case has a mirror image for when the parent is a right child. The mirror is the same code with left and right swapped — write one, derive the other, never invent it twice.

11 — insert fixup

Case 1: the uncle is red — recolour and climb

before — Z and its parent P are both red
after — recolour, then treat G as the new Z

Both children of G are red, so G must have been black. Push G's blackness down to both children:

  • P → black, U → black, G → red.
  • Every path through G still crosses the same number of black nodes, so property 5 survives untouched.
  • G is now red and might have a red parent — so set z = G and go round again.

No pointer is written. This is the case AVL cannot have: a rebalance that costs three colour bits and nothing else.

It is also the reason the loop exists at all. Cases 2 and 3 terminate; Case 1 is the one that can repeat, and each repetition moves two levels closer to the root.

12 — insert fixup

Cases 2 and 3: the uncle is black — rotate

With a black uncle, recolouring no longer balances: pushing blackness down from G would rob every path through U. The shape has to change.

Case 2 — the triangle

Z is the inner child of P

Rotate at P in the direction that swings Z outward. Nothing is recoloured. This is purely a normalising move: it turns the zig-zag into a straight line so that a single case can finish the job.

Case 3 — the line

after rotating at P — now Z, P, G form a line

Recolour P black and G red, then rotate at G. P rises into G's old position.

final — subtree root is black, loop terminates

The subtree root ends up black, so it cannot conflict with whatever is above it. The loop condition parent->colour == RED is now false. Case 3 always ends the repair.

Count the rotations across the whole insert: Case 1 does none, Case 2 does one, Case 3 does one and then stops. Worst path through the algorithm is Case 1 repeated, then Case 2, then Case 3 — at most two rotations, ever.

13 — play with it

Build one yourself

Things to try deliberately

  • Insert 1…15 in order and watch the black-height increase in steps, never gradually.
  • Find an insertion that causes a recolour to propagate more than one level.
  • Delete the root repeatedly. Count how often the shape changes at all.

What the counters mean

Rotations are pointer rewrites. Recolours are single-bit writes. When you compare structures, these are not the same unit of cost — that asymmetry is exactly what red-black trees are exploiting.

14 — deletion

Deletion is harder, and it is worth knowing why before you write it

Removing a red node is free. It is not counted by property 5 and it has no red children, so nothing breaks.

Removing a black node destroys property 5 on every path that went through it. Those paths are now one black short, and there is no local recolouring that fixes a deficit — you cannot invent a black node.

The double-black trick

Pretend the node that moved into the gap carries an extra unit of blackness. Property 5 is now satisfied by construction, at the price of a node that is either "doubly black" or "red-and-black". The job of the fixup is to discharge that extra unit — either by finding a red node nearby that can absorb it, or by pushing it up to the parent and trying again.

Insert fixup asks what colour is the uncle?. Delete fixup asks what colour is the sibling, and what colour are the sibling's children?. Same shape of algorithm, one more level of case analysis.

The four cases (x is doubly black, w is its sibling)

caseconditionaction
1w is redrotate at parent, recolour — reduces to case 2, 3 or 4
2w black, both its children blackcolour w red, move the extra black to the parent, loop
3w black, inner child redrotate at w — reduces to case 4
4w black, outer child redrotate at parent, recolour — done

Only case 2 loops, and it performs no rotation. Cases 1, 3 and 4 rotate once each and cases 3–4 terminate, which is where the guarantee of at most 3 rotations per deletion comes from.

Do not try to memorise this table. Implement it from the table, then let a property validator prove you got it right.

15 — implementation in C

Two decisions before you write a line

Decision 1: parent pointers

The fixup walks upwards — node, parent, grandparent, uncle. A recursive BST implementation walks downwards and rebuilds on the way out, which is elegant for AVL and awkward here.

Store a parent pointer. The alternative — passing Node ** around and reattaching subtrees — is legitimate but forces you to hold pointer indirection and tree logic in your head at the same time. Learn the algorithm first; optimise the representation later if you ever need to.

Decision 2: a sentinel NIL, not NULL

Property 3 says the leaves are black nodes. Take that literally: allocate one black node and point every empty child at it.

  • x->parent->colour is always safe to read — no null checks anywhere in the fixup.
  • The root's parent is the sentinel, so "am I the root?" is x->parent == t->nil.
  • Deletion temporarily writes to nil->parent. That is intentional and safe, but it means the sentinel is not thread-safe to share across trees.
#include <stdlib.h>

typedef enum { RED, BLACK } Colour;

typedef struct Node {
    int           key;
    Colour        colour;
    struct Node  *left, *right, *parent;
} Node;

typedef struct {
    Node *root;
    Node *nil;          /* the shared black leaf */
} RBTree;

RBTree *rb_create(void)
{
    RBTree *t = malloc(sizeof *t);
    if (!t) return NULL;

    t->nil = malloc(sizeof *t->nil);
    if (!t->nil) { free(t); return NULL; }

    t->nil->colour = BLACK;
    t->nil->key    = 0;
    t->nil->left   = t->nil->right = t->nil->parent = t->nil;

    t->root = t->nil;
    return t;
}

The sentinel pointing at itself is not a trick for its own sake: it means an accidental read of nil->left yields a black node rather than a segfault, which keeps the fixup code free of defensive branches.

16 — implementation in C

Rotations: the only operation that moves pointers

/* x's right child y takes x's place;
   x becomes y's left child.        */
static void left_rotate(RBTree *t, Node *x)
{
    Node *y = x->right;             /* y != nil */

    x->right = y->left;             /* 1. move y's left subtree */
    if (y->left != t->nil)
        y->left->parent = x;

    y->parent = x->parent;          /* 2. link y to x's parent  */
    if (x->parent == t->nil)
        t->root = y;
    else if (x == x->parent->left)
        x->parent->left = y;
    else
        x->parent->right = y;

    y->left   = x;                  /* 3. put x below y         */
    x->parent = y;
}

static void right_rotate(RBTree *t, Node *y)
{
    Node *x = y->left;              /* x != nil */

    y->left = x->right;
    if (x->right != t->nil)
        x->right->parent = y;

    x->parent = y->parent;
    if (y->parent == t->nil)
        t->root = x;
    else if (y == y->parent->right)
        y->parent->right = x;
    else
        y->parent->left = x;

    x->right  = y;
    y->parent = x;
}

The three-step shape

Every rotation is the same three edge rewrites, and getting them in the wrong order is the classic bug:

  1. Re-home the subtree that changes parents.
  2. Attach the rising node to the old parent — including the root case.
  3. Attach the sinking node below the rising one.

Six pointer fields are written. Six, not four — students routinely forget the parent back-links and then discover it three hours later inside the delete fixup.

Right rotate is not a separate algorithm. Write left_rotate, then produce right_rotate by swapping every left with right. If your two functions differ in any other way, one of them is wrong.

Neither rotation reads or writes a colour, and neither changes the in-order sequence of keys. A rotation is a pure shape change — colours are the caller's problem.

17 — implementation in C

Insert and its fixup

/* returns 1 inserted, 0 duplicate, -1 out of memory */
int rb_insert(RBTree *t, int key)
{
    Node *parent = t->nil, *cur = t->root;

    while (cur != t->nil) {              /* plain BST descent */
        parent = cur;
        if      (key < cur->key) cur = cur->left;
        else if (key > cur->key) cur = cur->right;
        else                     return 0;
    }

    Node *z = malloc(sizeof *z);
    if (!z) return -1;
    z->key    = key;
    z->left   = z->right = t->nil;
    z->parent = parent;
    z->colour = RED;                     /* always red */

    if      (parent == t->nil)     t->root        = z;
    else if (key < parent->key)    parent->left   = z;
    else                           parent->right  = z;

    insert_fixup(t, z);
    return 1;
}
static void insert_fixup(RBTree *t, Node *z)
{
    while (z->parent->colour == RED) {

        if (z->parent == z->parent->parent->left) {
            Node *u = z->parent->parent->right;   /* uncle */

            if (u->colour == RED) {               /* case 1 */
                z->parent->colour         = BLACK;
                u->colour                 = BLACK;
                z->parent->parent->colour = RED;
                z = z->parent->parent;
            } else {
                if (z == z->parent->right) {      /* case 2 */
                    z = z->parent;
                    left_rotate(t, z);
                }
                z->parent->colour         = BLACK;/* case 3 */
                z->parent->parent->colour = RED;
                right_rotate(t, z->parent->parent);
            }
        } else {
            /* mirror: swap every left and right above */
            Node *u = z->parent->parent->left;

            if (u->colour == RED) {
                z->parent->colour         = BLACK;
                u->colour                 = BLACK;
                z->parent->parent->colour = RED;
                z = z->parent->parent;
            } else {
                if (z == z->parent->left) {
                    z = z->parent;
                    right_rotate(t, z);
                }
                z->parent->colour         = BLACK;
                z->parent->parent->colour = RED;
                left_rotate(t, z->parent->parent);
            }
        }
    }
    t->root->colour = BLACK;              /* property 2, free */
}

The loop condition is the whole termination argument. Case 1 leaves z red two levels higher and re-tests. Cases 2 and 3 end with a black subtree root, so the condition fails. The final line enforces property 2 unconditionally, which is legal because recolouring the root black adds one to every path equally.

18 — implementation in C

Delete, transplant, and the fixup

static void transplant(RBTree *t, Node *u, Node *v)
{
    if      (u->parent == t->nil)   t->root = v;
    else if (u == u->parent->left)  u->parent->left  = v;
    else                            u->parent->right = v;
    v->parent = u->parent;      /* safe even if v is nil */
}

static Node *minimum(RBTree *t, Node *x)
{
    while (x->left != t->nil) x = x->left;
    return x;
}

void rb_delete(RBTree *t, Node *z)
{
    Node   *y = z, *x;
    Colour  y_original = y->colour;

    if (z->left == t->nil) {
        x = z->right;
        transplant(t, z, z->right);
    } else if (z->right == t->nil) {
        x = z->left;
        transplant(t, z, z->left);
    } else {
        y = minimum(t, z->right);      /* in-order successor */
        y_original = y->colour;
        x = y->right;

        if (y->parent == z) {
            x->parent = y;
        } else {
            transplant(t, y, y->right);
            y->right = z->right;
            y->right->parent = y;
        }
        transplant(t, z, y);
        y->left = z->left;
        y->left->parent = y;
        y->colour = z->colour;
    }
    free(z);

    if (y_original == BLACK)
        delete_fixup(t, x);           /* a black one vanished */
}

Note what is being tracked: not the colour of the node you asked to delete, but the colour of the node that actually left its position. When z has two children, z's colour is inherited by y and it is y's old colour that disappears from the tree.

static void delete_fixup(RBTree *t, Node *x)
{
    while (x != t->root && x->colour == BLACK) {

        if (x == x->parent->left) {
            Node *w = x->parent->right;        /* sibling */

            if (w->colour == RED) {                    /* 1 */
                w->colour         = BLACK;
                x->parent->colour = RED;
                left_rotate(t, x->parent);
                w = x->parent->right;
            }
            if (w->left->colour  == BLACK &&
                w->right->colour == BLACK) {           /* 2 */
                w->colour = RED;
                x = x->parent;
            } else {
                if (w->right->colour == BLACK) {       /* 3 */
                    w->left->colour = BLACK;
                    w->colour       = RED;
                    right_rotate(t, w);
                    w = x->parent->right;
                }
                w->colour         = x->parent->colour; /* 4 */
                x->parent->colour = BLACK;
                w->right->colour  = BLACK;
                left_rotate(t, x->parent);
                x = t->root;                  /* terminate */
            }
        } else {
            Node *w = x->parent->left;        /* mirror */

            if (w->colour == RED) {
                w->colour = BLACK;
                x->parent->colour = RED;
                right_rotate(t, x->parent);
                w = x->parent->left;
            }
            if (w->right->colour == BLACK &&
                w->left->colour  == BLACK) {
                w->colour = RED;
                x = x->parent;
            } else {
                if (w->left->colour == BLACK) {
                    w->right->colour = BLACK;
                    w->colour        = RED;
                    left_rotate(t, w);
                    w = x->parent->left;
                }
                w->colour         = x->parent->colour;
                x->parent->colour = BLACK;
                w->left->colour   = BLACK;
                right_rotate(t, x->parent);
                x = t->root;
            }
        }
    }
    x->colour = BLACK;      /* discharge the extra black */
}

19 — prove it works

Write the validator before you write delete

A red-black tree can be wrong for thousands of operations and still return correct answers to every search. Only a property check catches it.

/* returns black-height via *bh, or 0 on violation */
static int check(RBTree *t, Node *n, int *bh,
                 long lo, long hi)
{
    if (n == t->nil) { *bh = 1; return 1; }

    if (n->key <= lo || n->key >= hi)          /* BST order */
        return 0;

    if (n->colour == RED &&                    /* property 4 */
        (n->left->colour == RED || n->right->colour == RED))
        return 0;

    int lb, rb;
    if (!check(t, n->left,  &lb, lo, n->key)) return 0;
    if (!check(t, n->right, &rb, n->key, hi)) return 0;

    if (lb != rb) return 0;                    /* property 5 */

    *bh = lb + (n->colour == BLACK);
    return 1;
}

int rb_valid(RBTree *t)
{
    int bh;
    if (t->root->colour != BLACK) return 0;    /* property 2 */
    if (t->nil->colour  != BLACK) return 0;    /* property 3 */
    return check(t, t->root, &bh, LONG_MIN, LONG_MAX);
}
/* randomised differential test against a sorted array */
#define N 20000
int main(void)
{
    RBTree *t = rb_create();
    char   *present = calloc(N, 1);
    srand(12345);

    for (int op = 0; op < 500000; op++) {
        int k = rand() % N;

        if (rand() & 1) {
            int r = rb_insert(t, k);
            assert(r == (present[k] ? 0 : 1));
            present[k] = 1;
        } else {
            Node *z = rb_search(t, k);
            assert((z != t->nil) == present[k]);
            if (z != t->nil) rb_delete(t, z);
            present[k] = 0;
        }
        assert(rb_valid(t));      /* every single op */
    }
    puts("ok");
    return 0;
}

Build it like this:

gcc -Wall -Wextra -O2 -fsanitize=address,undefined rb.c -o rb

Asserting the invariant after every operation is deliberately expensive and deliberately worth it — it turns "the tree broke at some point" into "the tree broke on this exact operation with this exact key". Drop the assert to every 100th op once it passes, if you want to run it longer.

20 — where it lives, and what to do next

Red-black trees in production, and your exercises

Where you are already using one

  • Linux kernel — the CFS scheduler's run queue, the epoll interest set, virtual memory area lookup, and the ext3/4 directory index.
  • C++ — std::map, std::set, std::multimap in every major standard library.
  • Java — TreeMap, TreeSet, and the treeified buckets inside HashMap once a bucket exceeds eight entries.

The common thread is write-heavy or latency-sensitive workloads where a single operation must not be allowed to take O(log n) rotations. That is the requirement AVL cannot meet.

If someone asks in an interview "why does the kernel use a red-black tree rather than AVL?", the answer is not "it is faster". It is bounded rebalancing cost per operation, and cheaper repairs under contention, at the price of a slightly deeper tree.

Exercises — write the prediction down first

  1. Before running anything: how many rotations does inserting 1…7 into an empty red-black tree require? Now instrument left_rotate and right_rotate with a counter and check.
  2. Implement rb_create, rb_search, rb_insert, rb_valid. Do not start deletion until the validator passes 10⁵ random insertions.
  3. What is the black-height of the tree after inserting 1…1000 in order? Predict, then measure.
  4. Implement rb_delete and run the differential harness on the previous slide under AddressSanitizer.
  5. Instrument both trees: for 10⁵ mixed operations, report total rotations, total recolours, and the maximum rotations in any single operation for AVL and red-black. Explain the difference between the two columns.
  6. Property 2 says the root is black. Show that enforcing it is always free — that recolouring a red root black can never violate properties 4 or 5.
