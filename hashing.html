Hashing

Every other lookup structure narrows the search. A hash table refuses to search at all: it computes the address of the answer and goes there.

The whole subject is the price of that refusal — a function that scatters keys evenly, and a plan for the moment two of them land in the same place. Arrow keys, or the buttons below, to move through the deck.

01 — the problem

Array indexing is already O(1). It is also unaffordable.

An array does exactly what we want. The trouble is what it charges for the privilege.

You want a dictionary: store a value under a key, get it back in one step. An array does this perfectly — a[i] is one address computation and one load, no comparisons, no matter how big the array is.

So use an array indexed by the key. This is called direct addressing, and for a small integer key it is genuinely the right answer — a lookup table indexed by a byte is 256 slots and unbeatable.

Now make the key a string, or a 64-bit id, and count the slots you would need:

10 lowercase letters2610 = 141,167,095,653,3761.1 PB
a 64-bit id264 ≈ 1.8 × 1019148 EB
a 16-byte string25616 ≈ 3.4 × 1038more than there are atoms available

And you would be storing perhaps fifty thousand actual entries in it. The table is not merely large — it is almost entirely empty. The ratio of allocated slots to used slots is around 1028.

The alternative you already know

A balanced tree gives you O(log n) and that is genuinely fine. For ten million keys it is 23 comparisons.

But look at what those 23 comparisons are: 23 pointer dereferences to addresses that have nothing to do with each other. On modern hardware that is up to 23 cache misses, each roughly the cost of two hundred arithmetic instructions. The comparisons were never the expense.

02 — what does not fix it

Four repairs that miss

Just allocate a smaller array

Fine — but now two different keys can want the same slot, and you have said nothing about what happens then. That is not a repair, that is the actual problem, restated. It is also, eventually, the answer; it just is not one yet.

Sort the keys and binary search

O(log n) again, and every insert is O(n) because the array has to shift. You have traded a write problem for a read problem and kept the logarithm.

Compress the key into an index

Now you are close. Take the key, squeeze it into a number under m, use that as the index. This is hashing — but "compress" is doing enormous unexamined work. Which compression? What makes one good? And the pigeonhole principle has not gone anywhere: 1038 possible keys into 1,000 slots means collisions are guaranteed, not unlikely.

Find a perfect hash with no collisions

Possible, and genuinely used — for a fixed, known-in-advance key set, like the reserved words of a language. gperf does exactly this. Useless the moment keys arrive at runtime, which is every interesting case.

The first and third repairs are not wrong, they are incomplete. Together they are the design: compress the key into a small range, accept that collisions will happen, and have an answer ready for when they do. Everything in this deck is one of those two halves.

03 — the reframe

Stop giving every possible key a slot. Give every key you have a slot.

Direct addressing sizes the table by the universe of keys — every string you could conceivably be handed. That universe is astronomically larger than the set you will actually store, and the gap is pure waste.

So size the table by n, the number of keys you actually hold, and find a function h that maps the universe U down onto slots 0 … m−1, with m ≈ n.

h : U → {0, 1, …, m−1}

The lookup is then: compute h(key), go to that slot. One arithmetic evaluation and one memory access, independent of n. That is the payoff, and it is why hash tables underpin essentially every interpreter, database and cache you have used.

Since |U| is vastly bigger than m, the pigeonhole principle says some keys must share a slot. That is not a defect in h and no cleverness removes it. So the design splits cleanly in two, and the rest of this deck is those two halves:

  1. The hash function. How do you turn an arbitrary key into a slot number, such that the keys you actually get are spread evenly?
  2. Collision resolution. When two keys land in the same slot, where does the second one go, and how does a lookup find it again?

What "good" has to mean

Before seeing any mechanism, you can already write down what it must satisfy:

  • Deterministic. The same key must hash to the same slot every time, in this run.
  • Fast. If hashing costs more than 23 comparisons, you have built a slower tree.
  • Uniform over m slots — for the keys you actually get, not for imaginary uniform random ones. Real keys are ugly: sequential ids, similar names, shared prefixes.
  • Avalanche. Changing one bit of the key should change about half the bits of the hash. Without this, similar keys land near each other and clump.
  • Depends on the whole key. A hash that reads only the first four bytes cannot distinguish user_00001 from user_00002.

Note what is not on that list: cryptographic strength. A hash table wants speed and spread, not unforgeability — unless an attacker chooses your keys, at which point it wants both. That case gets its own slide at the end, and it has taken down real production systems.

04 — collisions

Collisions are arithmetic, not bad luck

People design hash tables expecting collisions to be an edge case. They are the common case, and much sooner than intuition says.

Throw k keys into m slots, perfectly uniformly at random. The chance that all k land somewhere different is

P(no collision) = (m/m)((m−1)/m)((m−2)/m) … ((m−k+1)/m)

and it falls off a cliff. This is the birthday problem, and the numbers are famously counter-intuitive:

not run yet

A million-slot table has an even-money chance of a collision by the 1,178th key. It is 0.1% full. Any design that treats collision as an exceptional path is a design that takes the exceptional path constantly.

The rule of thumb worth memorising: the first collision arrives around √m keys, not m. It is the same √ that makes a 64-bit hash unsafe against deliberate collision-finding at around 232 attempts.

What this rules out

  • "Collisions are rare, so a slow fallback is fine." It is not fine. The fallback runs on a good fraction of your lookups.
  • "I will pick m big enough that collisions stop." You cannot. The threshold grows as √m, so a thousand times more memory buys you thirty-two times more keys.
  • "A better hash function will fix it." A perfectly uniform hash produces exactly these numbers. The table above is the ideal case.

Which is the real reframe: collision resolution is not error handling. It is a core data-structure operation that runs on the hot path, and it deserves the same care as the hash function itself.

05 — integer keys

The division method, and the choice of m that quietly ruins it

Division: h(k) = k mod m

One instruction on paper, fast enough in practice, and correct for any m. The catch is that mod m keeps only the information that survives division by m — and for the wrong m, that is almost none of it.

If m = 2p, then k mod m is exactly the low p bits of k. The rest of the key is discarded. Hash pointers into a table of size 16 and you get the low 4 bits of an address — which, for 8- or 16-byte aligned allocations, are always zero. Every key lands in slot 0.

The same failure, less dramatically, for any m sharing a factor with structure in your keys. If m = 100 and your keys are prices in whole pounds ending in 99, you use one bucket in a hundred.

Rule: for the division method, make m prime, and not close to a power of 2. A prime shares no factor with any pattern in the keys, so every bit of the key participates in the remainder.

This is why you see table sizes like 53, 97, 193, 389, 769, 1543, 3079, 6151 — a doubling sequence of primes, precomputed, so growing the table is a table lookup rather than a primality test.

Multiplication: the one that tolerates a power of 2

Multiply, take the fractional part, scale to m:

h(k) = ⌊ m · frac(k · A) ⌋,   A = (√5 − 1)/2 ≈ 0.6180339887

The value of A is Knuth's, and the golden ratio is not decoration: it is the irrational hardest to approximate by a fraction, which is exactly the property that stops arithmetic progressions of keys from clumping.

In integer arithmetic, with m = 2p, that whole thing is two instructions:

/* 2654435769 ≈ 2^32 × 0.6180339887 */
uint32_t h = (uint32_t)(k * 2654435769u) >> (32 - p);

The shift takes the high p bits of the product, not the low ones — and the high bits of a multiply depend on every bit of k. That single difference is what makes a power-of-two table safe here and unsafe under division.

Which you pick decides how you grow the table. A power-of-two m makes % m a bit mask and resizing a shift; a prime m costs a real division on every operation but forgives a weaker hash. Both are defensible; mixing them up — a power-of-two table with a division hash — is the common disaster.

06 — string keys

Adding up the characters is the mistake everyone makes first

unsigned h_sum(const char *s) {
  unsigned h = 0;
  while (*s) h += (unsigned char)*s++;
  return h;                       /* fast, deterministic, and useless */
}

It satisfies three of the five requirements on slide 4. It fails the two that matter, and it fails them catastrophically:

  • Order is discarded. Any anagram collides. "abc", "cba", "bac" — one slot. Real key sets are full of anagrams you did not think of: id_12 and id_21, ab/cd and cd/ab.
  • The output range is tiny. The sum of L lowercase letters lies between 97L and 122L — a span of just 25L+1 values. For three-letter keys that is 76 possible hashes, total.

There are 17,576 three-letter lowercase strings and 76 possible sums. Make the table a million slots and 17,500 of those strings still pile into 76 buckets. No table size rescues a hash that throws the information away. The demo on the next slide runs exactly this.

What a real one looks like

/* djb2 — Bernstein. The 33 is a shift-and-add, and the
   multiply carries earlier characters into the high bits,
   so position matters and the range is the full word. */
unsigned h_djb2(const char *s) {
  unsigned h = 5381;
  while (*s) h = h * 33 + (unsigned char)*s++;
  return h;
}

/* FNV-1a — XOR first, then multiply. The XOR mixes the new
   byte into the low bits and the multiply spreads it upward. */
unsigned h_fnv1a(const char *s) {
  unsigned h = 2166136261u;
  while (*s) { h ^= (unsigned char)*s++; h *= 16777619u; }
  return h;
}

What the multiply is actually for

Both real hashes are the same shape: h ← h ⊗ c, folded over the string. The multiplication does two jobs at once:

  • It makes position matter — a character seen earlier has been multiplied more times, so "ab" and "ba" diverge.
  • It pushes information into the high bits, where % m for prime m can still see it.

The odd multiplier is not arbitrary either: an even one would shift a zero into the low bit every round and bleed entropy out of the bottom of the word.

Write neither of these from memory in production. Use the one your platform ships — and if keys can come from a user, use a seeded hash such as SipHash. The last slide explains why that is a security decision and not a performance one.

The C trap, and it is a real one: plain char may be signed. For any byte ≥ 128 — any UTF-8 text at all — *s is negative, and the arithmetic differs between compilers and platforms. Every cast above is (unsigned char) for that reason. A hash that disagrees with itself across builds corrupts any table you persist.

07 — measure the hash

Do not argue about hash functions. Count the buckets.

Three real hash functions over three real key sets, hashed into a real table. Nothing here is quoted from a paper.

Predict first: which of the four key sets will make the good hash functions look worst? And will switching m from prime to a power of two hurt all three equally?

bucket occupancy — how many buckets hold 0, 1, 2, … keys

How to read the numbers

  • χ²/m near 1.0 is ideal. It compares the spread you got against the spread uniform random hashing would give. Much above 1 means clumping; suspiciously far below 1 means the keys are being distributed too evenly to be random, which for a hash table is a bonus, not a fault.
  • Max bucket is the number that bites you. Average chain length is a comfort; the longest chain is your worst-case lookup.
  • Empty buckets should be about m·e−α. Far more empties than that means the keys are concentrated somewhere.

The sum hash on the three-letter set is the one to run first. Whatever you set m to, it cannot use more than 76 buckets, because the function only produces 76 distinct values. Raise m to 65,536 and watch the empty count go up while the max bucket does not move.

Then run the sequential ids with m as a power of two, and compare the sum hash against the other two. Sequential keys are the most common real-world key set there is, and they are exactly the case that finds a weak hash.

08 — the naming trap

Open hashing and open addressing are opposites

This is the worst-named pair of terms in data structures, your syllabus uses both, and examiners love it.

namealso calledwhere the entries live
Open hashingseparate chainingoutside the table, in a list hanging off each bucket
Closed hashingopen addressinginside the table, always, in some other slot

So open hashing is not open addressing — they are the two opposite designs. Getting this backwards in an exam is the single most common way to lose marks on this topic, and it is purely a vocabulary problem, not a comprehension one.

The mnemonic that actually works

Ask what the adjective is describing:

  • Open/closed hashing describes the table. Open hashing: the table is open-ended, entries spill out of it into lists. Closed hashing: the table is closed, everything stays inside.
  • Open addressing describes the address. A key's address is not fixed by its hash — it is open to being somewhere else.

Both phrases are consistent once you notice they are modifying different nouns. In practice, say chaining and open addressing and the ambiguity disappears.

open hashing — chaining: the bucket holds a pointer, the entries are elsewhere
closed hashing — open addressing: the same keys, all inside the array

09 — chaining

Separate chaining: let the bucket overflow somewhere else

Each slot holds the head of a linked list. Insert pushes onto the front — O(1), no search needed if duplicate keys are allowed, one search if they are not. Lookup hashes to the bucket and walks its list. Delete unlinks a node.

Define the load factor α = n/m. Under uniform hashing the expected chain length is exactly α, so:

operationexpectedworst case
unsuccessful search1 + α1 + n
successful search1 + α/21 + n
insertO(1)O(1)
delete1 + α1 + n

Note what is not there: no requirement that α < 1. Chaining works perfectly well with twice as many keys as buckets — α = 2 just means average chains of length two. The structure degrades smoothly and never breaks.

That graceful degradation is chaining's real selling point. Open addressing has a cliff: at α = 1 it is full and stops. Chaining has no cliff at all, which is why it is the safe default when you cannot predict n.

What it costs, honestly

  • A pointer per entry, plus malloc bookkeeping — typically 16 to 32 bytes of overhead on an 8-byte payload.
  • An allocation per insert. On a hot path this can exceed the cost of the hash.
  • A cache miss per hop. Chain nodes come from wherever the allocator had room, so walking a chain of three is three dependent misses. This is the cost that textbooks written before 1990 do not mention, and it is now the dominant one.
  • Delete must handle the head case. Use a Node **pp walking pointer and there is no special case at all — the slide-20 code does this.

The worst case is genuinely O(n): if every key hashes to the same bucket, the table is a linked list with extra steps. That is not hypothetical — it is precisely what an attacker arranges, and the reason Java 8 upgrades a chain to a red-black tree once it passes eight nodes.

Sizing it

Keep α around 1 and the average chain is one node. Many implementations grow at α = 0.75 for cache reasons rather than complexity ones; the maths permits far more.

10 — linear probing

Open addressing: if the slot is taken, keep walking

No lists, no allocation, no pointers. Every entry lives in the array itself. When h(k) is occupied by a different key, you probe a sequence of further slots until you find a free one:

sloti = ( h(k) + i ) mod m,   i = 0, 1, 2, 3, …

Lookup follows the identical sequence and stops at the first empty slot — if the key were in the table it would have been placed before that empty, so an empty slot proves absence. Remember that sentence; the deletion slide is entirely about it.

The appeal is the memory system. The probe sequence walks consecutive addresses, so probes two through eight are usually in the cache line the first probe already fetched. Chaining's second hop is a fresh cache miss; linear probing's second probe is nearly free.

And then, primary clustering

Runs of occupied slots grow, and they grow at an accelerating rate — because a run of length L is hit by any key hashing to any of its L slots, so longer runs capture new keys faster and grow faster still. Two adjacent runs merge into one long one the moment the gap between them fills.

The consequence is a cost curve that does not degrade gracefully, it detonates. Expected probes on an unsuccessful search are ½(1 + 1/(1−α)²):

α0.50.750.90.950.99
probes2.58.550.5200.55,000.5

That 1/(1−α)² is why every open-addressed table in production resizes at α between 0.5 and 0.75, and none of them let it reach 0.9.

Watch for

  • The longest run grows faster than the key count does. That is clustering, visible.
  • Two separate runs merging into one when a single key lands in the gap — one insert can double the worst-case probe length.
  • The average probe count staying low long after the maximum has become alarming. Averages hide this failure completely.
  • The measured probe count sitting below the formula. That is not an error — ½(1+1/(1−α)²) is an asymptotic result for large m, and this table has 64 slots. The gap closes as the table grows; the sweep on slide 16 runs 8,192 slots and lands within a few percent.

11 — better probe sequences

Quadratic and double hashing, and the coprimality rule nobody mentions

Linear

(h + i) mod m

Primary clustering. All keys colliding anywhere in a run share the rest of that run's probe sequence.

Best cache behaviour of the three. Always finds a free slot if one exists.

Quadratic

(h + i²) mod m
or (h + i(i+1)/2) mod m

Secondary clustering. Keys with the same home slot still share a sequence — but keys with different home slots now diverge, which kills the run-merging.

Jumps around, so it gives up the cache locality.

Double hashing

(h₁ + i·h₂(k)) mod m

Neither kind of clustering. The step size itself depends on the key, so two keys sharing a home slot still take different routes out of it.

Closest to the theoretical ideal of uniform hashing. Costs a second hash per lookup.

The trap that silently loses your keys. A probe sequence is only useful if it eventually visits every slot. Both non-linear schemes fail that unless you are careful, and the failure is silent — inserts quietly report "table full" with the table half empty, and lookups miss keys that are present.

schemethe ruleif you break it
quadratic, i²m prime and α < 0.5only ~half the slots are ever probed
quadratic, i(i+1)/2m a power of 2none — this variant provably visits all m
double hashinggcd(h₂(k), m) = 1, and h₂ ≠ 0visits only m/gcd slots

Making h₂ coprime to m, in practice

If m is prime: any h₂ in 1 … m−1 is automatically coprime. h2 = 1 + h % (m-1) is fine.

If m is a power of two: coprime means odd. The textbook 1 + h % (m-1) is not reliably odd, and the table breaks. Force the low bit:

unsigned h2 = ((h >> 3) & (m - 1)) | 1u;   /* always odd */

The >> 3 matters too: without it h₂ is derived from the same low bits that chose the home slot, so keys that collide tend to get the same step as well — reintroducing the clustering you paid a second hash to avoid.

This is not a hypothetical. Writing this deck, the first version of the C used the textbook 1 + h % (m-1) with a power-of-two table. It passed casual testing and failed the randomised harness at operation 86 — a lookup missing a key that was in the table. The harness on slide 23 is the reason you are reading the fixed version.

13 — deletion

Deleting from an open-addressed table by clearing the slot is a bug

It is the single most common way a hand-written hash table silently loses data.

Lookup terminates at the first empty slot, on the reasoning that an insert would have stopped there too. Clear an occupied slot and that reasoning becomes false: you have punched a hole in the middle of a probe sequence, and every key that was placed after that hole is now unreachable from its home slot.

The failure has no symptom at the moment it happens. The delete succeeds. The table reports the right count. Every other key still works. The corruption surfaces later, as a lookup returning "not found" for something you can see in the array — and that is the hardest kind of bug there is.

The fix: a third slot state

A slot is EMPTY, OCCUPIED, or DELETED — a tombstone. It is not a marker of laziness; it carries real information: a key used to live here, so the probe sequence continues past this point.

slot statesearchinsert
EMPTYstop, not foundplace here
OCCUPIEDcompare, else keep goingcompare, else keep going
DELETEDkeep goingremember it, keep going

The asymmetry in the last row is the whole trick, and it is the line people leave out: a search must walk through a tombstone, an insert may reuse it — but only after confirming the key is not already further along the sequence.

Insert therefore remembers the first tombstone it passes and keeps probing. If it finds the key, it updates in place. Only when it reaches an EMPTY does it go back and write at the remembered tombstone. Skip that "keep probing" step and you will happily store the same key twice.

Tombstones accumulate. They cost a probe each and are never reclaimed by more deletes. A long-lived table with heavy churn can end up entirely tombstones: n = 0, every lookup O(m). So the resize trigger must count count + tombstones, never just count — and a rehash is the only thing that clears them.

14 — load factor

The table has to grow, and growing means rehashing everything

The slot a key lives in is a function of m. Change m and every key's home slot changes. There is no way to move a table to a new size without recomputing every entry's position — a resize is O(n) and unavoidable.

Doubling makes it affordable anyway. Growing at m → 2m means the resize cost is paid over m inserts, so it amortises to O(1) per insert: the same argument as a growable array.

Amortised O(1) is not the same as O(1). One unlucky insert in m takes O(n) and stalls. If you are writing anything with a latency target — a game loop, an audio callback, a trading path — size the table up front or use an incremental rehash that migrates a few slots per operation.

When to grow

schemetypical triggerwhy there
chainingα ≥ 0.75 – 1.0chains stay near length 1; above this it is cache, not complexity
linear probingα ≥ 0.5 – 0.75the 1/(1−α)² curve turns vertical just past here
quadratic, i²α < 0.5, strictlyabove 0.5 a free slot may never be probed at all
double hashingα ≥ 0.7degrades most gently of the open-addressed schemes

Four things that go wrong in a resize

  • Counting only live entries. With tombstones in the table the trigger must be (count + tombs)/m, or a churning table never grows and drowns in tombstones.
  • Copying tombstones across. The new table starts clean — reinsert only OCCUPIED slots. This is the one moment tombstones are free to discard, and it is why rehashing is the cure for them.
  • Reusing the old hash value modulo the new m. Tempting, and wrong for open addressing: the whole probe sequence changes. Cache the full hash by all means, but re-probe from scratch.
  • Freeing the old keys too early. Reinsert copies the pointer or the string; free the old table only after every live entry has been moved.

Shrinking deserves a rule too. Halve at α < 0.125, not at α < 0.5 — otherwise a workload that sits right on the boundary alternates grow and shrink on every operation, and each one costs O(n). The gap between the two thresholds is what makes the amortised argument work at all.

Questions worth asking before you press

  • At α = 0.75, how many probes does an unsuccessful linear-probing search take? The formula says 8.5 — will the measurement agree?
  • Which scheme has the worst maximum probe count, and is it the same one with the worst average?
  • Chaining at α = 0.75 versus linear probing at α = 0.75: which touches fewer memory locations? Probes and cache lines are not the same quantity.
  • Does double hashing beat quadratic at low α, high α, or both?

How to read it honestly

  • Probe counts are exact and portable. They are properties of the algorithm and will reproduce anywhere, including in the C.
  • Milliseconds are not. A JavaScript engine hides the memory effects that make linear probing win in C — chain nodes here are objects the engine may lay out contiguously, which a real malloc will not. Treat the time column as a hint and the probe column as evidence.
  • The maximum matters more than the mean. Your p99 latency is set by the longest probe, and the mean stays reassuring long after the maximum has gone bad.
  • If the measurement contradicts something on an earlier slide, the measurement wins. Say so out loud and work out why.

16 — design decisions

Five choices, made before the first line

1 · Chaining or open addressing

Chaining when n is unpredictable, deletes are frequent, or entries are large. It never fills up and deletion is trivial.

Open addressing when entries are small and lookups dominate. No allocator traffic, and probes hit cache lines you already paid for.

If you are unsure: chaining. It has no cliff.

2 · Who owns the key

Copy it (strdup) and the table owns memory it must free. Store the caller's pointer and lookups are free — until the caller frees or mutates the key and the table silently corrupts.

Copy, unless you can state the lifetime rule in one sentence and enforce it.

3 · Prime m or a power of two

Prime: forgiving of a weak hash, costs a real % — about 20–40 cycles — on every operation.

Power of two: % m becomes & (m-1), one cycle. Demands a hash with good low bits, and constrains both non-linear probe sequences (slide 12).

The code here uses powers of two with FNV-1a, whose avalanche makes the low bits sound.

4 · Cache the hash?

Storing the 32-bit hash beside each entry lets you skip strcmp whenever hashes differ — a large win for long string keys, and it makes resizing cheaper. Costs 4 bytes a slot.

5 · How you say "empty"

You need three states in open addressing, and how you encode them matters:

  • An explicit state byte. Clear, one extra byte per slot, what the code here does.
  • Sentinel key values — NULL for empty, (char*)1 for deleted. Saves the byte, and is exactly the sort of cleverness that produces a crash six months later.
  • A separate bitmap. Two bits per slot, packed. Best cache behaviour, most code.

Take the explicit byte until you have measured that it matters.

Write the invariant down before the code: every OCCUPIED key is reachable from its home slot without crossing an EMPTY. That one sentence is what deletion must preserve, what resize must re-establish, and what the validator on slide 23 checks. Everything else follows from it.

17 — the hash functions in C

Three hashes, one cast that is not optional

#include <stdint.h>

/* THE TRAP: plain `char` may be signed. For any byte >= 128 --
   that is, any UTF-8 text at all -- *s is NEGATIVE, the
   arithmetic differs between platforms, and a hash you
   persisted on one machine does not match on another.
   Every one of these casts to unsigned char. It is not style. */

/* the broken one, kept so the deck can measure it */
unsigned h_sum(const char *s) {
  unsigned h = 0;
  const unsigned char *p = (const unsigned char *)s;
  while (*p) h += *p++;
  return h;
}

/* djb2 -- Bernstein. h*33 is (h<<5)+h, so it is two
   integer ops, and the compiler will find that itself. */
unsigned h_djb2(const char *s) {
  unsigned h = 5381;
  const unsigned char *p = (const unsigned char *)s;
  while (*p) h = h * 33 + *p++;
  return h;
}

/* FNV-1a -- XOR then multiply. Better avalanche in the low
   bits than djb2, which is what a power-of-two table needs. */
unsigned h_fnv1a(const char *s) {
  unsigned h = 2166136261u;                  /* FNV offset basis */
  const unsigned char *p = (const unsigned char *)s;
  while (*p) { h ^= *p++; h *= 16777619u; }  /* FNV prime        */
  return h;
}

Unsigned overflow in C is defined behaviour — it wraps modulo 232. That is exactly what these rely on, and it is why every variable here is unsigned and not int. Signed overflow is undefined, and the same code written with int is a UB bug that -fsanitize=undefined will report.

Proving the trap is real

/* on a platform where char is signed (x86 Linux, macOS): */
char c = (char)200;
printf("%u\n", (unsigned)c);        /* 4294967240  */
printf("%u\n", (unsigned)(unsigned char)c);  /* 200 */

The first line sign-extends to a huge value. Fold that into a running hash and every byte above 127 contributes wildly differently than intended — and on ARM, where char is unsigned by default, it does not. Same source, two hash values.

Checking your hash before you trust it

Two five-minute tests that catch most weak hashes:

  • Anagrams. h("abc") == h("cba") must be false. The sum hash fails this and so does any hash without a multiply.
  • Avalanche. Flip one bit of a key and count the output bits that changed. It should be near 16 of 32. Consistently under 4 means the hash is not mixing and a power-of-two table will clump.

Slide 8 runs the bucket-distribution version of this on four key sets.

Do not invent your own. These are here so you can read one and know what the shape means; in production use your platform's, and use a seeded hash the moment keys can come from a user.

18 — chaining in C

Separate chaining, including the delete that has no special case

typedef struct Node {
  char *key; int val; struct Node *next;
} Node;

typedef struct {
  Node **bucket; size_t m, count;
  unsigned (*hash)(const char *);
} Chain;

Chain *chain_new(size_t m, unsigned (*h)(const char *)) {
  Chain *t = malloc(sizeof *t);
  t->bucket = calloc(m, sizeof *t->bucket);  /* all NULL */
  t->m = m; t->count = 0; t->hash = h;
  return t;
}

int chain_put(Chain *t, const char *key, int val) {
  size_t b = t->hash(key) % t->m;
  for (Node *n = t->bucket[b]; n; n = n->next)
    if (strcmp(n->key, key) == 0) { n->val = val; return 0; }

  Node *n = malloc(sizeof *n);
  n->key = strdup(key); n->val = val;
  n->next = t->bucket[b];        /* push at the head: O(1) */
  t->bucket[b] = n; t->count++;
  return 1;
}

int chain_get(Chain *t, const char *key, int *out) {
  size_t b = t->hash(key) % t->m;
  for (Node *n = t->bucket[b]; n; n = n->next)
    if (strcmp(n->key, key) == 0) { *out = n->val; return 1; }
  return 0;
}
/* The pointer-to-pointer walk. `pp` always points AT the
   link that must be rewritten -- the bucket slot itself on
   the first iteration, a node's next field afterwards.
   So the head case and the middle case are the same code. */
int chain_del(Chain *t, const char *key) {
  size_t b = t->hash(key) % t->m;
  Node **pp = &t->bucket[b];
  while (*pp) {
    if (strcmp((*pp)->key, key) == 0) {
      Node *dead = *pp;
      *pp = dead->next;          /* unlink, wherever we are */
      free(dead->key); free(dead);
      t->count--;
      return 1;
    }
    pp = &(*pp)->next;
  }
  return 0;
}

void chain_free(Chain *t) {
  for (size_t i = 0; i < t->m; i++) {
    Node *n = t->bucket[i];
    while (n) {
      Node *nx = n->next;        /* save BEFORE freeing */
      free(n->key); free(n);
      n = nx;
    }
  }
  free(t->bucket); free(t);
}

The Node **pp idiom is worth the two minutes it takes to understand. Written with a prev pointer instead you need if (prev == NULL) bucket[b] = ...; else prev->next = ...; — a branch that exists only to say the same thing twice, and the branch people get wrong.

nx = n->next before the free, not after. Reading a freed node is the classic use-after-free in list teardown, it usually appears to work, and ASan catches it instantly.

19 — open addressing in C

Three slot states, and the insert that respects all of them

typedef enum { EMPTY = 0, OCCUPIED = 1, DELETED = 2 } SlotState;
typedef struct { char *key; int val; SlotState state; } Slot;

typedef struct {
  Slot *slot; size_t m, count, tombs;
  unsigned (*hash)(const char *);
  int mode;              /* 0 linear, 1 quadratic, 2 double */
} Open;

/* m is a power of two here, which constrains both non-linear
   modes -- see slide 12. Break either rule and the probe
   sequence stops covering the table, silently. */
static size_t probe_at(Open *t, unsigned h, size_t i) {
  switch (t->mode) {
    case 1:                       /* triangular numbers:    */
      return (h + i*(i+1)/2) % t->m;   /* visits all m      */
    case 2: {                     /* h2 must be ODD here    */
      unsigned h2 = ((h >> 3) & (unsigned)(t->m - 1)) | 1u;
      return (h + i*h2) % t->m;
    }
    default:
      return (h + i) % t->m;
  }
}

int open_get(Open *t, const char *key, int *out, int *probes) {
  unsigned h = t->hash(key); int p = 0;
  for (size_t i = 0; i < t->m; i++) {
    size_t b = probe_at(t, h, i); p++;
    if (t->slot[b].state == EMPTY) { *probes = p; return 0; }
    if (t->slot[b].state == OCCUPIED &&
        strcmp(t->slot[b].key, key) == 0) {
      *out = t->slot[b].val; *probes = p; return 1;
    }
    /* DELETED: keep walking. That is the whole point. */
  }
  *probes = p; return 0;
}
int open_put(Open *t, const char *key, int val, int *probes) {
  /* the trigger counts TOMBSTONES too, or a churning table
     never grows and slowly fills with them */
  if ((double)(t->count + t->tombs + 1) / (double)t->m > 0.70)
    open_grow(t);

  unsigned h = t->hash(key);
  size_t first_tomb = (size_t)-1;
  int p = 0;

  for (size_t i = 0; i < t->m; i++) {
    size_t b = probe_at(t, h, i); p++;

    if (t->slot[b].state == EMPTY) {
      /* only now is it safe to use the tombstone: we have
         proved the key is not further down the sequence */
      if (first_tomb != (size_t)-1) { b = first_tomb; t->tombs--; }
      t->slot[b].key = strdup(key);
      t->slot[b].val = val;
      t->slot[b].state = OCCUPIED;
      t->count++; *probes = p; return 1;
    }
    if (t->slot[b].state == DELETED) {
      if (first_tomb == (size_t)-1) first_tomb = b;
      continue;                  /* remember it, keep going */
    }
    if (strcmp(t->slot[b].key, key) == 0) {
      t->slot[b].val = val; *probes = p; return 0;  /* update */
    }
  }
  return -1;      /* unreachable while the resize above runs */
}

int open_del(Open *t, const char *key) {
  unsigned h = t->hash(key);
  for (size_t i = 0; i < t->m; i++) {
    size_t b = probe_at(t, h, i);
    if (t->slot[b].state == EMPTY) return 0;
    if (t->slot[b].state == OCCUPIED &&
        strcmp(t->slot[b].key, key) == 0) {
      free(t->slot[b].key);
      t->slot[b].key = NULL;
      t->slot[b].state = DELETED;   /* NOT EMPTY. Never EMPTY. */
      t->count--; t->tombs++;
      return 1;
    }
  }
  return 0;
}

Read open_put's loop once more. It cannot write at the tombstone the moment it sees one, because the key might already exist further along the probe sequence — and writing early would store it twice, with the second copy permanently shadowed. That is why first_tomb is remembered and used only at the EMPTY.

20 — resize and teardown

The rehash, which is also the only cure for tombstones

/* Called from open_put when (count + tombs + 1)/m exceeds
   the threshold. Note what it does NOT do: it does not copy
   the old array, and it does not carry tombstones across.
   The new table starts clean, which is the moment every
   accumulated tombstone is discarded for free. */
static void open_grow(Open *t) {
  size_t om  = t->m;
  Slot  *os  = t->slot;

  t->m     = om * 2;
  t->slot  = calloc(t->m, sizeof *t->slot);
  t->count = 0;
  t->tombs = 0;                     /* gone, all of them */

  for (size_t i = 0; i < om; i++) {
    if (os[i].state == OCCUPIED) {
      open_put(t, os[i].key, os[i].val, NULL);  /* re-probes */
      free(os[i].key);              /* open_put strdup'd it  */
    } else if (os[i].key) {
      free(os[i].key);              /* defensive: tombstones */
    }                               /* should own no key     */
  }
  free(os);
}

void open_free(Open *t) {
  for (size_t i = 0; i < t->m; i++)
    if (t->slot[i].key) free(t->slot[i].key);
  free(t->slot);
  free(t);
}

The recursion here is safe and worth noticing: open_grow calls open_put, which begins by testing the load factor. After doubling, the factor is at most half the threshold, so the test cannot fire again. Depth two, never three. Convince yourself of that before you ship it — an accidental resize loop inside a resize is a stack overflow with a very confusing trace.

The free(os[i].key) inside the loop is the line that gets omitted. open_put makes its own copy with strdup, so the old copy is now garbage and leaks silently — a leak that grows with every resize and never appears in a functional test. -fsanitize=address at exit names it immediately.

The cheaper variant, if you cached the hash

Storing each entry's 32-bit hash lets the rehash skip the hash function entirely and move the pointer rather than copying the string:

/* no strdup, no free, no rehashing of the key bytes */
size_t b = find_free_slot(t, os[i].hash);
t->slot[b] = os[i];          /* steal the pointer   */
os[i].key  = NULL;           /* old table disowns it */

For a table of long string keys this turns an O(n·len) resize into an O(n) one. It also makes the ownership rule subtler, which is the trade.

Growing chaining instead

Same idea, and slightly nicer: chain nodes can be relinked rather than reallocated, since the node already holds the key. Walk each old bucket, compute the new index, splice the node onto the new bucket's head. No malloc, no strdup, no free in the whole resize.

21 — testing it

Write the validator before you write delete

A hash table with a broken probe chain answers almost every query correctly. Only a property check finds the operation that broke it.

/* THE INVARIANT, stated as code: every OCCUPIED key must be
   findable from its own home slot. If a delete punched a hole
   in a probe sequence, some key stops being reachable and
   this returns 0 -- while the array still visibly contains it. */
int open_valid(Open *t) {
  size_t occ = 0, tom = 0;
  for (size_t i = 0; i < t->m; i++) {
    if (t->slot[i].state == OCCUPIED) {
      occ++;
      if (!open_get(t, t->slot[i].key, NULL, NULL)) return 0;
    } else if (t->slot[i].state == DELETED) {
      tom++;
      if (t->slot[i].key) return 0;   /* a tombstone owns no key */
    }
  }
  return occ == t->count
      && tom == t->tombs
      && occ + tom <= t->m;
}

It is O(m·probes) and far too slow for production — call it every few hundred operations in the test harness and never in the shipped path. That is the normal shape for an invariant checker.

And a negative control

/* Keep the WRONG delete in the test file. A test that cannot
   fail is not evidence. This one proves the harness would
   actually notice if you got deletion wrong. */
int open_del_broken(Open *t, const char *key) {
  /* ... identical, except: */
  t->slot[b].state = EMPTY;      /* the bug */
  t->count--;
  return 1;
}

Find three keys that share a home slot, insert them, delete the middle one with the broken version, and assert the third key is now not found. If that assertion ever passes, your test is not exercising the path you think it is.

The differential harness

/* Random ops against a reference model. The model is a plain
   array indexed by key number -- obviously correct, absurdly
   slow, and therefore the perfect oracle. */
int main(void) {
  int ok = 1; char kb[64];

  for (int mode = 0; mode < 3; mode++) {
    Open *t = open_new(64, h_fnv1a, mode);
    int model[N]; for (int i = 0; i < N; i++) model[i] = -1;

    for (int op = 0; op < 120000; op++) {
      int i = rnd() % N; keyof(kb, i);

      if (rnd() % 2 == 0) { int v = rnd() % 1000;
                            open_put(t, kb, v, NULL); model[i] = v; }
      else                { open_del(t, kb);          model[i] = -1; }

      int got, found = open_get(t, kb, &got, NULL);
      if (found != (model[i] >= 0)) { ok = 0; break; }
      if (found && got != model[i]) { ok = 0; break; }

      if (op % 211 == 0 && !open_valid(t)) { ok = 0; break; }
    }
    /* then sweep EVERY key, present or not, against the model */
    for (int i = 0; i < N; i++) { keyof(kb, i); int got;
      if (open_get(t, kb, &got, NULL) != (model[i] >= 0)) ok = 0; }
    open_free(t);
  }
  puts(ok ? "ALL PROPERTY TESTS PASSED" : "FAILURES");
  return !ok;
}

Build it this way, every time:

gcc -std=c11 -Wall -Wextra -O1 \
    -fsanitize=address,undefined hashing.c -o hashing

This exact harness is what caught the double-hashing bug described on slide 12 — at operation 86, on the third mode, with a lookup that missed a key that was present. Casual testing had not touched it. The final sweep matters as much as the loop: it is what proves no key was orphaned along the way.

22 — the adversarial case

When the keys are chosen by someone who read this deck

Average-case O(1) assumes the keys are not picked to defeat you. On a web server, they are.

Every bound in this deck is an average over keys that spread evenly. Feed a table n keys that all hash to the same bucket and it degrades to a linked list: every operation O(n), and building the table O(n²).

Now consider that a web framework puts HTTP POST parameters into a hash table, keyed by names the client chooses. If the hash function is public and unseeded — and djb2 and FNV are both entirely public — an attacker can precompute thousands of colliding parameter names offline and send them in one request.

This is hash flooding, and it was demonstrated against PHP, Python, Ruby, Java, ASP.NET and Node in the same disclosure. A single request of a few hundred kilobytes could occupy a CPU for minutes. The fix landed across every major runtime within months.

What the fix is

  • A per-process random seed mixed into the hash at startup. The attacker cannot precompute collisions without knowing it.
  • A keyed hash designed for this — SipHash-1-3 is the standard choice, fast enough for a hash table and built to resist collision-finding even when the output is observable.
  • A cap on the collision chain, converting to a tree past a threshold — Java 8's approach, which bounds the damage to O(log n) rather than preventing it.

The judgement call is simple: if any key can originate outside your process, use a seeded hash. Internal keys you generated yourself do not need it and should not pay for it.

23 — where it wins, where it loses

Unbeatable for exact lookup. Useless for anything ordered.

Where hashing is the right answer

  • Every language's dictionary. Python dict, JS objects, Java HashMap, Go map. Interpreters resolve variable names through one on every access.
  • Compiler symbol tables and string interning.
  • Caches — memcached, Redis, your CPU's own cache lines.
  • Database joins. A hash join is the standard plan for equality joins on unsorted input.
  • Deduplication and set membership, including Bloom filters, which are hashing with the table thrown away.
  • Sharding and load balancing — consistent hashing decides which server owns a key.

Where it loses

  • Range queries. "All keys between 100 and 200" requires scanning the whole table. A good hash deliberately destroys the ordering that would have made this cheap.
  • Ordered iteration. Traversal order is arbitrary and changes when the table resizes.
  • Min, max, successor, predecessor. All O(n).
  • Prefix and fuzzy matching. Autocomplete cannot use a hash table; one character's difference means an unrelated slot.
  • Hard latency bounds. The amortised resize stalls, and the worst case is O(n).
  • Adversarial keys, unless seeded — the previous slide.
  • Tiny n. Under about a dozen entries, a linear scan of an array beats hashing and fits in one cache line.

Reach for instead

  • A B-tree or B+ tree — ranges, ordered scans, and on-disk data. This is why database indexes are B-trees and not hash tables.
  • A red-black or AVL tree — ordered in-memory data with guaranteed worst-case bounds.
  • A trie — prefix search, autocomplete, routing tables.
  • A sorted array — small, static, read-only key sets. Binary search with perfect cache behaviour.
  • A perfect hash (gperf) — a fixed key set known at compile time, such as language keywords. One probe, guaranteed, no collisions at all.

Exercises — predict first, then measure

  1. Before running anything: with m = 1,000 buckets and a perfect hash, how many keys before you expect a collision? Now check it against the simulator on slide 5, and explain why the answer is nearer 38 than 500.
  2. Implement h_sum and hash all 17,576 three-letter lowercase strings into a table of 10,007. Predict the number of non-empty buckets before you run it. Then explain why raising m to 100,003 does not change that number.
  3. Build a linear-probing table with m = 16 and no resizing. Insert keys until it is full, then insert one more. What does your code do? If the honest answer is "loops forever", fix it — and note that the bound is the loop condition i < m, not a flag.
  4. Write open_del the wrong way — state = EMPTY. Then find the shortest sequence of operations on the smallest table that makes a present key unfindable. Three keys and one delete is enough; get it down to that.
  5. Instrument open_get to count probes and plot the average against α from 0.1 to 0.95 in steps of 0.05. Compare your curve to ½(1 + 1/(1−α)²). Where it disagrees, say which assumption of the formula your table violates.
  6. Take a table through 100,000 alternating inserts and deletes of the same 50 keys, with no resize. Predict what tombs reaches, then measure. Now change the resize trigger to count only count and not count + tombs, and explain the result.
  7. Write the anagram test and the avalanche test from slide 18 and run them on h_sum, h_djb2 and h_fnv1a. Predict which one wins the avalanche test before you measure — then check whether the winner is also the winner on the bucket-distribution test on slide 8.
