The heap
8 nodes for 8 players. The winners moved up and took their slot with them.

The one rule that survived

Every parent is ≥ both of its children. That is the entire definition of a max-heap. It is just "the winner sits above the people it beat", written down.

The rule that did not survive

Nothing whatsoever is promised about left vs right. Siblings never played each other, so the heap has no opinion about them. None.

The trap that costs marks every year

It is a tree. It is not a search tree.

Max-heap

BST
Ordered horizontally. In-order traversal comes out sorted, by construction.

Pens down

Sink it. One node, one path, straight down.

Never sideways, never back up. At most height steps — that's log₂n.

The loop

siftDown(a, i, n): while left(i) < n: big = left(i) if right(i) < n and a[right(i)] > a[big]: big = right(i) // the LARGER child if a[i] >= a[big]: return // stop: rule satisfied swap(a[i], a[big]) i = big // follow it down

Why the larger child — the proof

Swap 9 with the smaller child 55 and you get 55 sitting above 66. Still broken, and now you've wasted a move. The promoted value must beat both children, and only the bigger of the two is guaranteed to.

Notice what the loop never does. It never looks at a sibling subtree, never climbs, never restarts. That is the whole reason it costs O(log n) and not O(n) — and it works only because you were promised both subtrees were already heaps. Break that promise and sift-down quietly returns you a broken heap. Remember that in twenty slides.

The whole build

buildHeap(a, n): for i = n/2 - 1 down to 0: siftDown(a, i, n)

Two lines. No second array, no insert routine, no recursion needed.

Why backwards is not optional

siftDown(i) is only correct when both subtrees of i are already heaps. Walking from the bottom up makes that true by induction: when you arrive at i, everything below it is finished. Go top-down instead and every call is a lie — you'll get an array that looks repaired and isn't.

Add up the real work

total ≤ Σ (n / 2^(h+1)) × h = n × Σ h / 2^(h+1) = n × 1 = O(n)

That sum converges — it does not grow with n. Building a heap is linear: cheaper than one pass of most sorts.

Then why is heap sort n log n?

Because building the heap was never the expensive part. Draining it is: n extractions, each one a full-height sift-down from the root — and the root is precisely the node the argument above said was expensive. Which brings us to the last question of the day.

The entire algorithm

heapSort(a, n): buildHeap(a, n) // O(n), once for end = n-1 down to 1: swap(a[0], a[end]) // max to its final home siftDown(a, 0, end) // heap is one smaller now

Why it needs no extra memory

One array, one boundary. Left of it: a shrinking heap. Right of it: a growing, already-final sorted tail. They can never collide, because they are the same moving line. Total extra space: a couple of ints.

Read it right-to-left

The green tail grows by exactly one cell per pass, and nothing in it ever moves again. Cover the left half with your hand: the right half is already the answer.

The red cell is not "the biggest left"

It is the biggest of what remains — and it got there for free, because the heap put it at index 0 while you weren't looking. That is the whole payoff of the tournament.

And the bill

n passes × log n per sink = O(n log n), guaranteed, every time, on every input — plus O(1) memory.

Pick heap sort when

You cannot afford a bad day (no n² worst case, ever) and you cannot afford extra memory. Embedded, kernels, real-time. It has no pathological input to trip over.

Skip it when

You need stability, or raw speed on typical data — quick sort usually wins on wall-clock because heap sort jumps all over memory and the cache hates it.

The bigger prize

Sorting is the side effect. The heap itself is a priority queue: O(log n) insert, O(1) peek, O(log n) extract. Schedulers, Dijkstra, A*, event simulation, your OS run queue.

Your turn now

Four drills. Same four moves every time.

1 · Draw the tree

From the array, using 2i+1 / 2i+2. Yes, every time. The people who "do it in their head" are the people who lose a subtree.

2 · Compare, pick the bigger child

Both children, then the bigger one, then the parent. In that order — it's the order that stops you swapping the wrong way.

3 · Swap and follow

Rewrite the whole array after each swap and move your finger to the child's index. Never look back up.

4 · Verify

Walk indices 0 .. n/2-1 and check each against its children. A heap you didn't verify is a heap you didn't build.

Sixteen lines

Every idea from today, in C, with no malloc in sight.

void siftDown(int a[], int i, int n) { while (2*i + 1 < n) { // while a left child exists int big = 2*i + 1; if (big + 1 < n && a[big + 1] > a[big]) big++; // right child is bigger if (a[i] >= a[big]) return; // heap rule holds, done int t = a[i]; a[i] = a[big]; a[big] = t; i = big; } } void heapSort(int a[], int n) { for (int i = n/2 - 1; i >= 0; i--) siftDown(a, i, n); // build: O(n) for (int end = n - 1; end > 0; end--) { int t = a[0]; a[0] = a[end]; a[end] = t; siftDown(a, 0, end); // drain: O(n log n) } }

C trap 1 · the missing guard

Drop big + 1 < n and you read a[n] — which during the sort is a retired, already-sorted value. No crash, no warning: it quietly drags sorted elements back into the heap. Your array comes out almost sorted, which is the worst kind of bug.

C trap 2 · the unsigned loop

size_t i = n/2 - 1; while (i >= 0) { ... i--; } // hangs forever

An unsigned i is never < 0. It wraps to a gigantic number and walks off the array. Use a signed int for any index that counts down to zero.

Want a min-heap?

Flip > to < and >= to <=. That is the complete diff. The sort then comes out descending — work out why before next lab.

The index arithmetic (0-based)

left(i) = 2i+1 right(i) = 2i+2 parent(i) = (i-1)/2 last non-leaf = n/2 - 1 height = ⌊log₂n⌋

The two rules

Shape: complete — every level full, last level packed left.
Order: parent ≥ both children. Siblings: no relationship whatsoever.

The loop

1. buildHeap: sift down from n/2-1 to 0.
2. Swap a[0] with a[end].
3. Shrink the heap by one.
4. Sift the new root down; repeat.

Costs

peek max O(1) build heap O(n) insert / extract O(log n) heap sort O(n log n) always extra space O(1) search for a value O(n)

The two directions

siftDown value too small for its position — used by build & extract. Compare against the bigger child.
siftUp value too big for its position — used by insert. Compare against the parent, no choice to make.

Insert — for when you want a priority queue

a[n] = v; n++; // next free slot, keeps it complete i = n-1; while (i > 0 && a[parent(i)] < a[i]) { swap(a[i], a[parent(i)]); i = parent(i); }
Learn from other people's pain

The five mistakes, ranked by how often I see them.

1 · Swapping with the wrong child

Compare the two children to each other first, then the winner to the parent. Swap with the smaller one and the heap is still broken — you moved the problem sideways.

2 · Stopping after one swap

Sift-down is a loop, not a step. Follow the value down until it beats both children or runs out of them. Drill 1 exists entirely for this.

3 · Forgetting to shrink

Swap, then n--, then sift. Sift with the old n and the value you just retired gets pulled back in — output nearly sorted, and wrong.

4 · Building the heap top-down

Sift-down assumes both subtrees are already heaps. Walking forwards from index 0 breaks that on every call, and yields an array that looks plausible and isn't.

5 · Expecting the heap to look sorted

Mid-sort the heap region is supposed to be a jumble — the only promise is the root. If you catch yourself checking left < right, you're still thinking in BST.
