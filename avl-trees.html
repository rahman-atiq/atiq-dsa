AVL trees

The first data structure anyone built that repairs its own shape — invented in 1962, and still the shortest balanced binary search tree you can have.

The tree above is taking keys in ascending order, the input that destroys an ordinary BST. Watch the height. Arrow keys, or the buttons below, to move through the deck.

01 — the failure we are fixing

A binary search tree is only as good as the order it was fed

The BST promise is O(log n). The proof of that promise quietly assumes the tree is bushy — and nothing in the insert algorithm enforces it.

Feed the same keys in two different orders and you get two completely different structures with the same contents:

  • Random order — height around 1.39 log₂ n. Fine.
  • Ascending order — every key goes right. Height n. You have built a singly linked list that also wastes a pointer per node.

Sorted input is not a contrived attack. It is the default: primary keys, timestamps, a table rebuilt from a sorted export, an index restored from a backup.

Search on the degenerate tree is O(n). At a million keys that is a million comparisons instead of twenty.

02 — what should "balanced" mean?

Three definitions, two of them useless

Perfectly balanced

Every level full except the last. Height is exactly ⌈log₂(n+1)⌉ — optimal.

Unusable. A single insertion can force a near-total rebuild. Maintaining it costs O(n) per write.

Weight balanced

Every node's two subtrees hold roughly the same number of nodes.

Expensive. Every node must store a subtree size, and a single insertion changes that count on every node up to the root — before you even consider rotating.

Height balanced

Every node's two subtrees differ in height by at most one.

Workable. It is a local test, it needs one small number per node, and — the part that is not obvious — it still forces the height to O(log n).

The move here is giving up optimality to buy maintainability. A perfectly balanced tree is shorter than an AVL tree by a fraction of a level, and costs orders of magnitude more to keep that way. Adelson-Velsky and Landis found the loosest constraint that still works.

03 — the idea

One number per node, checked locally

Define the balance factor of a node as

bf(n) = height(n.left) − height(n.right)

An AVL tree is a binary search tree in which every node satisfies bf ∈ {−1, 0, +1}.

That is the entire definition. Two things about it are worth pausing on.

It is local

Checking a node requires its two children's heights and nothing else. No traversal, no global state, no comparison with a distant part of the tree.

It is cheap to keep current

An insertion or deletion can only change the heights of nodes on the path back to the root. Everything off that path is untouched, so one walk up the path re-establishes the invariant.

balance factor shown beside each node

Height, by convention

This deck uses height(empty) = 0 and height(leaf) = 1, which makes the C code a clean 1 + max(left, right) with no negative numbers.

CLRS uses height(leaf) = 0 instead. Both are fine; mixing them inside one implementation is not. Pick one, write it in a comment at the top of the file, and never think about it again.

04 — why one level of slack is enough

The emptiest legal AVL tree is a Fibonacci tree

To bound the height, ask the opposite question: for a given height h, what is the fewest nodes an AVL tree can have? Call it N(h). That worst case is the tree that is as stringy as the rules allow.

Build it greedily. A minimal tree of height h has a root, a minimal subtree of height h−1, and — since bf may be ±1 — a minimal subtree of height h−2:

N(h) = 1 + N(h−1) + N(h−2), with N(0) = 0, N(1) = 1

That is the Fibonacci recurrence with an offset: N(h) = Fib(h+2) − 1. Fibonacci numbers grow like φh, where φ ≈ 1.618, so N(h) grows exponentially in h — which is exactly what we needed. Inverting it:

h ≤ 1.44 log₂(n + 2) − 0.33

Worst case, an AVL tree is 44% taller than a perfect tree. Nothing in common use does better while still being maintainable.

The sparsest AVL trees

Read row by row: with 4 nodes you cannot be taller than 3 levels; with 7 you cannot be taller than 4.

05 — the repair primitive

A rotation changes the shape and preserves the order

before — right rotation about y
after — x has risen, y has sunk

Three pointer writes and two height updates:

  • x = y->left — the node that will rise.
  • y->left = x->right — x's right subtree changes parent.
  • x->right = y — y becomes x's child.

Then recompute the height of y first, then x — bottom-up, because x's height depends on y's.

Read the in-order traversal of both diagrams: A x B y C in each. A rotation cannot break the BST property, because it does not move any key past any other key. It only changes who is whose parent.

That is why rotation is the universal repair tool for binary search trees. Red-black trees use the identical operation. The only difference between the two structures is when they decide to apply it.

06 — the four cases

Two shapes, and their mirrors

When a node's balance factor reaches ±2, exactly one of four patterns caused it. The pattern is named by the two steps from the unbalanced node down towards the new key.

Left-Left — one right rotation

bf(z) = +2 and bf(y) ≥ 0

Left-Right — rotate left at y, then right at z

bf(z) = +2 and bf(y) < 0

How to decide, in two questions

  1. Is bf(z) greater than 1 or less than −1? That tells you which side is heavy.
  2. Does the heavy child lean the same way or the opposite way? Same way is a straight line — one rotation. Opposite way is a zig-zag — rotate the child first to straighten it, then rotate.

That is all four cases. RR and RL are LL and LR with every left swapped for right.

casebf(z)bf(child)fix
LL> 1≥ 0right rotate z
LR> 1< 0left rotate z.left, then right rotate z
RR< −1≤ 0left rotate z
RL< −1> 0right rotate z.right, then left rotate z

Note the = 0 boundary. A child with bf 0 can only arise during deletion — after an insertion the heavy child always leans. Handling it as the straight-line case is correct; forgetting it is the classic AVL deletion bug.

07 — insertion

Insert like a BST, then repair on the way out

  1. Descend and attach the new key exactly as in a plain BST. It always becomes a leaf.
  2. On the way back up the recursion, recompute each node's height.
  3. At the first node whose balance factor has reached ±2, apply the matching rotation from the case table.
  4. Stop. You are done.

Why step 4 works

Before the insertion, the subtree at the unbalanced node had some height h. The insertion made it h+1. The rotation puts it back to h — exactly what it was.

So every ancestor above sees a subtree of unchanged height, and no ancestor can have become unbalanced. One rotation, single or double, always suffices for an insertion.

This is a genuinely strong result and it is worth making a student prove the height claim on one case by hand before accepting it.

Cost of an insertion

stepcost
descend to the leafO(log n)
height updates on the way upO(log n)
rotations≤ 2

A "double rotation" is two single rotations, so LR and RL cost 2. LL and RR cost 1.

What is easy to get wrong

  • Updating heights before the recursive call instead of after. The child's height is not final until its own call returns.
  • Rotating and then forgetting to return the new subtree root to the parent's call frame.
  • Updating the rotated nodes' heights in the wrong order.

  • Insert 10, 20, 15 — the smallest tree that needs a double rotation.
  • Build a tall thin tree, then delete a single leaf on the short side and watch how far the repair travels.

Reading the balance factors

After every completed operation, every factor must be −1, 0 or +1. A ±2 is only ever a transient state inside an operation. If you ever see one here, the implementation is broken.

09 — deletion

Deletion is where the symmetry breaks

Deletion starts identically: remove the key as in a plain BST — leaf, single child, or replace with the in-order successor — then rebalance on the way back up.

The difference is what a rotation does to the subtree's height.

insertiondeletion
subtree height beforehh
after the operationh + 1h
after the rotationhh − 1
can the parent now be unbalanced?noyes

The rotation that fixes the child shortens it, which can unbalance the parent. So you must keep checking all the way to the root: a single deletion can cost O(log n) rotations.

In code this costs you nothing extra — you rebalance at every level on the way out regardless, and the loop simply does not terminate early. But the worst-case guarantee is materially weaker, and it is the main reason red-black trees exist.

The three removal cases

  • Leaf — detach and free it.
  • One child — splice the child into its place.
  • Two children — copy the in-order successor's key into this node, then recursively delete that successor from the right subtree. The successor has at most one child, so the recursion bottoms out immediately.

Identical to BST deletion. Everything AVL-specific happens after, in the rebalance.

The bf = 0 trap

After a deletion, the heavy child can have balance factor 0 — it cannot after an insertion. If your case test is written as bf(child) > 0 for the left case and you never consider the zero, you will take the double-rotation branch when you should take the single one, and silently corrupt the tree. Test for < 0 and treat everything else as the straight-line case.

10 — evidence, not assertion

Predict first, then run it

Real AVL and plain-BST implementations, running in this page. Write your prediction down before you press.

Before you press

  • How tall does the plain BST get on sorted input? On random input?
  • How many rotations does the AVL tree need for n sorted insertions?
  • What is the worst number of rotations for a single deletion?

The row that matters

"Most rotations in one operation" is the only row that is a guarantee rather than an average. Insertions are capped at 2. Deletions are not, and the measurement will show it — that single row is the entire argument for preferring a red-black tree in write-heavy code.

11 — implementation in C

The node, and four helpers that carry everything

#include <stdlib.h>
#include <limits.h>

/* convention: height(NULL) = 0, height(leaf) = 1 */

typedef struct Node {
    int           key;
    int           height;
    struct Node  *left, *right;
} Node;

static int height(Node *n)
{
    return n ? n->height : 0;
}

static int max_i(int a, int b)
{
    return a > b ? a : b;
}

static void update(Node *n)
{
    n->height = 1 + max_i(height(n->left), height(n->right));
}

static int balance(Node *n)
{
    return n ? height(n->left) - height(n->right) : 0;
}

Why height() is a function

Writing n->height directly works everywhere except the one place it matters — when n is NULL. Wrapping it removes every null check from the rest of the file, and null children are the common case at the bottom of the tree.

The same trick as the red-black sentinel, achieved with a function instead of an allocation.

Store the height, or the balance factor?

Storing the height costs an int but makes every update a one-liner. Storing the balance factor needs only two bits, but every rotation has to derive the new factors by case analysis, which is fiddly and easy to get wrong.

Production implementations store the factor to save space. Learn it with the height, get it correct, then optimise if you ever actually need to.

No parent pointers. The recursion carries the path for you, and each call returns the new root of its subtree — which is how a rotation gets reattached without ever needing Node **.

12 — implementation in C

Rotations, and the single rebalance routine

static Node *right_rotate(Node *y)
{
    Node *x  = y->left;
    Node *t2 = x->right;

    x->right = y;
    y->left  = t2;

    update(y);          /* y first: x depends on it */
    update(x);
    return x;           /* new subtree root */
}

static Node *left_rotate(Node *x)
{
    Node *y  = x->right;
    Node *t2 = y->left;

    y->left  = x;
    x->right = t2;

    update(x);
    update(y);
    return y;
}
/* recompute height, fix this node if it has
   drifted to +-2, return the new subtree root */
static Node *rebalance(Node *n)
{
    update(n);
    int b = balance(n);

    if (b > 1) {                        /* left heavy  */
        if (balance(n->left) < 0)       /* LR: zig-zag */
            n->left = left_rotate(n->left);
        return right_rotate(n);         /* LL          */
    }
    if (b < -1) {                       /* right heavy */
        if (balance(n->right) > 0)      /* RL: zig-zag */
            n->right = right_rotate(n->right);
        return left_rotate(n);          /* RR          */
    }
    return n;                           /* already fine */
}

All four cases in twelve lines, and both insert and delete call this same function. Write it once, test it once, and the rest of the implementation is ordinary BST code.

The < 0 and > 0 tests are the boundary discussed earlier: balance factor 0 on the heavy child falls through to the single-rotation branch, which is what deletion requires.

13 — implementation in C

Insert and delete

/* returns the new root of this subtree */
Node *avl_insert(Node *n, int key)
{
    if (!n) {
        Node *z = malloc(sizeof *z);
        if (!z) return NULL;
        z->key    = key;
        z->height = 1;
        z->left   = z->right = NULL;
        return z;
    }

    if      (key < n->key) n->left  = avl_insert(n->left,  key);
    else if (key > n->key) n->right = avl_insert(n->right, key);
    else                   return n;      /* duplicate */

    return rebalance(n);
}

Node *avl_search(Node *n, int key)
{
    while (n && n->key != key)
        n = key < n->key ? n->left : n->right;
    return n;
}

Call it as root = avl_insert(root, key);. The assignment is what reattaches a rotated subtree — miss it and the tree silently loses everything below the rotation.

static Node *min_node(Node *n)
{
    while (n->left) n = n->left;
    return n;
}

Node *avl_delete(Node *n, int key)
{
    if (!n) return NULL;

    if (key < n->key) {
        n->left  = avl_delete(n->left,  key);
    } else if (key > n->key) {
        n->right = avl_delete(n->right, key);
    } else {
        if (!n->left || !n->right) {      /* 0 or 1 child */
            Node *c = n->left ? n->left : n->right;
            free(n);
            return c;                     /* may be NULL  */
        }
        Node *s = min_node(n->right);     /* 2 children   */
        n->key   = s->key;
        n->right = avl_delete(n->right, s->key);
    }

    return rebalance(n);
}

Every return path from the found-it branch either returns a replacement subtree or falls through to rebalance. That single exit point is why deletion needs no extra rotation logic — the cascade happens automatically as each recursive frame returns.

14 — prove it works

The validator checks the stored heights too

A broken AVL tree still answers searches correctly for a long time. The stale-height bug is the one that hides.

/* returns the true height; sets *ok = 0 on any fault */
static int check(Node *n, long lo, long hi, int *ok)
{
    if (!n) return 0;

    if (n->key <= lo || n->key >= hi)      /* BST order */
        *ok = 0;

    int l = check(n->left,  lo, n->key, ok);
    int r = check(n->right, n->key, hi, ok);

    if (l - r > 1 || r - l > 1)             /* AVL balance */
        *ok = 0;

    int h = 1 + max_i(l, r);
    if (n->height != h)                     /* stored height */
        *ok = 0;

    return h;
}

int avl_valid(Node *root)
{
    int ok = 1;
    check(root, LONG_MIN, LONG_MAX, &ok);
    return ok;
}
#define N 20000

int main(void)
{
    Node *root = NULL;
    char *present = calloc(N, 1);
    srand(12345);

    for (int op = 0; op < 500000; op++) {
        int k = rand() % N;

        if (rand() & 1) {
            root = avl_insert(root, k);
            present[k] = 1;
        } else {
            root = avl_delete(root, k);
            present[k] = 0;
        }
        assert(avl_valid(root));
        assert((avl_search(root, k) != NULL) == (present[k] != 0));
    }
    puts("ok");
    return 0;
}

Build it like this:

gcc -Wall -Wextra -O2 -fsanitize=address,undefined avl.c -o avl

The three assertions in check map onto the three things that can go wrong: the ordering, the balance rule, and the bookkeeping. Most real bugs show up as the third one first — a height that was never recomputed after a rotation.

15 — choosing

When AVL is the right answer, and when it is not

plain BSTAVLred-black
Worst-case heightn1.44 log₂ n2 log₂ n
Extra per nodenoneheight (int) or 2 bits1 bit
Rotations per insert0≤ 2≤ 2
Rotations per delete0O(log n)≤ 3
Repairs without pointer writes—neverusually (recolouring)
Lookup speedunpredictablefastestslightly slower
Best fornothing in productionread-heavy workloadswrite-heavy workloads

Where AVL wins

  • The tree is built once and queried many times — a lookup table, a static index, a symbol table after parsing.
  • Lookup latency matters more than insert latency.
  • You want the shortest possible tree and can afford the writes.

Where it loses

  • Frequent deletions — the O(log n) rotation cascade is unbounded per operation.
  • Shared under a lock — every rotation is a pointer write and therefore contention.
  • Data larger than memory — neither AVL nor red-black helps there; that is what B-trees are for.

In an interview, "AVL is faster" and "red-black is faster" are both wrong answers. The right one is AVL is shallower so it reads faster; red-black bounds the repair cost so it writes faster. The choice follows the read/write ratio, not a preference.

16 — what to do next

Exercises

Write the prediction down first

  1. Before running anything: inserting 1…7 into an empty AVL tree, how many rotations occur and what is the final root? Instrument both rotate functions and check.
  2. Construct by hand the smallest AVL tree that requires a double rotation on insertion. Then the smallest that requires one on deletion.
  3. Implement avl_insert, avl_search and avl_valid. Do not write deletion until the validator survives 10⁵ random insertions.
  4. Implement avl_delete and run the differential harness under AddressSanitizer.
  5. Deliberately break the balance(n->left) < 0 test into <= 0 and find the shortest delete sequence that corrupts the tree. This teaches the boundary better than reading about it.
  6. Measure: for 10⁵ mixed operations, report total rotations and the maximum rotations in any single operation, split between inserts and deletes. Explain the two numbers.
  7. Build an AVL tree of height 10 with the minimum possible number of nodes. Verify it against N(h) = Fib(h+2) − 1.
  8. Add a size field to each node maintained through rotations, then implement select(k) — the k-th smallest key — in O(log n). This is the standard follow-up interview question.

Where AVL trees actually appear

  • Windows NT's process address space descriptors.
  • Several in-memory database indexes where reads dominate overwhelmingly.
  • Teaching and interviews — far more than production, honestly. Most standard libraries ship red-black trees.

That is not a reason to skip it. AVL is where rotations, height maintenance and the recursive rebuild pattern are easiest to see clearly, and every later balanced structure reuses those ideas. Learn it properly here and red-black deletion stops looking like magic.

The one-sentence summary

Keep every node's two subtree heights within one of each other, repair with rotations on the way out of the recursion, and the tree can never exceed 1.44 log₂ n.
