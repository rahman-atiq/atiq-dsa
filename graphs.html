Graphs

Everything the tree decks assumed away: more than one parent, more than one path, and cycles. Almost nothing in the real world is a tree.

A tree is a graph with two extra restrictions. Drop them and the data structure stops being about hierarchy and starts being about relationships. Arrow keys, or the buttons below, to move through the deck.

01 — why trees are not enough

A tree is a graph with three things forbidden

Every tree in the previous decks quietly enforced three rules, and every one of them is wrong about the world:

  • One parent per node. But a file belongs to two projects, a person has two parents, a module is imported by five others.
  • No cycles. But roads loop, friendships are mutual, and package A can depend on B which depends on A — which is precisely the bug you need to detect.
  • Exactly one path between any two nodes. But there are many routes from Manchester to Leeds, and the interesting question is which one is shortest.

Remove those restrictions and you have a graph: a set of vertices and a set of edges between them. That is the whole definition, and it is deliberately almost empty — which is why nearly every interesting computational problem can be phrased as one.

A binary search tree answers "where is this key?". A graph answers "how are these things connected, and what is the best way through?".

Two bounds worth memorising, because every complexity result in this deck is stated in terms of them:

In a simple undirected graph, |E| ≤ |V|(|V|−1)/2. In a directed one, |E| ≤ |V|(|V|−1). So |E| is somewhere between 0 and roughly |V|², and "O(V + E)" can mean anything from linear to quadratic depending on which end you are at.

Most real graphs are sparse. Road networks have degree about 4. Social graphs have a few hundred edges per vertex out of billions of possible ones. That fact drives the next two slides.

03 — the first real decision

Adjacency matrix: a V × V grid of yes or no

Allocate a two-dimensional array and set m[u][v] = 1 when the edge exists. For an undirected graph the matrix is symmetric; for a weighted one, store the weight instead of 1.

What it is good at

  • "Is there an edge u→v?" — one array lookup, O(1). Nothing else matches this.
  • Adding or removing an edge — O(1).
  • Simple to write, impossible to get subtly wrong.

What it is bad at

  • Space is O(V²) whatever |E| is. A million vertices needs 10¹² entries — a terabyte to store a graph that might have four edges per vertex.
  • Listing a vertex's neighbours costs O(V), because you must scan the whole row including the zeros. Every traversal does this for every vertex, so BFS and DFS become O(V²).

The demo graph as a matrix

64 cells, 22 of them set. Already 66% waste at eight vertices, and the waste grows with V.

Use a matrix when the graph is dense, when V is small and fixed, or when your algorithm's inner loop is "does this edge exist?" — Floyd-Warshall, for instance, wants a matrix.

04 — the first real decision

Adjacency list: each vertex keeps its own neighbours

An array of V lists. adj[u] holds exactly the vertices u has an edge to — nothing else is stored.

What it is good at

  • Space is O(V + E), which for a sparse graph is a rounding error next to O(V²).
  • Iterating a vertex's neighbours is O(degree), which is what every traversal actually wants. BFS and DFS become O(V + E).

What it is bad at

  • "Is there an edge u→v?" costs O(degree(u)) — you have to search the list.
  • Removing an edge means finding it first.
  • Pointer chasing, so worse cache behaviour than a matrix at small V.

This is the default. Unless you know your graph is dense or you need O(1) edge queries, use an adjacency list.

The same graph as lists

22 entries, because each undirected edge appears twice — once in each endpoint's list. That doubling is why the space bound is O(V + 2E), which we write as O(V + E).

A linked-list implementation that prepends will produce neighbours in reverse insertion order. That changes the order BFS and DFS visit things — not their correctness, but it will make your output differ from the textbook's, and students lose hours to that.

05 — choosing between them

The rule of thumb

The matrix wins on space only when E is within a constant factor of V² — that is, when the graph is genuinely dense. In practice that almost never happens above a few thousand vertices.

A matrix on a graph with 10⁵ vertices and average degree 6 wastes about 99.99% of its memory, and slows every traversal down by four orders of magnitude. Try the numbers.

06 — the central idea

BFS and DFS are the same algorithm with a different container

Write the generic traversal once:

put the start vertex in the container
while the container is not empty:
    take a vertex u out
    if u is already visited: skip it
    mark u visited
    for each neighbour v of u:
        if v is not visited: put v in the container

Now choose the container.

  • Queue — first in, first out. You finish everything one step away before looking two steps away. That is breadth-first search.
  • Stack — last in, first out. You follow one path as deep as it goes before backing up. That is depth-first search.
  • Priority queue keyed by distance — you take the cheapest known vertex next. That is Dijkstra.

Three of the most important graph algorithms differ only in which data structure holds the frontier. Teach this once and BFS, DFS and Dijkstra stop being three things to memorise.

The two rules that stop it looping forever

  1. Mark visited. A graph has cycles; without a visited array the loop never terminates. This is the single difference from tree traversal, and it is the whole difference.
  2. Mark on the way in, not the way out. For BFS, mark a vertex when you enqueue it, not when you dequeue it. Otherwise the same vertex is enqueued once per incoming edge and the queue blows up.

Cost

Each vertex enters the container at most once and each edge is examined at most twice (once from each end), so with an adjacency list both traversals are

O(V + E) time, O(V) extra space.

With a matrix, the neighbour loop costs O(V) instead of O(degree), and the whole thing degrades to O(V²).

07 — breadth-first search

BFS explores in layers, and that gives you shortest paths for free

Because the queue empties in the order things arrived, BFS finishes every vertex at distance 1 before touching any at distance 2. The moment you first reach a vertex, you have reached it by the fewest possible edges.

In an unweighted graph, BFS from s computes the shortest-path distance from s to every reachable vertex, in O(V + E). No priority queue, no Dijkstra, nothing cleverer required.

Keep a dist[] array instead of a separate visited[]: initialise it to −1, and "not yet visited" is just "distance is still −1". One array does both jobs.

Keep a parent[] array as well and you can reconstruct the actual route, not merely its length, by walking backwards from the destination.

What BFS gives you

  • Shortest path in an unweighted graph.
  • Connected components — run it from every unvisited vertex and count the runs.
  • Bipartite testing — two-colour by layer parity; an edge inside a layer means not bipartite.
  • The "six degrees of separation" family of problems, verbatim.

Watch out for

Weighted graphs. BFS counts edges, not weights. On a weighted graph it will confidently return the route with fewest hops, which may be far from the cheapest. That is what Dijkstra is for.

Disconnected graphs. One BFS only reaches one component. If the task is "visit everything", wrap it in a loop over all vertices.

Queue sizing. With mark-on-enqueue, each vertex enters at most once, so an array of V is exactly enough and you never need a dynamic structure.

08 — depth-first search

DFS goes as deep as it can, and the order it backs out is the useful part

DFS is usually written recursively, because the call stack already is the stack:

  • Mark u visited.
  • For each unvisited neighbour, recurse.
  • Return.

The subtlety is that DFS has two natural moments to do work: when you first arrive at a vertex, and when you finish with it. A surprising number of algorithms depend on the second one.

Edge classification

Colour each vertex white (untouched), grey (entered, not finished) or black (finished). Then for an edge u→v:

  • v is white — a tree edge, part of the DFS forest.
  • v is grey — a back edge. You have found an ancestor, which means you have found a cycle.
  • v is black — a forward or cross edge; harmless.

"Grey means cycle" is the entire directed cycle-detection algorithm, and it falls out of DFS at no extra cost.

Recursive or iterative?

Recursive is shorter and clearer. It also overflows the stack on a graph with a long path — a million-vertex chain will crash. If the graph is large or adversarial, write the iterative version.

They are not identical. The naive iterative version pushes all neighbours then pops the last one, so it visits neighbours in reverse order compared with the recursive version. Both are valid depth-first traversals; only one matches the textbook's printed output.

Also note the iterative stack can hold the same vertex several times before it is visited, so size it by E, not V.

What DFS gives you

  • Cycle detection, directed and undirected.
  • Topological sort, by reversed finish order.
  • Connected components, and strongly connected components via Tarjan or Kosaraju.
  • Bridges and articulation points.
  • Maze and puzzle solving, backtracking search.

09 — watch them run

Same graph, same start, different container

What to watch

  • The container line. BFS takes from the front, DFS from the back — that is the only difference in the code.
  • BFS distances increase monotonically in visit order. DFS distances jump around.
  • Both visit every vertex exactly once and produce a spanning tree of the component — different trees, same vertices.

Predict before you step

Pick a start vertex and write down the full visit order for both before pressing anything. Getting BFS right is easy; getting DFS right requires you to know which neighbour the implementation takes first, which is exactly the detail people skip.

10 — what traversal buys you

Four problems that are one traversal with bookkeeping

Connected components

Loop over every vertex. If it is unvisited, run a traversal from it and stamp everything reached with the same component id. Increment the id and continue.

The number of traversals you started is the number of components. O(V + E) total — the loop does not make it quadratic, because each vertex is visited once across all runs.

Cycle detection

Directed — DFS with colours. An edge to a grey vertex is a back edge, and a back edge is a cycle.

Undirected — DFS tracking each vertex's parent. An edge to a visited vertex that is not your parent is a cycle. Forgetting the parent check means every single edge reports a false cycle.

Bipartite testing (two-colouring)

BFS from each unvisited vertex, colouring each layer alternately. If you ever find an edge joining two vertices of the same colour, the graph is not bipartite.

Equivalently: a graph is bipartite exactly when it contains no odd-length cycle. Scheduling conflicts and matching problems reduce to this.

Shortest path, unweighted

BFS, recording dist and parent. Walk the parent chain backwards from the target to recover the route.

If every edge has the same weight, reaching for Dijkstra here is a mistake — it is slower and adds a heap you do not need.

The pattern is worth naming out loud for a student: none of these is a new algorithm. Each is "run a traversal, and record one extra thing while you do it."

11 — ordering a dependency graph

Topological sort: which order can I do these in?

Given a DAG, produce an ordering of the vertices such that every edge points forwards. Build systems, course prerequisites, spreadsheet recalculation, task schedulers and package managers are all this one problem.

Kahn's algorithm — repeatedly take what is ready

  1. Compute the in-degree of every vertex.
  2. Put every vertex with in-degree 0 into a queue — these have no unmet prerequisites.
  3. Take one out, append it to the output, and decrement the in-degree of each of its successors. Any that reach 0 join the queue.
  4. If the output contains fewer than V vertices, the graph has a cycle and no ordering exists.

Step 4 is free cycle detection, and it is more useful than a yes/no: the vertices missing from the output are exactly the ones tangled in the cycle, which is what you want to print in the error message.

The DFS alternative

Run DFS and push each vertex onto a list when it finishes. Reverse the list. It works because a vertex can only finish after everything it depends on has finished — but it gives you no natural place to report which vertices formed the cycle.

a small DAG of module prerequisites

Topological order is usually not unique. Any vertex with in-degree 0 is a legal next choice, so a graph with several roots has several valid answers. If your test compares against one expected string, the test is wrong — validate the property instead: for every edge u→v, position(u) < position(v).

12 — weights change everything

Shortest paths: pick the right algorithm, not the famous one

Why Dijkstra breaks on negative edges

Dijkstra's correctness rests on one assumption: once you pull a vertex out of the priority queue, its distance is final, because every other route to it must go through something already more expensive.

A negative edge destroys that. A longer-looking route can suddenly become cheaper later, and Dijkstra has already committed and moved on.

Dijkstra on a graph with a negative edge does not crash or loop — it returns a confidently wrong answer. That is a far worse failure mode, and it is why "are the weights non-negative?" is the first question to ask.

Where negative weights actually come from

  • Currency arbitrage — a negative cycle is the profit opportunity you are searching for.
  • Net cost models where some steps earn a rebate.
  • Reductions from other problems that map "gain" to a negative edge.

If none of these applies, your weights are non-negative and Dijkstra is correct.

Beyond the syllabus, worth knowing the names

Minimum spanning tree (Kruskal with union-find, Prim with a heap), strongly connected components (Tarjan, Kosaraju), A* for pathfinding with a heuristic, and Dinic’s algorithm for flow. Maximum flow itself is covered later in this deck. All of them sit on top of what is here.

13 — dijkstra

Dijkstra: always expand the cheapest vertex you know about

Every vertex carries a tentative distance — the best route found so far. All start at infinity except the source, which starts at 0.

Then repeat: take the unsettled vertex with the smallest tentative distance, declare it settled, and relax each of its outgoing edges.

relax(u, v, w):
    if dist[u] + w < dist[v]:
        dist[v]   = dist[u] + w
        parent[v] = u

Relaxation is the only thing that ever changes a distance, and it appears verbatim in Bellman-Ford and Floyd-Warshall too. The algorithms differ entirely in the order they relax edges.

The invariant that makes it correct

When a vertex is settled, its distance is final. Any other route to it would have to leave the settled set through some unsettled vertex, and that vertex already has a distance at least as large — so the route cannot be shorter.

Read that argument again and notice where it uses non-negative weights. It is the only place, and removing the assumption breaks everything.

The cost depends entirely on the queue

"take the cheapest" implemented astotaluse when
linear scan of an arrayO(V²)dense graphs, small V, or when you want short code
binary heapO((V+E) log V)the default; sparse graphs
Fibonacci heapO(E + V log V)theory; the constants rarely pay off in practice

The practical detail nobody mentions

A binary heap has no efficient "decrease-key". Real implementations do not bother: they push a duplicate with the better distance and skip stale entries on pop.

Item it = pop();
if (it.d > dist[it.v]) continue;   /* stale */

The heap can now hold up to E entries instead of V, which is why the bound is written O((V+E) log V). Size the array accordingly or you will overflow it on a dense graph.

15 — negative weights

Bellman-Ford: stop being clever about the order

Dijkstra's speed comes from knowing which edge to relax next. If negative weights make that knowledge unreliable, give it up entirely and relax every edge, repeatedly.

Do V − 1 passes. In each pass, relax all E edges in any order.

Why V − 1 passes is exactly enough

A shortest path in a graph with no negative cycle is simple — it never repeats a vertex — so it has at most V − 1 edges.

Now the induction: after pass 1, every shortest path using one edge is correct. After pass 2, every one using two edges is correct, because its final edge is relaxed from a vertex whose distance was already settled by pass 1. After pass k, all paths of k edges are right. So V − 1 passes finish the job.

Negative cycle detection comes free

Run one more pass. If any distance still improves, there is no shortest path at all — you have found a cycle you could go round forever, getting cheaper each time.

Cost

O(V · E). On a sparse graph with 10⁵ vertices that is roughly 10¹¹ operations against Dijkstra's 10⁶. Use it only when you have to.

The early exit that matters in practice

If a whole pass changes nothing, no later pass can change anything either — return immediately. On most real graphs this triggers after a handful of passes rather than V − 1, which turns the worst case into something usable.

Where it is actually used

  • Routing protocols. RIP is distance-vector routing, which is Bellman-Ford run in a distributed way across routers.
  • Currency arbitrage. Take −log of each exchange rate; a negative cycle is a sequence of trades that returns more than you started with.
  • Difference constraints. Systems of inequalities of the form xj − xi ≤ w become a graph, and Bellman-Ford either solves them or proves them infeasible.

SPFA is a queue-based refinement that is much faster on average and still O(V·E) in the worst case. Worth knowing it exists; not worth reaching for first.

16 — all pairs

Floyd-Warshall: three loops, and the outer one is the algorithm

Sometimes you want the distance between every pair, not from one source. Running Dijkstra V times works and costs O(V(V+E) log V). For a dense graph there is something simpler and often faster.

Define dk[i][j] as the shortest route from i to j allowed to pass through only the vertices {0 … k} as intermediates. Then:

dk[i][j] = min( dk−1[i][j] , dk−1[i][k] + dk−1[k][j] )

Either the route does not use k at all, or it goes i → k → j. There is no third option, and that is the entire derivation.

Because each layer only reads the one below it, you can drop the k index and update the matrix in place.

for k in 0..n-1:            # MUST be the outer loop
    for i in 0..n-1:
        for j in 0..n-1:
            d[i][j] = min(d[i][j], d[i][k] + d[k][j])

The bug everyone writes once

Putting k innermost. The code compiles, runs, and returns plausible-looking numbers that are wrong, because you are no longer building up the set of permitted intermediates in order.

If you ever have to debug someone's Floyd-Warshall, check the loop order first. It is nearly always that.

Cost and character

  • O(V³) time, O(V²) space, with a tiny constant factor — it is three tight loops over a contiguous array and the cache loves it.
  • Handles negative edges. d[i][i] < 0 afterwards means vertex i sits on a negative cycle.
  • Practical up to roughly V = 1000. Beyond that, V³ stops being a small number.

Use INF carefully

Initialise unreachable pairs to INT_MAX / 4, not INT_MAX. The inner line adds two of them together, and INT_MAX + INT_MAX is undefined behaviour that will quietly produce a negative distance.

17 — a different question

Maximum flow: how much can you push through the pipes?

Shortest path asks for the best single route. Max flow asks something else entirely: using all the routes at once, how much can get from source to sink?

A flow network is a directed graph where each edge carries a capacity c(u,v) ≥ 0, plus two distinguished vertices: a source s and a sink t.

A flow assigns a number f(u,v) to each edge subject to two rules:

  1. Capacity. 0 ≤ f(u,v) ≤ c(u,v). You cannot push more through a pipe than it holds.
  2. Conservation. For every vertex except s and t, flow in equals flow out. Nothing accumulates and nothing appears from nowhere.

The value of the flow is the net amount leaving s. Maximise it.

Notice there is no notion of distance here. An edge's length is irrelevant; only its capacity matters. This is why max flow is not a shortest-path problem wearing a hat — it is a genuinely different structure.

18 — the key idea

Greedy fails, and the fix is an edge that lets you change your mind

The obvious algorithm: find any path from s to t with spare capacity, push as much as it takes, repeat. It is wrong, and the counterexample is small.

capacities shown on each edge

Push 1 unit along S → A → B → T first. Then fill S → A → T with 9 more and S → B → T with 9 more, and greedy stops at 19. One unit of S→A and one of B→T sit stranded, unreachable because the single unit committed to the middle edge cannot be taken back. The true maximum is 20.

The problem is not the path you chose. It is that having chosen it, you have no way to partially undo it.

The residual graph

Keep, alongside the network, a residual capacity for every ordered pair:

  • Forward: cf(u,v) = c(u,v) − f(u,v) — how much more you could push.
  • Backward: cf(v,u) = f(u,v) — how much you could take back.

That backward edge is the whole trick. Pushing flow along it does not mean sending water uphill; it means cancelling flow you previously committed on the forward edge, and rerouting it somewhere better. On the network to the left, the residual edge B → A lets you route S → B → A → T, which cancels the one unit on A→B and frees both stranded units at once.

An augmenting path is any path from s to t in the residual graph. Its bottleneck is the smallest residual capacity along it. Push that much, update both directions, repeat until no augmenting path exists.

Why "no augmenting path" means "done"

If you cannot reach t from s in the residual graph, then the set of vertices you can reach forms a barrier. Every edge crossing out of it is completely saturated — otherwise it would have residual capacity and you could have crossed. That barrier is a cut, and the next slides show it is a minimum one.

19 — choosing the path

Ford-Fulkerson leaves a choice open. Edmonds-Karp closes it.

Ford-Fulkerson is the method: while an augmenting path exists, augment along it. It deliberately does not say which path, and that omission is expensive.

What goes wrong

Take the network on the previous slide, but with the outer capacities set to 1,000,000 and the middle edge still 1. An adversary who always hands you a path through the middle edge makes you augment by one unit at a time — two million iterations for a graph with four vertices.

Ford-Fulkerson with arbitrary path choice is O(E · |f*|) — proportional to the answer's magnitude, not the graph's size. With irrational capacities it can fail to terminate at all.

The fix

Edmonds-Karp is Ford-Fulkerson with one rule added: always choose a shortest augmenting path, measured in number of edges. Which means: find it with BFS.

That one line makes the running time O(V · E²) — independent of the capacities entirely. On the two-million-iteration example above, BFS finds the two-edge paths first and finishes in two augmentations.

Why shortest paths bound the work

Each augmentation saturates at least one edge on the path. The distance from s to any vertex in the residual graph never decreases as the algorithm runs, and a saturated edge cannot reappear until that distance has grown by at least 2.

So each edge can be the bottleneck at most O(V) times, giving O(V·E) augmentations, each costing O(E) for the BFS.

Write Edmonds-Karp. It is about forty lines, it is correct, and its bound does not depend on how large your numbers are. Reach for Dinic's only when you have measured that you need it.

20 — the theorem

Max-flow min-cut: the answer and its proof are the same object

An s-t cut is a split of the vertices into two sets, S containing the source and T containing the sink. Its capacity is the total capacity of the edges going from S to T — the edges you would have to sever to disconnect them.

Two observations, one easy and one not:

  • Every flow is at most every cut's capacity. Anything reaching t must cross the cut, so the cut is a ceiling. This direction is obvious once stated.
  • The maximum flow exactly equals the minimum cut. That is the theorem, and it is not obvious at all.

max flow = min cut. When the two meet, each one certifies the other: you cannot push more, and here is the bottleneck that proves it.

You already computed the cut

When Edmonds-Karp stops, run one final BFS on the residual graph from s. Let S be everything it reaches. Every original edge from S to T must be saturated — if any had spare capacity, the BFS would have crossed it.

So the minimum cut is: the original edges leaving the residual-reachable set. Three extra lines of code after the main loop.

Why the cut is often the real answer

The flow value is a number. The cut is a list of specific edges — and that is usually what somebody actually wanted:

  • "Which links do I upgrade to increase throughput?" — the ones in the min cut. Upgrading anything else changes nothing.
  • "Where is this network most fragile?" — the min cut is the cheapest set of failures that disconnects it.
  • "Which pixels are foreground?" — in image segmentation, the min cut is the boundary.
  • "Which projects do I fund?" — the S side of the min cut in the project-selection reduction.

A student who can compute max flow but cannot extract the cut has done most of the work and stopped just before the useful part.

22 — reductions

Problems that are secretly max flow

Bipartite matching

Given applicants and jobs, and who is qualified for what, assign as many people as possible without double-booking anyone.

The reduction: add a super-source connected to every applicant with capacity 1, a super-sink fed by every job with capacity 1, and capacity 1 on each qualification edge. Max flow equals the size of the maximum matching, and the saturated middle edges are the matching.

The capacity-1 constraint on the source edges is what enforces "one job per person" — the conservation rule does the rest.

Edge-disjoint paths

How many routes from s to t share no edge? Set every capacity to 1 and compute the max flow. The answer is the flow value, and decomposing the flow gives you the actual routes.

This is Menger's theorem, and it is how you answer "how many simultaneous link failures can this network survive?".

Project selection

Each project earns a profit and requires some equipment, each with a cost. Equipment is shared. Which subset of projects maximises net profit?

Source → each project with capacity = its profit; each equipment → sink with capacity = its cost; project → equipment with infinite capacity. The min cut partitions into "fund it" and "do not", and the answer is total profit minus the min cut.

Image segmentation

Each pixel is a vertex. Source and sink represent foreground and background; edge capacities encode how strongly each pixel resembles each, and neighbouring pixels are joined by edges that penalise splitting them apart.

The minimum cut is the segmentation boundary. This is the basis of GrabCut and a large amount of classical computer vision.

The skill worth teaching here is not the algorithm — it is recognising the shape. "Assign at most one of these to each of those" is almost always bipartite matching. "Partition into two groups, paying for the boundary" is almost always min cut.

23 — implementation in C

The representation

#include <stdlib.h>
#include <limits.h>

#define MAXV 1024

typedef struct Edge {
    int          to;
    int          weight;
    struct Edge *next;
} Edge;

typedef struct {
    int   n;            /* number of vertices  */
    int   directed;
    Edge *adj[MAXV];    /* adj[u] = list head  */
} Graph;

void graph_init(Graph *g, int n, int directed)
{
    g->n        = n;
    g->directed = directed;
    for (int i = 0; i < n; i++)
        g->adj[i] = NULL;
}

int graph_add_edge(Graph *g, int u, int v, int w)
{
    Edge *e = malloc(sizeof *e);
    if (!e) return 0;
    e->to = v; e->weight = w;
    e->next = g->adj[u];
    g->adj[u] = e;                  /* prepend */

    if (!g->directed) {
        Edge *f = malloc(sizeof *f);
        if (!f) return 0;
        f->to = u; f->weight = w;
        f->next = g->adj[v];
        g->adj[v] = f;              /* the other direction */
    }
    return 1;
}

Read the undirected case carefully

An undirected edge is stored as two directed edges. That is why |E| undirected edges cost 2|E| list nodes, and why every traversal examines each edge twice.

The commonest beginner bug in this file is adding only one direction and then wondering why the graph is half-connected.

Prepending makes graph_add_edge O(1), at the cost of neighbours coming out in reverse insertion order. Correct, but your traversal output will not match a textbook that appends. If that matters, append instead and keep a tail pointer.

Iterating, everywhere in this deck

for (Edge *e = g->adj[u]; e; e = e->next) {
    int v = e->to;
    /* ... */
}

Every algorithm that follows uses exactly this loop. If you write a graph_free that walks the same lists and frees them, you have the whole memory story covered.

24 — implementation in C

BFS, with an explicit queue

/* dist[] doubles as the visited marker:
   -1 means not yet reached                  */
void bfs(Graph *g, int s, int *dist, int *parent)
{
    int queue[MAXV], head = 0, tail = 0;

    for (int i = 0; i < g->n; i++) {
        dist[i]   = -1;
        parent[i] = -1;
    }

    dist[s] = 0;
    queue[tail++] = s;

    while (head < tail) {
        int u = queue[head++];

        for (Edge *e = g->adj[u]; e; e = e->next) {
            if (dist[e->to] == -1) {        /* first time seen */
                dist[e->to]   = dist[u] + 1;
                parent[e->to] = u;
                queue[tail++] = e->to;      /* mark on ENQUEUE */
            }
        }
    }
}
/* walk the parent chain backwards from t */
int path_to(int *parent, int s, int t, int *out)
{
    int len = 0;
    for (int v = t; v != -1; v = parent[v]) {
        out[len++] = v;
        if (v == s) break;
    }
    if (out[len - 1] != s) return 0;        /* unreachable */

    for (int i = 0; i < len / 2; i++) {     /* reverse */
        int tmp = out[i];
        out[i] = out[len - 1 - i];
        out[len - 1 - i] = tmp;
    }
    return len;
}

/* visit every component, not just one */
void bfs_all(Graph *g, int *comp)
{
    int dist[MAXV], parent[MAXV], c = 0;

    for (int i = 0; i < g->n; i++) comp[i] = -1;

    for (int s = 0; s < g->n; s++) {
        if (comp[s] != -1) continue;
        bfs(g, s, dist, parent);
        for (int i = 0; i < g->n; i++)
            if (dist[i] != -1 && comp[i] == -1) comp[i] = c;
        c++;
    }
}

A circular buffer is unnecessary here. With mark-on-enqueue each vertex is added exactly once, so head and tail never exceed V and a plain array is both correct and faster.

25 — implementation in C

DFS, both ways, and cycle detection

void dfs(Graph *g, int u, int *visited)
{
    visited[u] = 1;
    /* pre-order work for u goes here */

    for (Edge *e = g->adj[u]; e; e = e->next)
        if (!visited[e->to])
            dfs(g, e->to, visited);

    /* post-order work for u goes here  */
}

/* iterative: stack may hold duplicates,
   so size it by edges, not vertices    */
void dfs_iter(Graph *g, int s, int *visited)
{
    int stack[MAXE], top = 0;
    stack[top++] = s;

    while (top > 0) {
        int u = stack[--top];
        if (visited[u]) continue;
        visited[u] = 1;

        for (Edge *e = g->adj[u]; e; e = e->next)
            if (!visited[e->to])
                stack[top++] = e->to;
    }
}
enum { WHITE, GREY, BLACK };

/* directed: an edge into a GREY vertex is a
   back edge, and a back edge is a cycle      */
static int cyclic_from(Graph *g, int u, int *colour)
{
    colour[u] = GREY;

    for (Edge *e = g->adj[u]; e; e = e->next) {
        if (colour[e->to] == GREY) return 1;
        if (colour[e->to] == WHITE &&
            cyclic_from(g, e->to, colour)) return 1;
    }

    colour[u] = BLACK;
    return 0;
}

int graph_has_cycle(Graph *g)
{
    int colour[MAXV];
    for (int i = 0; i < g->n; i++) colour[i] = WHITE;

    for (int u = 0; u < g->n; u++)
        if (colour[u] == WHITE && cyclic_from(g, u, colour))
            return 1;
    return 0;
}

For an undirected graph this is wrong as written — every edge looks like a back edge to your own parent. Pass the parent down and skip it: if (e->to == parent) continue;. Handle multi-edges separately if your graph allows them.

26 — implementation in C

Topological sort and Dijkstra

/* Kahn. returns 1 on success, 0 if cyclic */
int topo_sort(Graph *g, int *out)
{
    int indeg[MAXV] = {0};
    int queue[MAXV], head = 0, tail = 0, count = 0;

    for (int u = 0; u < g->n; u++)
        for (Edge *e = g->adj[u]; e; e = e->next)
            indeg[e->to]++;

    for (int u = 0; u < g->n; u++)
        if (indeg[u] == 0) queue[tail++] = u;

    while (head < tail) {
        int u = queue[head++];
        out[count++] = u;

        for (Edge *e = g->adj[u]; e; e = e->next)
            if (--indeg[e->to] == 0)
                queue[tail++] = e->to;
    }

    return count == g->n;     /* short means a cycle */
}

When this returns 0, the vertices not in out are exactly those on or downstream of a cycle. Print them — "circular dependency involving A, B, C" is a far better error than "cycle detected".

/* O(V^2) Dijkstra: no heap, fine for dense
   graphs and short enough to get right     */
void dijkstra(Graph *g, int s, int *dist)
{
    int done[MAXV] = {0};

    for (int i = 0; i < g->n; i++) dist[i] = INT_MAX;
    dist[s] = 0;

    for (int it = 0; it < g->n; it++) {
        int u = -1;
        for (int i = 0; i < g->n; i++)          /* pick cheapest */
            if (!done[i] && dist[i] != INT_MAX &&
                (u == -1 || dist[i] < dist[u]))
                u = i;

        if (u == -1) break;                     /* rest unreachable */
        done[u] = 1;

        for (Edge *e = g->adj[u]; e; e = e->next)
            if (dist[u] + e->weight < dist[e->to])
                dist[e->to] = dist[u] + e->weight;   /* relax */
    }
}

Replace the linear "pick cheapest" scan with a binary heap and this becomes O((V + E) log V). Write the O(V²) version first, get it correct, then swap the selection step — the relaxation logic does not change.

dist[u] + e->weight overflows if dist[u] is INT_MAX. The dist[i] != INT_MAX guard in the selection loop is what prevents it — do not delete it as redundant.

27 — implementation in C

Dijkstra with a binary heap

typedef struct { int v, d; } Item;

static Item heap[MAXE + MAXV];   /* duplicates allowed */
static int  hsize;

static void hpush(int v, int d)
{
    int i = hsize++;
    heap[i].v = v; heap[i].d = d;

    while (i > 0) {                       /* sift up */
        int p = (i - 1) / 2;
        if (heap[p].d <= heap[i].d) break;
        Item t = heap[p]; heap[p] = heap[i]; heap[i] = t;
        i = p;
    }
}

static Item hpop(void)
{
    Item top = heap[0];
    heap[0] = heap[--hsize];

    int i = 0;
    for (;;) {                            /* sift down */
        int l = 2*i + 1, r = l + 1, m = i;
        if (l < hsize && heap[l].d < heap[m].d) m = l;
        if (r < hsize && heap[r].d < heap[m].d) m = r;
        if (m == i) break;
        Item t = heap[m]; heap[m] = heap[i]; heap[i] = t;
        i = m;
    }
    return top;
}
void dijkstra(Graph *g, int s, int *dist, int *parent)
{
    for (int i = 0; i < g->n; i++) {
        dist[i]   = INT_MAX;
        parent[i] = -1;
    }
    dist[s] = 0;
    hsize   = 0;
    hpush(s, 0);

    while (hsize > 0) {
        Item it = hpop();

        if (it.d > dist[it.v])
            continue;                  /* stale duplicate */

        for (Edge *e = g->adj[it.v]; e; e = e->next) {
            long nd = (long)it.d + e->weight;

            if (nd < dist[e->to]) {    /* relax */
                dist[e->to]   = (int)nd;
                parent[e->to] = it.v;
                hpush(e->to, dist[e->to]);
            }
        }
    }
}

Three details that are all load-bearing: the stale check after the pop, the long in the addition so INT_MAX cannot overflow, and the heap sized by E rather than V because every successful relaxation pushes a duplicate.

Reuse path_to() from the BFS slide on parent[] to recover the actual route. The reconstruction is identical — only the way the parents were computed differs.

28 — implementation in C

Bellman-Ford and Floyd-Warshall

/* returns 1 on success,
   0 if a negative cycle is reachable from s */
int bellman_ford(Graph *g, int s, int *dist, int *parent)
{
    for (int i = 0; i < g->n; i++) {
        dist[i]   = INT_MAX;
        parent[i] = -1;
    }
    dist[s] = 0;

    for (int pass = 0; pass < g->n - 1; pass++) {
        int changed = 0;

        for (int u = 0; u < g->n; u++) {
            if (dist[u] == INT_MAX) continue;

            for (Edge *e = g->adj[u]; e; e = e->next) {
                long nd = (long)dist[u] + e->weight;
                if (nd < dist[e->to]) {
                    dist[e->to]   = (int)nd;
                    parent[e->to] = u;
                    changed = 1;
                }
            }
        }
        if (!changed) return 1;        /* settled early */
    }

    for (int u = 0; u < g->n; u++) {   /* the Vth pass */
        if (dist[u] == INT_MAX) continue;
        for (Edge *e = g->adj[u]; e; e = e->next)
            if ((long)dist[u] + e->weight < dist[e->to])
                return 0;              /* negative cycle */
    }
    return 1;
}
#define INF (INT_MAX / 4)      /* headroom for INF + INF */

/* d[i][j] starts as the edge weight,
   0 on the diagonal, INF if no edge    */
void floyd_warshall(int n, int d[][MAXV])
{
    for (int k = 0; k < n; k++)          /* MUST be outer */
        for (int i = 0; i < n; i++) {
            if (d[i][k] == INF) continue;   /* prune a row */

            for (int j = 0; j < n; j++)
                if (d[i][k] + d[k][j] < d[i][j])
                    d[i][j] = d[i][k] + d[k][j];
        }
}

int has_negative_cycle(int n, int d[][MAXV])
{
    for (int i = 0; i < n; i++)
        if (d[i][i] < 0) return 1;
    return 0;
}

The continue when d[i][k] is INF is not just a speed-up — without it you add INF to INF on every unreachable pair, which is exactly the overflow the INT_MAX / 4 definition is there to survive. Keep both.

29 — implementation in C

Edmonds-Karp, in forty lines

#define MAXF 128

static int cap[MAXF][MAXF];   /* residual capacity  */
static int orig[MAXF][MAXF];  /* the original graph */
static int nf;                /* number of vertices */

void flow_init(int n)
{
    nf = n;
    for (int i = 0; i < n; i++)
        for (int j = 0; j < n; j++)
            cap[i][j] = orig[i][j] = 0;
}

void flow_add_edge(int u, int v, int c)
{
    cap[u][v]  += c;          /* += handles parallel edges */
    orig[u][v] += c;
}

/* BFS the residual graph; fills parent[],
   returns the bottleneck, or 0 if t is unreachable */
static int augment(int s, int t, int *parent)
{
    int visited[MAXF] = {0};
    int queue[MAXF], head = 0, tail = 0;

    for (int i = 0; i < nf; i++) parent[i] = -1;
    visited[s] = 1;
    queue[tail++] = s;

    while (head < tail) {
        int u = queue[head++];

        for (int v = 0; v < nf; v++) {
            if (visited[v] || cap[u][v] <= 0) continue;

            visited[v] = 1;
            parent[v]  = u;

            if (v == t) {                  /* shortest path found */
                int b = INT_MAX;
                for (int x = t; x != s; x = parent[x])
                    if (cap[parent[x]][x] < b)
                        b = cap[parent[x]][x];
                return b;
            }
            queue[tail++] = v;
        }
    }
    return 0;
}
int max_flow(int s, int t)
{
    int parent[MAXF], total = 0, b;

    while ((b = augment(s, t, parent)) > 0) {
        for (int v = t; v != s; v = parent[v]) {
            int u = parent[v];
            cap[u][v] -= b;        /* consume forward  */
            cap[v][u] += b;        /* open the reverse */
        }
        total += b;
    }
    return total;
}

Those two lines inside the loop are the residual graph. cap[v][u] += b is the "change your mind" edge — everything on the concept slides reduces to that one statement.

Why a matrix here, after all that

The adjacency-list decks argued hard against matrices. Flow networks are the exception, for two reasons.

  • Residual edges appear and disappear constantly. cap[u][v] is O(1) to read and update; finding and mutating a list node is not.
  • A reverse edge must exist for every forward edge, so the structure is dense in the directions that matter even when the input graph is sparse.

For large sparse networks, the production answer is an edge array with paired indices — edge i and edge i^1 are each other's reverse. Same idea, better memory. Write the matrix version first.

Note that max_flow destroys cap[][], turning it into the final residual graph. That is not a side effect to clean up — the next slide needs it.

30 — implementation in C

The min cut, and bipartite matching for free

/* call AFTER max_flow. fills cut[][2] with the
   edges crossing the cut; returns how many.     */
int min_cut(int s, int cut[][2])
{
    int visited[MAXF] = {0};
    int queue[MAXF], head = 0, tail = 0, k = 0;

    visited[s] = 1;                 /* reachable in residual */
    queue[tail++] = s;

    while (head < tail) {
        int u = queue[head++];
        for (int v = 0; v < nf; v++)
            if (!visited[v] && cap[u][v] > 0) {
                visited[v] = 1;
                queue[tail++] = v;
            }
    }

    for (int u = 0; u < nf; u++)
        for (int v = 0; v < nf; v++)
            if (visited[u] && !visited[v] && orig[u][v] > 0) {
                cut[k][0] = u;
                cut[k][1] = v;
                k++;
            }
    return k;                       /* their total capacity
                                       equals the max flow  */
}

This is why orig[][] was kept. The residual tells you which vertices are reachable; the original tells you which edges were really there. You need both, and only for these fifteen lines.

/* left  vertices: 0 .. L-1
   right vertices: L .. L+R-1
   source = L+R, sink = L+R+1          */
int bipartite_matching(int L, int R,
                       int qualified[][MAXF],
                       int match[])
{
    int s = L + R, t = L + R + 1;
    flow_init(L + R + 2);

    for (int i = 0; i < L; i++) flow_add_edge(s, i, 1);
    for (int j = 0; j < R; j++) flow_add_edge(L + j, t, 1);

    for (int i = 0; i < L; i++)
        for (int j = 0; j < R; j++)
            if (qualified[i][j])
                flow_add_edge(i, L + j, 1);

    int size = max_flow(s, t);

    for (int i = 0; i < L; i++) {       /* read it back */
        match[i] = -1;
        for (int j = 0; j < R; j++)
            if (orig[i][L+j] > 0 && cap[i][L+j] == 0)
                match[i] = j;           /* edge saturated */
    }
    return size;
}

The reduction is nine lines of graph building and one call. Recognising that a problem is bipartite matching is the hard part; once you have, the code is mechanical.

Reading the matching back out is the step people forget. A saturated middle edge — original capacity 1, residual capacity 0 — is an assignment that was made.

Test the property, not the output

Graph algorithms have many correct answers. A test that compares against one printed string will fail on a correct implementation and pass on a broken one.

/* a topological order is valid iff every edge
   points forwards in it                       */
int topo_valid(Graph *g, int *order, int count)
{
    int pos[MAXV];
    if (count != g->n) return 0;

    for (int i = 0; i < count; i++) pos[order[i]] = i;

    for (int u = 0; u < g->n; u++)
        for (Edge *e = g->adj[u]; e; e = e->next)
            if (pos[u] >= pos[e->to]) return 0;
    return 1;
}

/* BFS distances must satisfy the triangle rule */
int bfs_valid(Graph *g, int s, int *dist)
{
    if (dist[s] != 0) return 0;

    for (int u = 0; u < g->n; u++) {
        if (dist[u] == -1) continue;
        for (Edge *e = g->adj[u]; e; e = e->next) {
            if (dist[e->to] == -1) return 0;   /* reachable */
            if (dist[e->to] > dist[u] + 1) return 0;
        }
    }
    return 1;
}
int main(void)
{
    Graph g;
    int dist[MAXV], parent[MAXV], order[MAXV];
    srand(12345);

    for (int trial = 0; trial < 2000; trial++) {
        int n = 5 + rand() % 40;
        graph_init(&g, n, 0);                 /* undirected */

        for (int i = 0; i < n * 2; i++) {

        }

        assert(bfs_valid(&g, 0, dist));

        graph_free(&g);
    }

    /* DAG: build edges only from lower to higher id,
       so a cycle is impossible by construction      */
    for (int trial = 0; trial < 2000; trial++) {
        int n = 5 + rand() % 40;
        graph_init(&g, n, 1);
        for (int i = 0; i < n * 2; i++) {
            int u = rand() % n, v = rand() % n;
            if (u < v) graph_add_edge(&g, u, v, 1);
        }
        assert(!graph_has_cycle(&g));
        assert(topo_sort(&g, order));
        assert(topo_valid(&g, order, g.n));

32 — prove these work too

Testing shortest paths and flows

Both answers are numbers, which makes them look easy to test and is exactly why people test them badly. Check the properties the answer must satisfy, and cross-check the algorithms against each other.

/* a distance array is correct iff no edge can
   still be relaxed, and every reachable vertex
   has a distance                                */
int dist_valid(Graph *g, int s, int *dist)
{
    if (dist[s] != 0) return 0;

    for (int u = 0; u < g->n; u++) {
        if (dist[u] == INT_MAX) continue;
        for (Edge *e = g->adj[u]; e; e = e->next) {
            if (dist[e->to] == INT_MAX) return 0;
            if (dist[u] + e->weight < dist[e->to]) return 0;
        }
    }
    return 1;
}

/* and cross-check: on a non-negative graph,
   Dijkstra and Bellman-Ford must agree exactly  */
void cross_check(Graph *g, int s)
{
    int a[MAXV], b[MAXV], pa[MAXV], pb[MAXV];

    dijkstra(g, s, a, pa);
    assert(bellman_ford(g, s, b, pb));

    for (int i = 0; i < g->n; i++) assert(a[i] == b[i]);
    assert(dist_valid(g, s, a));
}
/* a flow is valid iff it respects capacities,
   conserves at every internal vertex, and its
   value equals the capacity of the min cut     */
int flow_valid(int s, int t, int total)
{
    int cut[MAXF * MAXF][2];

    for (int u = 0; u < nf; u++) {
        if (u == s || u == t) continue;

        int in = 0, out = 0;
        for (int v = 0; v < nf; v++) {
            int f = orig[u][v] - cap[u][v];   /* flow on u->v */
            if (f > 0) out += f;
            if (f < 0) return 0;              /* over capacity */

            int g = orig[v][u] - cap[v][u];
            if (g > 0) in += g;
        }
        if (in != out) return 0;              /* conservation */
    }

    int k = min_cut(s, cut), capsum = 0;
    for (int i = 0; i < k; i++)
        capsum += orig[cut[i][0]][cut[i][1]];

    return capsum == total;                   /* the theorem */
}

The last line is the strongest test you can write for a flow implementation. Max-flow min-cut says the two numbers must be equal; if your code disagrees with the theorem, your code is wrong. Run it on a few thousand random networks.

Build everything with -fsanitize=address,undefined. The flow code indexes two V×V matrices in nested loops, which is precisely where an off-by-one goes unnoticed for a long time.

33 — where this goes

In production, and what to learn next

Where you already rely on these

  • make, ninja, Gradle, npm, apt — topological sort over a dependency DAG, with cycle detection as the error path.
  • Google Maps, any satnav — Dijkstra or A* over a weighted road graph, heavily preprocessed.
  • Compilers — control-flow graphs for optimisation, call graphs for inlining, DFS for dominator trees.
  • Spreadsheets — recalculation order is a topological sort, and circular-reference detection is cycle detection.
  • Git — the commit history is a DAG, and git log is a traversal of it.
  • Social and recommendation systems — BFS for degrees of separation, random walks for ranking.

The honest summary: BFS, DFS and a sensible representation cover most of what you will ever need. Everything more advanced is worth learning, but it is built on these and reduces to them more often than not.
