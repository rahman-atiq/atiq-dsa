B-trees

A search tree built for a machine where reading one byte and reading four thousand bytes cost exactly the same — which is every machine you have ever used.

Red-black trees asked how cheaply a tree can be kept balanced. B-trees ask a different question: what if counting comparisons was the wrong thing to count all along? Arrow keys, or the buttons below, to move through the deck.

01 — the assumption nobody stated

Every balanced BST assumes all memory costs the same

It does not. It has not since about 1970.

where the data islatencyif an L1 hit took 1 second
L1 cache~1 ns1 second
L3 cache~15 ns15 seconds
main memory~80 ns1 min 20 sec
NVMe SSD~80 µs22 hours
spinning disk seek~8 ms3 months

When we counted comparisons and called it O(log n), we were implicitly charging the same price for every node we touched. On the top two rows that is roughly honest. On the bottom two it is off by a factor of a hundred thousand.

The thing being counted

In an in-memory algorithm the scarce resource is the comparison. Once the data outgrows RAM the scarce resource is the block transfer, and comparisons become free by comparison.

Any structure that is optimal under one cost model will usually be badly wrong under the other. That is not a flaw in red-black trees. It is a change in the problem.

02 — the damage, in numbers

A perfectly balanced tree is still 30 blocks deep

Take a billion keys in a red-black tree. Everything works exactly as promised: height around 30, no degenerate chains, every rotation bounded.

  • Each node is maybe 40 bytes, allocated by malloc whenever the key arrived.
  • Consecutive nodes on a search path are nowhere near each other in memory. The tree's logical structure and its physical layout have nothing to do with one another.
  • So each of the 30 hops is its own cache miss, and if the index lives on disk, its own read.

30 hops × 80 µs on NVMe = 2.4 ms for a single lookup.

Roughly 400 lookups per second, per thread. A database doing that would be unusable.

And the pathology is worse than the arithmetic suggests: each read pulls in a 4 KB page to deliver 40 useful bytes. 99% of every transfer is discarded.

Things that do not fix this

  • A tighter balance invariant. AVL gets you to 1.44 log₂ n instead of 2 log₂ n. You go from 30 hops to 22. Still catastrophic.
  • A faster comparison. Comparisons were never the cost.
  • A better allocator. It helps at the margin, but the tree still visits one key per block read.
  • More RAM. Works until the data grows, which it does.

Every one of these attacks the constant factor. The problem is not the constant factor.

03 — where the leverage actually is

The problem is the base of the logarithm

The height of any tree with branching factor b is logb n. A binary tree fixes b = 2, and every balancing scheme in the world then fights over the constant in front.

But logb n = log₂ n / log₂ b. Raising the branching factor divides the height. It is the only lever that moves the number of block reads by an order of magnitude rather than a percentage.

keysb = 2b = 128b = 256

Height in levels, rounded up. The middle and right columns are not cleverer algorithms. They are the same algorithm with a different number in one place.

So why was anyone using b = 2?

Because in RAM, a wide node buys you nothing. Touching 256 keys inside a node costs 256 comparisons whether they are contiguous or not, and a binary tree does log₂ n comparisons in total — which is fewer.

Under a block cost model that reasoning inverts. The comparisons inside a node are free, because the node already arrived as a single transfer. Only the number of nodes visited is billed.

Wide nodes are not a general improvement. They are the correct answer to a specific cost model, and the wrong answer to the one red-black trees were designed for.

04 — the idea

You already paid for the whole block. Fill it.

The unit of transfer between memory and storage is a page, typically 4 KB. Between RAM and cache, it is a 64-byte line. In both cases the hardware charges you for the whole unit no matter how much of it you read.

So size the node to the unit:

4096 bytes ÷ (8-byte key + 8-byte child pointer) ≈ 256 children per node.

A billion keys now fit in four levels. Four block reads per lookup instead of thirty — and in practice three, because the root and the level below it stay resident in cache after the first few queries.

Nothing about the search logic changed. It is still descend-and-compare. What changed is that each descent now discards one two-hundred-and-fifty-sixth of the search space instead of one half.

Identical key set, identical asymptotics, both perfectly valid balanced search trees. Count the levels. Now imagine each level is a disk seek.

05 — the structure, stated properly

A B-tree of minimum degree t

  1. Every node holds its keys in sorted order, and a node with k keys has exactly k + 1 children.
  2. Every node except the root holds at least t − 1 keys, and therefore at least t children. This is the guarantee that stops the tree going sparse.
  3. Every node holds at most 2t − 1 keys, and therefore at most 2t children. This is what makes a node fit one block. A node with 2t − 1 keys is full.
  4. The root may hold as few as one key — or none, if the tree is empty.
  5. All leaves are at exactly the same depth. Not approximately. Exactly.

Keys inside a node partition the key space for its children: everything in child i lies strictly between key i−1 and key i. It is a binary search tree's ordering rule, generalised from one key per node to many.

Read property 5 again

This is the invariant, and it is a much stronger statement than "balanced". A red-black tree permits one path to be twice another. A B-tree permits no variation at all in leaf depth.

Every operation in this deck exists to preserve it. That is why B-trees grow and shrink from the root rather than the leaves: adding a level at the top is the only change that keeps all leaves level with each other.

Why "minimum degree"?

Some textbooks use order m = maximum children, and disagree with each other about whether m counts keys or children. CLRS uses minimum degree t and it removes the ambiguity, so this deck does too. t = 2 gives the smallest legal B-tree: 1 to 3 keys, 2 to 4 children.

06 — why the height collapses

From "at least t−1 keys" to a height bound

Only property 2 matters here. The worst case for height is the emptiest legal tree: root with one key and two children, every other node with the minimum t − 1 keys and t children.

Count the nodes level by level: 1, then 2, then 2t, then 2t², and so on. At height h the tree has at least

n ≥ 2th − 1, so h ≤ logt((n + 1) / 2)

Which is O(log n) again — but with t in the base, and t is a number you choose to match your hardware rather than a number the data structure forces on you.

The number that actually matters

A lookup costs h + 1 node reads. Inside each node you do a scan over up to 2t − 1 keys, which is real work but happens entirely in cache on data that has already arrived.

Worst-case height, by t

tmax keys/noden = 10⁶n = 10⁹

These are worst cases, assuming every node is as empty as the rules allow. Random insertion leaves nodes roughly 69% full on average, so real trees sit a level below these numbers.

The root is read on every single query, so it stays in cache permanently. The level below it is read on every query too, and for t = 128 that is 128 nodes — half a megabyte, also resident. In practice a four-level B-tree costs one actual disk read.

08 — search

Search is the easy one, and it sets up everything else

At each node, scan the sorted keys for the first one that is not less than your target.

  • If it matches, you are done.
  • If the node is a leaf, the key is not in the tree.
  • Otherwise descend into the child at that position and repeat.

That is it. The whole algorithm is "narrow the interval, go down one level", exactly as in a BST — the interval just narrows by a factor of 2t instead of 2.

Linear scan or binary search inside the node?

Binary search is O(log t) instead of O(t), which sounds obviously better and often is not. A linear scan over a contiguous sorted array is perfectly predicted by the prefetcher and branch predictor; a binary search jumps around and mispredicts almost every step.

For t up to roughly 64, measure before you switch. Either way the cost is inside one already-loaded block, so it is not where your lookup time is going.

The invariant search relies on

Keys within a node are sorted, and child i holds exactly the keys strictly between key i−1 and key i. Every insert and delete operation in the rest of this deck has to preserve that, including in the middle of a split or a merge.

Cost

  • Node reads: h + 1, which is O(logt n).
  • Comparisons: O(t) per node, O(t · logt n) in total.

Note that the comparison count is worse than a red-black tree's. That is the trade, and under a block cost model it is an excellent one.

09 — insertion

Every key goes into a leaf. The problem is what happens when the leaf is full.

A new key always belongs in a leaf — descend as if searching, and insert it into the sorted array there. If the leaf has room, you are finished, and no other node in the tree is touched.

If the leaf already holds 2t − 1 keys, it overflows. The fix is a split:

  • The full node's 2t − 1 keys divide into t−1 on the left, a single median, and t−1 on the right.
  • Left and right become two legal nodes, each with the minimum t − 1 keys.
  • The median moves up into the parent, as the separator between them.

Which raises the obvious question: what if the parent is full too?

Two ways to handle that

Split on the way up. Insert into the leaf, and if it overflows, split and push the median up, repeating as far as necessary. Natural, and it splits only the nodes that genuinely needed it.

Split on the way down. While descending, split every full node you pass through, before you go into it. By the time you reach the leaf, every node on the path has room, so a split can never cascade.

CLRS and most real implementations take the second option. It costs a handful of unnecessary splits, and buys a single downward pass: you never have to walk back up, never have to keep the path pinned in memory, and never hold a lock on a node you have already left.

That last point is why databases care. Under concurrency, an algorithm that only ever moves downward can release the parent's latch as soon as the child is known to be safe.

10 — insertion

Splitting a full child

before — the child is full, t = 3
after — median 40 has moved up

With t = 3 a full node holds 5 keys. Split it at the median:

  • keys 10 20 stay in the original node,
  • keys 50 60 move into a new right sibling,
  • key 40 moves up into the parent,
  • and if it is an internal node, its 6 children divide 3 and 3.

Both halves end up with exactly t − 1 keys, which is the legal minimum — never below it. The parent gains one key and one child.

Splitting is the only way a B-tree gets taller, and it only happens at the root. When the root itself is full, a fresh root is created with the old root as its single child, then that child is split. The new root has one key and two children — which is exactly what property 4 permits.

This is why all leaves stay at the same depth. Growth happens at the top, so every leaf gains a level at the same instant. No leaf can ever be one level deeper than another.

Build one yourself

Things to try deliberately

  • Find an insertion that splits a node which did not need splitting. That is the price of the single downward pass.
  • Delete keys until a merge happens, then keep going until the root collapses.

Occupancy

Watch the fill percentage as you add random keys. It settles around 69% — ln 2 — not 100%. Every real B-tree wastes about a third of every block, and it is still enormously ahead. That slack is what makes most insertions touch exactly one node.

12 — deletion

Deletion is the hard one, for the mirror-image reason

Insertion's enemy is overflow: a node with too many keys. Deletion's enemy is underflow: a node dropping below t − 1 keys, which breaks property 2 and lets the tree go sparse and tall.

And there is a second complication insertion did not have. A key you want to delete might sit in an internal node, where you cannot simply remove it — its two surrounding children would be left with nothing separating them.

The same trick as insertion, inverted

Rather than deleting and repairing upward, guarantee on the way down that you never enter a node that could underflow:

Before descending into a child, ensure that child has at least t keys — one more than the minimum. Then removing a key from it can never take it below t − 1.

Topping up a thin child is done by borrowing from an adjacent sibling if one can spare a key, or merging with a sibling if neither can.

Borrow, or rotate

Borrowing is not a straight steal. The sibling's nearest key moves up into the parent, and the parent's separator moves down into the thin child. The ordering rule survives because the separator was always between them. If the nodes are internal, the corresponding child pointer moves across too.

Merge

When both neighbours sit at the minimum, no borrow is possible. Instead, the thin child, the parent's separator key, and the sibling all combine into one node holding (t−1) + 1 + (t−1) = 2t − 1 keys — exactly full, and legal.

The parent loses one key. If the parent was the root and that was its last key, the merged node becomes the new root and the tree loses a level — from the top, so all leaves rise together.

14 — the variant the world actually ships

B⁺ trees: move everything to the leaves

A textbook B-tree stores real data next to every key, at every level. Almost no production system does that. The B⁺ variant makes two changes:

  • Records live only in the leaves. Internal nodes hold separator keys and child pointers — nothing else. They are pure routing.
  • Leaves are linked left to right. Each leaf points at its successor.

Both changes are small. Both matter enormously.

What that buys

  • Higher fanout. Without payload in internal nodes, a 4 KB block holds far more separators, so the tree is shallower again.
  • Range scans become sequential. WHERE age BETWEEN 30 AND 40 is one descent to the first leaf, then a straight walk along the leaf chain. No re-descent, no random I/O.
  • Uniform latency. Every lookup costs exactly h reads, because a key match at an internal node is only a separator, never an answer. Predictable beats occasionally-fast.

The cost

Separator keys are duplicated — once as a router, once in a leaf. A few percent more space, and the separators are no longer required to be keys that still exist. Deleting a key does not oblige you to remove it from the internal nodes above; it just stays as a boundary marker.

That is a feature, not a compromise: deletion in a B⁺ tree touches fewer nodes than in a plain B-tree, because it almost always stops at the leaf.

15 — implementation in C

The node layout is the design decision

#include <stdlib.h>
#include <limits.h>

#define T     3                /* minimum degree  */
#define MAXK  (2*T - 1)        /* 2t-1 keys       */
#define MAXC  (2*T)            /* 2t children     */

typedef struct BNode {
    int            n;          /* keys in use     */
    int            leaf;       /* 1 if no children*/
    int            key[MAXK];
    struct BNode  *child[MAXC];
} BNode;

typedef struct { BNode *root; } BTree;

static BNode *node_new(int leaf)
{
    BNode *x = malloc(sizeof *x);
    if (!x) return NULL;
    x->n    = 0;
    x->leaf = leaf;
    return x;
}

BTree *bt_create(void)
{
    BTree *t = malloc(sizeof *t);
    if (!t) return NULL;
    t->root = node_new(1);
    if (!t->root) { free(t); return NULL; }
    return t;
}

Why the arrays are inline

Writing int *key and allocating separately would look tidier and would destroy the entire point. The node has to be one contiguous run of bytes, because the whole design rests on it arriving in a single transfer.

The same applies to the child array. Fixed-size, inline, sized by a compile-time constant so the compiler can compute every offset.

Print sizeof(BNode) and compare it with your page size. On a real system you pick T so that the result lands just under 4096 — that is the whole tuning story. For teaching, T = 3 keeps the diagrams legible.

No parent pointers

Unlike the red-black tree, nothing here ever needs to walk upward. Both insert and delete repair the tree on the way down, so plain recursion is enough and the node stays smaller.

16 — implementation in C

Search, and splitting a full child

/* first index i with key[i] >= k */
static int find_key(BNode *x, int k)
{
    int i = 0;
    while (i < x->n && x->key[i] < k) i++;
    return i;
}

BNode *bt_search(BNode *x, int k, int *pos)
{
    int i = find_key(x, k);

    if (i < x->n && x->key[i] == k) {
        *pos = i;
        return x;
    }
    if (x->leaf) return NULL;
    return bt_search(x->child[i], k, pos);
}

find_key is used by search, insert and all five deletion cases. Write it once and make it obviously correct — an off-by-one here surfaces as corruption three operations later.

/* x->child[i] is full; split it around its median */
static void split_child(BNode *x, int i)
{
    BNode *y = x->child[i];
    BNode *z = node_new(y->leaf);

    z->n = T - 1;
    for (int j = 0; j < T - 1; j++)          /* right half */
        z->key[j] = y->key[j + T];
    if (!y->leaf)
        for (int j = 0; j < T; j++)
            z->child[j] = y->child[j + T];
    y->n = T - 1;                            /* left half  */

    for (int j = x->n; j > i; j--)           /* make room  */
        x->child[j + 1] = x->child[j];
    x->child[i + 1] = z;

    for (int j = x->n - 1; j >= i; j--)
        x->key[j + 1] = x->key[j];

    x->key[i] = y->key[T - 1];               /* median up  */
    x->n++;
}

Trace the indices once by hand with T = 3. y holds keys 0…4; z takes 3 and 4; the median is key 2; y is left with 0 and 1. Children 0…5 divide as 0…2 and 3…5. Everything else in the file depends on these six lines being right.

17 — implementation in C

Insert: split everything full on the way down

/* precondition: x is not full */
static void insert_nonfull(BNode *x, int k)
{
    int i = x->n - 1;

    if (x->leaf) {
        while (i >= 0 && k < x->key[i]) {
            x->key[i + 1] = x->key[i];
            i--;
        }
        x->key[i + 1] = k;
        x->n++;
        return;
    }

    while (i >= 0 && k < x->key[i]) i--;
    i++;

    if (x->child[i]->n == MAXK) {
        split_child(x, i);
        if (k > x->key[i]) i++;   /* median decides side */
    }
    insert_nonfull(x->child[i], k);
}
void bt_insert(BTree *t, int k)
{
    BNode *r = t->root;

    if (r->n == MAXK) {           /* root full: grow up */
        BNode *s = node_new(0);
        s->child[0] = r;
        t->root = s;
        split_child(s, 0);
        insert_nonfull(s, k);
    } else {
        insert_nonfull(r, k);
    }
}

Nine lines, and they contain the only place a B-tree ever gets taller. The new root starts with one key and two children, which property 4 explicitly allows, and every leaf gains a level simultaneously.

The precondition is the proof

Read the comment above insert_nonfull as a contract. bt_insert establishes it for the root; the split inside the loop re-establishes it for each child before descending. Because it always holds, a leaf insertion can never overflow, and no repair pass upward is ever needed.

Duplicate keys are not handled here — this version will happily store the same key twice. Decide your policy (reject, or count) and enforce it in bt_insert with a search first.

18 — implementation in C

Delete: the five cases, in code

static void node_remove(BNode *x, int k);

static int get_pred(BNode *x, int i)
{
    BNode *c = x->child[i];
    while (!c->leaf) c = c->child[c->n];
    return c->key[c->n - 1];
}

static int get_succ(BNode *x, int i)
{
    BNode *c = x->child[i + 1];
    while (!c->leaf) c = c->child[0];
    return c->key[0];
}

static void remove_internal(BNode *x, int i)
{
    int k = x->key[i];

    if (x->child[i]->n >= T) {              /* case 2 */
        int pred = get_pred(x, i);
        x->key[i] = pred;
        node_remove(x->child[i], pred);
    } else if (x->child[i + 1]->n >= T) {   /* case 3 */
        int succ = get_succ(x, i);
        x->key[i] = succ;
        node_remove(x->child[i + 1], succ);
    } else {                                /* case 4 */
        merge(x, i);
        node_remove(x->child[i], k);
    }
}
static void node_remove(BNode *x, int k)
{
    int i = find_key(x, k);

    if (i < x->n && x->key[i] == k) {
        if (x->leaf) {                      /* case 1 */
            for (int j = i + 1; j < x->n; j++)
                x->key[j - 1] = x->key[j];
            x->n--;
        } else {
            remove_internal(x, i);
        }
        return;
    }

    if (x->leaf) return;                    /* not present */

    int last = (i == x->n);                 /* case 5 */
    if (x->child[i]->n < T) fill(x, i);

    if (last && i > x->n) node_remove(x->child[i - 1], k);
    else                  node_remove(x->child[i], k);
}

void bt_delete(BTree *t, int k)
{
    node_remove(t->root, k);

    if (t->root->n == 0 && !t->root->leaf) {
        BNode *old = t->root;               /* shrink */
        t->root = old->child[0];
        free(old);
    }
}

The last variable is the subtle line. If you were heading into the rightmost child and fill merged it leftwards, that child no longer exists at index i — it is now part of child[i-1]. Get this wrong and you read freed memory.

19 — implementation in C

Topping up a thin child: borrow and merge

static void borrow_from_prev(BNode *x, int i)
{
    BNode *c = x->child[i], *s = x->child[i - 1];

    for (int j = c->n - 1; j >= 0; j--)
        c->key[j + 1] = c->key[j];
    if (!c->leaf)
        for (int j = c->n; j >= 0; j--)
            c->child[j + 1] = c->child[j];

    c->key[0] = x->key[i - 1];        /* parent comes down */
    if (!c->leaf) c->child[0] = s->child[s->n];

    x->key[i - 1] = s->key[s->n - 1]; /* sibling goes up   */
    c->n++;
    s->n--;
}

static void borrow_from_next(BNode *x, int i)
{
    BNode *c = x->child[i], *s = x->child[i + 1];

    c->key[c->n] = x->key[i];
    if (!c->leaf) c->child[c->n + 1] = s->child[0];

    x->key[i] = s->key[0];

    for (int j = 1; j < s->n; j++)
        s->key[j - 1] = s->key[j];
    if (!s->leaf)
        for (int j = 1; j <= s->n; j++)
            s->child[j - 1] = s->child[j];

    c->n++;
    s->n--;
}
static void merge(BNode *x, int i)
{
    BNode *c = x->child[i], *s = x->child[i + 1];

    c->key[T - 1] = x->key[i];       /* separator drops in */
    for (int j = 0; j < s->n; j++)
        c->key[j + T] = s->key[j];
    if (!c->leaf)
        for (int j = 0; j <= s->n; j++)
            c->child[j + T] = s->child[j];

    for (int j = i + 1; j < x->n; j++)
        x->key[j - 1] = x->key[j];
    for (int j = i + 2; j <= x->n; j++)
        x->child[j - 1] = x->child[j];

    c->n += s->n + 1;
    x->n--;
    free(s);
}

static void fill(BNode *x, int i)
{
    if (i != 0 && x->child[i - 1]->n >= T)
        borrow_from_prev(x, i);
    else if (i != x->n && x->child[i + 1]->n >= T)
        borrow_from_next(x, i);
    else if (i != x->n)
        merge(x, i);
    else
        merge(x, i - 1);
}

merge is split_child run backwards, and the index arithmetic is the same arithmetic reversed. If you got the split right, check the merge against it rather than deriving it from scratch.

20 — prove it works

Write the validator before you write delete

A broken B-tree answers most searches correctly for a long time. Only a structural check finds the damage on the operation that caused it.

typedef struct { int ok; int leaf_depth; } Check;

static void check(BNode *x, int depth, int is_root,
                  long lo, long hi, Check *c)
{
    if (x->n > MAXK)                       c->ok = 0;
    if (!is_root && x->n < T - 1)          c->ok = 0;
    if (is_root && !x->leaf && x->n < 1)   c->ok = 0;

    for (int j = 0; j < x->n; j++) {
        if (j && x->key[j-1] >= x->key[j]) c->ok = 0;
        if (x->key[j] <= lo || x->key[j] >= hi) c->ok = 0;
    }

    if (x->leaf) {
        if (c->leaf_depth < 0)             c->leaf_depth = depth;
        else if (c->leaf_depth != depth)   c->ok = 0;
        return;
    }
    for (int j = 0; j <= x->n; j++)
        check(x->child[j], depth + 1, 0,
              j == 0     ? lo : x->key[j-1],
              j == x->n  ? hi : x->key[j], c);
}

int bt_valid(BTree *t)
{
    Check c = { 1, -1 };
    check(t->root, 0, 1, LONG_MIN, LONG_MAX, &c);
    return c.ok;
}
#define N 20000

    srand(12345);

        int k = rand() % N;

        if (rand() & 1) {
            if (!present[k]) { bt_insert(t, k); present[k] = 1; }
        } else {
            if (present[k]) { bt_delete(t, k); present[k] = 0; }
        }
        assert(bt_valid(t));
        assert((bt_search(t->root, k, &pos) != NULL)
               == (present[k] != 0));
    }
    puts("ok");
    return 0;
}

Build it like this:

gcc -Wall -Wextra -O2 -fsanitize=address,undefined bt.c -o bt

The five checks in check map one-to-one onto the five properties. The leaf-depth check is the one that catches the subtle bugs — a merge that loses a level shows up here and almost nowhere else.

21 — where it lives, and what to do next

In production, and when not to reach for one

Where you are already using one

  • Every relational database index you have ever created — InnoDB, PostgreSQL, SQL Server, Oracle, SQLite.
  • Filesystems — NTFS, HFS+, XFS, btrfs, ext4's directory hashing.
  • In-memory too, increasingly: Rust's BTreeMap and Abseil's B-tree containers beat red-black trees on modern CPUs, because the cache line is a block and the same argument applies one level up the hierarchy.

When not to. Random-key write-heavy workloads are the weak spot: every insert dirties a different page, so the disk sees random writes. That is the case LSM trees (RocksDB, Cassandra, LevelDB) were built for — they buffer in memory and write sequentially, paying for it with slower reads.

If a database uses a B⁺ tree and its competitor uses an LSM tree, they are not disagreeing about data structures. They are disagreeing about read/write ratio.

Exercises — write the prediction down first

  1. Before running anything: inserting 1…20 into an empty B-tree with t = 2, how many splits occur and what is the final height? Instrument split_child and check.
  2. Predict the height for n = 10⁶ with t = 50. Then build it and measure.
  3. Implement bt_create, bt_search, bt_insert and bt_valid. Do not start deletion until the validator survives 10⁵ random insertions.
  4. Implement deletion and run the differential harness under AddressSanitizer.
  5. Measure average node occupancy after 10⁵ random insertions, then after 10⁵ ascending insertions. The two numbers differ a lot. Explain why before you look it up.
  6. Splitting on the way down splits nodes that would never have overflowed. Count them. What did the wasted splits buy?
  7. Set T to 128 and replace the linear scan in find_key with binary search. Measure. If it did not help, work out why.
  8. Compare against the red-black deck: for the same 10⁶ keys, which structure does more total pointer writes, and which touches more distinct cache lines per lookup?
