B-Trees
Stop counting comparisons. Start counting page reads.

Every tree you have built so far — BST, AVL, red-black — optimises the same number: comparisons. That number has been the right one because everything lived in RAM. Today the data does not fit in RAM, the machine starts charging you for something else entirely, and every balanced binary tree you know becomes the wrong shape. You are going to work out the right one.

The hardware does not sell you bytes. It sells you pages.

You cannot read 20 bytes off a disk. The smallest thing the device will hand over is a block — 4096 bytes, typically. Ask for one byte, pay for 4096. Ask for 20, pay for 4096.

One red-black node in one 4 KB page: key 8B + two pointers 16B + a colour bit = 24 bytes. The hatched 4072 are what you paid for and threw away, on every single level.

So the cost model was never "comparisons"

The unit that costs money is the page touch. A lookup's price is the number of nodes on the root→leaf path — which is the height — and nothing else. Comparisons inside a page you have already paid for are free.

cost of a lookup ≈ height × page read
The turn

Height is set by one thing, and it was never the balance rule.

Where does height come from?

A perfectly balanced tree where every node has m children stores n keys in

h ≈ logm n = log₂n / log₂m

Every balanced binary tree in the world is stuck at m = 2, so log₂m = 1 and there is nothing left to optimise. AVL and red-black are not fighting over the height formula — they are fighting over the constant in front of it.

Your design brief — write this one down

You get one 4 KB page per node. Spend all of it. Invent a tree that obeys all four:

aA node holds many keys and many child pointers — enough to fill a page. 102030…
bThe height stays O(logm n) no matter what order the keys arrive in. Same demand as always.
cPages must actually be full. A tree of half-empty pages has a fanout of 2 and you are back where you started.
dRepairs must not shuffle pages around. Moving a page is a disk write, and rotations move pages.

Five minutes, in pairs. Constraint (d) is the one that gives the game away — if you can't rotate, then every rebalancing trick you learned in the last two labs is off the table. You need a completely different way to fix a broken tree.

The keys were never the data. They are fences.

In a BST the key at a node answers left or right? Here, k sorted keys answer which of my k+1 buckets? A node's job is unchanged: narrow the search. You simply gave it a bigger vocabulary.

Name it, and then read it back to yourself

A node with at most m children and at most m−1 keys is an m-way search tree. Set m = 2 and every word of that sentence collapses into the definition of a binary search tree. The BST was the special case all along.

The definition

One node, one page, one scan. Then descend.

The ordering rule, in full

A node holds sorted keys k₁ < k₂ < … < kj and j+1 child pointers c₀ … cj, interleaved:

c₀  k₁  c₁  k₂  c₂  …  kj  cj

Every key in subtree ci lies strictly between ki and ki+1. The two ends are open: c₀ holds everything below k₁, cj everything above kj.

Search — and notice what it costs

Scan the keys in the node for your target. Miss? You land between two fences, and that gap is the pointer to follow. Repeat.

One page read per level. The scan inside the page is free — you already paid for those bytes.

55 > 40, 55 < 70 → take the middle gap. Scan that page: found. Two page reads. A BST holding the same 8 keys needs three or four.

The invention

You cannot rotate. So stop trying to fix the tree, and refuse to break it.

1Attack the height directly. Don't bound it, fix it: every leaf sits at exactly the same depth. Not "within one". The same. There is now no such thing as a long path, because every path is the same length.
✗Test it before you trust it. That chain on the last slide? Its leaves are all at depth 4 — there is only one leaf. Rule 1 alone permits it. Rule 1 is worth nothing on its own, and for exactly the reason you already guessed: nothing forces the pages to be full.
2Every node is at least half full: at least ⌈m/2⌉ children. Now a tree of height h is forced to contain at least 2⌈m/2⌉h−1−1 keys — so h cannot grow unless n grows exponentially.
3Two exemptions, both forced: the root is excused (a tree with three keys can't have a half-full root), and leaves have no children to count.

Stop. That is the whole invention. An m-way search tree obeying those two rules is a B-tree. Everything from here — splitting, merging, borrowing, the C code — is nothing but how you keep those two promises while keys arrive and leave.

The question you should be asking

"All leaves at the same depth" is a brutal promise. Add one key to a full leaf and it must split — so that leaf gets deeper than its siblings. How can any insertion possibly keep that promise?

Hold that thought for four slides. The answer is the single most elegant idea in this lab.

Same idea, exam language

You invented both rules. Here are all five, as they will be marked.

1Every node holds at most m−1 keys and at most m children.
2Every node except the root holds at least ⌈m/2⌉−1 keys, and every internal one has at least ⌈m/2⌉ children.
3The root is exempt: at least 1 key, and at least 2 children if it is not itself a leaf.
4All leaves appear on the same level. This is the one that does the work.
5Keys inside a node are sorted, and subtree ci holds exactly the keys between ki and ki+1.

The convention trap — check which one your exam uses

This deck uses order m = the maximum number of children, which is what your syllabus means. CLRS does not. CLRS uses minimum degree t: at least t−1 and at most 2t−1 keys, so m = 2t. A "B-tree of order 5" and a "B-tree with t = 5" are completely different trees. Some books even define order as the maximum number of keys. State your convention in the first line of every answer.

Do the algebra yourself

Three lines. Follow along on paper — you will be asked to reproduce this.

1Count the nodes the rules force to exist. Write t = ⌈m/2⌉. Level 1 is the root. Level 2 has at least 2 nodes (rule 3), and every node below drags in at least t children — so level i has ≥ 2ti−2 nodes.
2Give every node its minimum keys. Root ≥ 1, everyone else ≥ t−1. Sum the levels: n ≥ 1 + (t−1)·∑2ti−2 = 2th−1 − 1
3Rearrange for h. Every step was a minimum, so that many keys are required — which caps h from above.
h ≤ 1 + log⌈m/2⌉ ( (n+1) / 2 )

Read the base of that logarithm. Not 2 — ⌈m/2⌉. Rule 2 is what puts m in the denominator of the height. Without it the base collapses to 2 and you have written a red-black tree with extra steps.

In practice it beats the table

The root is read on every lookup so it stays in RAM, and level 2 caches too. A billion-key index costs one or two real reads — whereas the red-black tree's 30 touches were all misses.

The honest version

A B-tree does not do fewer comparisons. It does exactly the same number.

Do the multiplication

Binary-search the keys inside each page: log₂m comparisons per page. Visit logmn pages. Multiply:

log₂m × logmn = log₂m × log₂n⁄log₂m = log₂n

The m cancels. Identical to a perfectly balanced binary tree — because it is one. A B-tree of order 256 is a binary search over the same sorted keys, with the comparisons grouped 8 at a time into pages you already paid for.

And if you scan the page linearly instead?

Then it is m/2 per level — about 500 comparisons for our billion keys instead of 30. Seventeen times more work, and still the right choice, because 500 ns of sequential scanning inside a cached page loses to one 80 µs page read by a factor of 160.

So say it properly in the viva

A B-tree is not faster because it is cleverer at searching. It is faster because it changed the unit of cost:

Comparisons per lookupunchanged
Pointer dereferences30 → 4
Bytes usefully read per page24 → 4096
Cache / page faults~30 → ~1

The generalisable lesson

Same move as arrays beating linked lists, as cache-oblivious algorithms, as every database on earth: when one operation costs a thousand times more than another, minimise the expensive one — even by doing far more of the cheap one. Big-O with the wrong unit is a confident wrong answer.

Why property 4 can never break

Splits push keys upward. A leaf split leaves every leaf exactly where it was. The only event that changes any leaf's depth is the root splitting — and that adds one level to every path simultaneously.

So "all leaves on the same level" is not a rule you enforce. It is a rule you cannot break.

Upside down, and say it out loud

Every other tree you have written grows downward at the leaves and is rebalanced from above. A B-tree grows upward from the root. That single inversion is what buys perfect level balance for free, with zero rotations, ever.

This is also the only way a B-tree ever gets taller — which means the height changes very rarely: at order 256 a tree crosses from three levels to four at around 5 million keys, and from four to five at around a billion. Most indexes change height two or three times in their entire life.

Before you write code

The obvious algorithm needs parent pointers. The clever one does not.

Reactive — split on the way back up

Descend to the leaf and insert. If it overflowed, split and hand the median up; if that overflowed, repeat. The recursion unwinding does the climbing.

Matches how you do it on paperyes
Splits only pages that truly overflowyes
Needs the path kept — recursion or a stackyes
Pages pinned in memory during descentall of them

Fine in RAM. On disk it means locking every page on the path until you know whether the split reaches the root.

Proactive — split on the way down

Descending, whenever you are about to step into a full child, split it first. You are on its parent, which is guaranteed to have room, so the median lands safely.

Number of passes over the tree1
Parent pointers / stack needednone
Pages held at once2
Occasionally splits a page that had roomyes
Requires m to be evenyes — see below

This is CLRS's B-TREE-INSERT.

Induction, not hand-waving: split the root up front if it is full, then only ever descend into a node you have confirmed is not full — so every median has somewhere to go and the cascade cannot happen.

But count the keys. Proactive splitting cuts m−1 keys, not m: order 5 gives 2|1|1 and the right half is left with 1 key when the minimum is 2 — illegal. It works only for even m, where 2t−1 cuts into t−1|1|t−1. That is why CLRS uses t and defines m = 2t. So: reactive on paper and in this deck's C; proactive only for a real disk B-tree, at an even order.

Your turn — and notice the asymmetry

Insertion had one repair: split. Deletion is going to need more, because "too few keys" can be fixed by taking one from someone who has spare, or by giving up and fusing two starved pages into one. Work out which of those two you would prefer, and when you would have no choice.

Pens down

Every deletion happens in a leaf. Even the ones that don't look like it.

1Key is in a leaf with room to spare (more than the minimum). Rub it out. Done. No further thought required — and this is the overwhelming majority of deletions.
2Key is in an internal node. Do not erase a fence. Overwrite it with its in-order predecessor (the largest key in the subtree on its left) or its successor — both sit in a leaf — then delete that key from that leaf instead.
3The leaf is now below minimum. Underflow. Two ways out, and you must try them in this order: borrow from an adjacent sibling that has spare, otherwise merge with one that does not.

Step 2 is the whole trick, and it is worth naming

The predecessor is a perfect stand-in: it is larger than everything in the left subtree and smaller than everything in the right one — which is the definition of the fence you just removed. The ordering never wobbles for an instant.

And it converts every deletion into a leaf deletion. You only ever need to know how to repair a starved leaf. This is the identical trick you used for BST deletion in week two — nothing new, just wider nodes.

Why it rotates instead of sliding sideways

Ask what would happen if you moved 40 directly into the left leaf: you would get 1040 sitting to the left of the fence 30. 40 > 30. Property 5 destroyed.

The only key in the entire tree that legally belongs immediately to the right of 10 is the separator 30 itself. So 30 must come down — which leaves the fence empty, and the sibling's smallest key 40 is the only key that legally fills it. The rotation is forced, not chosen.

Left sibling, right sibling — write one, mirror the other

Borrowing from the left is the same three moves with every direction reversed: the separator comes down to become the starved page's first key, and the left sibling's largest key goes up.

If your two branches differ in any way beyond swapping first for last and left for right, one of them is wrong. Same rule you learned writing left_rotate and right_rotate last lab.

At an internal node the borrowed key drags a child pointer with it. Forgetting that child is the single most common deletion bug — in exams and in code.

The separator goes down, and that is the catch

A merge consumes a key from the parent. Three pages became two, so the parent needs one fewer fence — but the parent is now one key lighter, and it may have been at its minimum too.

So you re-ask the whole question one level up: does the parent underflow? Borrow, or merge, or stop. Identical problem, one level higher — the exact mirror of a split cascading upward.

Try to borrow first. Always.

Borrowing terminates immediately and touches 3 pages. Merging destroys a page, lowers the tree's fill, and may cascade to the root. They are not equally good.

Check both adjacent siblings before giving up — a common exam slip is to look only right, find it starved, and merge when the left neighbour was sitting there with four keys. A node's cousins do not count, though: only siblings sharing your parent can lend, because only they have a separator between you.

An empty root is the only legitimate reason to delete a node other than by merging. Never "tidy up" a root holding 1 key — that is legal and required.

The symmetry, stated once, for the exam

root splits → +1 level  ·  root empties → −1 level

Nothing else in the entire structure can change a leaf's depth. Not a split, not a borrow, not a merge below the root, not any sequence of them in any order.

That is why a B-tree needs no balance factors, no colours, no heights, no rotations, and no metadata of any kind — and why it stays perfectly level after a billion operations. The balance is structural, not maintained.

Insert — four steps

1Walk the fences down to a leaf. Always a leaf.
2Room? Slot it in sorted. Stop. Full (m−1) is legal.
3Overflowed to m keys? Write all m out, take the median: left half stays, median goes up, right half is a new page.
4Parent overflowed too? Repeat. Root overflowed? New root, 1 key — height +1.

Median of all m keys, the new one included. Never of the old m−1.

Delete — four steps

1Internal key? Overwrite it with its predecessor (or successor) and delete that from its leaf instead.
2Remove from the leaf. Still ≥ min? Stop.
3Underflow → borrow: check both adjacent siblings. Separator comes down, sibling's nearest key goes up. Stops immediately.
4Both at min → merge: pull the separator down, fuse the pages. Parent lost a key — repeat. Root emptied? Discard it — height −1.

Borrowing or merging an internal page? The moved key drags a child pointer with it.

What actually ships

Every database you have ever used indexes with the variant, not the original.

One change, and it is small

In a B-tree a key carries its record wherever it sits — a key in the root is data. In a B+ tree, internal nodes hold separator keys only and every record lives in a leaf. Separators are copies, so a key can appear twice: as a fence, and as data.

Then the leaves are linked left to right in a list.

Why that tiny change wins

Internal pages carry no payload → more fences per pagehigher fanout
Higher fanout → fewer levelsshorter tree
Range scan — "all rows between X and Y"walk the leaf list
Every lookup costs exactly h readspredictable latency
Lookup can stop early at an internal nodenever

The range scan is the real reason: WHERE age BETWEEN 30 AND 40 re-descends for every successor in a B-tree, but is one descent then a sequential walk in a B+ tree — the pattern disks are fastest at.

In the exam

Unless the question says B+, draw a plain B-tree: keys in every node, no leaf links, every key exactly once. The giveaway you have drawn a B+ tree by accident is a key appearing in both an internal node and a leaf — promoting a median moves it, it does not copy it.

The row that is not a difference is "comparisons per lookup". All three do about log₂n of them, because all three are binary searches over sorted keys — that is information-theoretically the floor and nobody beats it. The only row that ever differed is the one below it. So never say "B-trees are faster than AVL trees": say "a B-tree does the same search with far fewer boundary crossings, and boundary crossings are what the hardware bills you for." If your data fits comfortably in L2 cache, an AVL tree may well beat a B-tree — and that is the same sentence, read in the other direction.

Learn from other people's pain

The five mistakes, ranked by how often I see them.

1Splitting a page that is merely full. A page holding m−1 keys is maximally useful, not broken. You split only when it would hold m. Splitting early wastes work and lowers the fill, which was the entire point of rule 2.
2Taking the median of the wrong set. Insert the new key first, write out all m keys, then point at the middle one. Picking the median of the original m−1 gets it right by luck about half the time, which is worse than getting it wrong every time — you never find out.
3Erasing a key straight out of an internal node. That key is a fence, not just data. Overwrite it with its in-order predecessor or successor, then delete that key from the leaf it came from. Every deletion is a leaf deletion.
4Losing a child pointer. When you borrow or merge at an internal node, the key that moves drags a subtree with it. Check children = keys + 1 at every node before you hand the paper in — it is a two-second scan and it catches this instantly.
5Getting "order" wrong — or reaching for a merge too early. State your convention in line one (this deck: order m = max children). And when a page starves, check both adjacent siblings for a lender before merging: borrowing terminates immediately, merging can cascade to the root.

The 10-second audit, every single time you hand in a B-tree. Read the leaves left to right — sorted? Count keys in every node — within range, root exempt? Count children — keys + 1 everywhere? Put a ruler under the leaves — all on one line? Four checks. They catch every mistake on this slide.

Implementation · 1 of 2

One decision before you write a line: give every page a spare slot.

#define M 5 /* order: max children */ #define MAXK (M - 1) /* max keys, m-1 = 4 */ #define MINK (((M + 1) / 2) - 1) /* min keys, = 2 */ typedef struct BTNode { int n; /* keys in use */ int key[MAXK + 1]; /* +1: the overfill slot */ struct BTNode *kid[MAXK + 2]; int leaf; } BTNode; typedef struct { BTNode *root; } BTree; /* the whole search, and it really is this short */ BTNode *bt_search(BTNode *x, int k, int *pos) { while (x) { int i = 0; while (i < x->n && k > x->key[i]) i++; if (i < x->n && k == x->key[i]) { *pos = i; return x; } if (x->leaf) return NULL; x = x->kid[i]; /* one page read */ } return NULL; }

Decision 1 — the overfill slot

key[MAXK+1] and kid[MAXK+2] are one larger than the rules allow. That spare slot lets the code overfill a page on purpose, exactly as you do on scratch paper, and only then cut it. Size the arrays tightly and you need a special case for "the key that didn't fit" — which is where most hand-written B-trees go wrong.

Decision 2 — no parent pointers

A split hands its median upward, and the recursion is already standing on the parent when the call returns. Unlike the red-black fixup, nothing here ever walks up: no parent field, no stack, no sentinel.

Read bt_search once more

The inner while scans inside a page — free, the bytes are already here. The outer one is the descent, and each trip is one page read. The two loops are the two cost units from slide 3, in the same function.

Implementation · 2 of 2

Split, promote, and let the recursion do the climbing.

/* x holds MAXK+1 keys. The median leaves via *up; the new right page is returned. */ static BTNode *split(BTNode *x, int *up) { int mid = (MAXK + 1) / 2; /* = 2 */ BTNode *z = calloc(1, sizeof *z); z->leaf = x->leaf; z->n = MAXK - mid; /* = 2 */ for (int j = 0; j < z->n; j++) z->key[j] = x->key[mid + 1 + j]; for (int j = 0; j <= z->n; j++) z->kid[j] = x->kid[mid + 1 + j]; *up = x->key[mid]; /* moves up */ x->n = mid; return z; } static BTNode *ins(BTNode *, int, int *); /* → */ void bt_insert(BTree *t, int k) /* height changes here */ { int up; BTNode *r2 = ins(t->root, k, &up); if (!r2) return; /* no new root */ BTNode *r = calloc(1, sizeof *r); r->leaf = 0; r->n = 1; r->key[0] = up; r->kid[0] = t->root; r->kid[1] = r2; t->root = r; /* grew at the top */ }
/* NULL = absorbed, nothing for you to do. Non-NULL = I split; *up is the median and this is the page that goes to its right. */ static BTNode *ins(BTNode *x, int k, int *up) { int i = 0, promoted; BTNode *right = NULL; while (i < x->n && k > x->key[i]) i++; if (i < x->n && k == x->key[i]) return NULL; /* duplicate */ if (x->leaf) promoted = k; /* lands here */ else if (!(right = ins(x->kid[i], k, &promoted))) return NULL; /* child coped */ /* make room at slot i, then drop them in */ for (int j = x->n; j > i; j--) { x->key[j] = x->key[j - 1]; x->kid[j + 1] = x->kid[j]; } x->key[i] = promoted; x->kid[i + 1] = right; x->n++; return x->n <= MAXK ? NULL : split(x, up); }

Three return paths

Duplicate → NULL.
My child absorbed it → NULL.
I overflowed → the new right page.

A caller only ever asks "did my child hand me a key?" — the paper method, in one question.

The last line is the whole algorithm

x->n <= MAXK ? NULL : split(...) — under the limit stop, over it cut and pass the median up. That ternary is the cascade.

Then prove it

Assert after every insert: keys in range, children = keys+1, all leaves at one depth, in-order sorted.

The one sentence to keep

A B-tree is an m-way search tree that keeps every leaf on one level and every page at least half full — and it achieves both without ever measuring anything, because it only ever changes height at the root.
